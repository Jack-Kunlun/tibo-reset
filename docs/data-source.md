# 数据源

本文件回答一个问题：**数据从哪里来，为什么这么设计。**
如果你只想知道「采集挂了怎么办」，直接看最后一节。

---

## 1. 结论速览

| 项 | 结论 |
|---|---|
| 主链路 | **本机登录态浏览器**（CDP 驱动已登录的 Chrome），同一会话里收**两条流** |
| 两条流 | `/`（原创）+ **`/with_replies`（原创 + 回复）**。他的关键承诺大量落在回复里（见 §5） |
| 采集策略 | **增量优先**（翻到连续两整屏都已知即停），**每 72 小时自动全量回补一次**（见 §4.4） |
| 兜底 | 免登录 HTML 首屏（本机没开 Chrome 时），**只覆盖最近 7 条** |
| 采集范围 | **上一次明确重置往前 24 小时 → 现在**（见 §4.1） |
| 出口代理 | **实测探测**，不读 `HTTPS_PROXY`（在本机它是沙箱自己的端口，连不通 x.com，见 §4.5） |
| 他的回复 | **直接收 `/with_replies`**（登录态可用）。回复雷达已退为兜底、默认关闭 |
| 403 的性质 | **不是「X 封了境外 IP」，是 Cloudflare 拦云机房 IP 段** |
| 页面提示 | 两道互斥：采集失败（`errors` 非空）与数据超期未更新（按 `updated_at` 判据，见 §5） |
| 采集频率 | 本机定时任务，**实测每 2 小时**一轮。自动化配置声明的是 8 小时，两者不一致的成因未确证（见 §5） |
| 他给时间的方式 | 「星期 + 钟点」的松散组合、散在多条推文里（见 §4.6）。同一天常被 2–3 条从不同角度指到 |

## 2. 403 的根因（实测，不是推测）

同一时刻、同一 URL，两个出口的结果**完全不同**：

| 出口 | 结果 |
|---|---|
| 本机（住宅 IP，经本机代理 `127.0.0.1:7890`） | **HTTP 200**，213,770 字节完整页面，**4/4 稳定**，约 1.4 秒 |
| GitHub Actions（AWS 机房 IP） | **HTTP 403**，5,749 字节的 Cloudflare 挑战页 |

> ⚠ 这里的 `7890` 是**实测探到**的（§4.5），不是从 `HTTPS_PROXY` 读来的 ——
> 本机那个变量指向沙箱自己的出口端口，用它连 x.com 是 HTTP 000。这个区别很要紧：
> 早先几轮「本机可达」的结论恰好成立，是因为复用了手动以 7890 起的浏览器窗口。

本地那份页面里 `full_text:"…"` 与 `created_at_ms:` 都在，7 条推文一应俱全 ——
也就是说**解析逻辑从来没问题，问题只在出口 IP 的声誉**。

这个结论推翻了两条早期假设：

- ❌ 「x.com 在境内不可直连」→ 真实情况是本机走代理可直连，早期那次 3/3 超时是 curl 没走代理导致的
- ❌ 「换域名可以绕过」→ 见下节

## 3. 已排除的通道（别再试了）

以下全部在 runner 上实测过，不是猜的。省得下次再走一遍。

### 换域名 —— 无效

`x.com` / `twitter.com` / `mobile.twitter.com` **三个域名的 CF 策略完全一致**，
返回的是同一份 5749 字节挑战页。加完整浏览器头（`sec-ch-ua`、`sec-fetch-*`、
`upgrade-insecure-requests`）与裸 UA 的结果也一样。

### X 官方嵌入接口 —— 被限流

`syndication.twitter.com/srv/timeline-profile/screen-name/<user>` 返回 **429**（20 字节），
连试 3 次带退避重试仍是 429。这个接口本身是免 key 的，但机房 IP 被限流。

### X API —— 通，但缺 queryId

`POST api.x.com/1.1/guest/activate.json` → **200**，能拿到 guest_token；
`api.x.com/graphql/<queryId>/UserByScreenName` → **200**，能拿到 userId。

**但**：内置的 web bearer 已失效 —— 首轮实测（11:56）它还能换到 token，
几分钟后同样的 bearer 就返回
`{"errors":[{"message":"Invalid or expired token","code":89}]}`。
而 `UserTweets` 的 queryId 需要从 X 前端 JS 里现挖，拿 JS 又需要站点 HTML（403），
成了闭环。这条链路**理论上可达但当前不可用**。

### archive.org —— 可达但没用

`archive.org/wayback/available` → 200，x.com 有快照。
但快照 HTML 只有 **3,521 字节**，里面**没有任何 JS 引用**，
挖不出 bearer 与 queryId。作为「绕开 CF 拿页面源码」的入口是失败的。

### 第三方镜像 —— 全废

| 通道 | 结果 |
|---|---|
| `rsshub.app/twitter/user/<user>` | 404（账号不可见） |
| `nitter.net` / `xcancel.com` / `lightbrd.com` / `nitter.space` | 451 / 403 / 超时 |
| `nitter.privacyredirect.com` / `nitter.tiekoetter.com` | 200 但返回的不是 RSS 条目 |
| `api.fxtwitter.com/<user>` | 200，但只有用户资料，**没有时间线接口** |
| `api.vxtwitter.com` | 403 Cloudflare 挑战 |
| `api.twitterapi.io` | 403（要 key） |

### 免费代理中转 —— 全废

`allorigins` / `codetabs` → 522；`r.jina.ai` → 403 CF；`corsproxy.io` → 401。

### 另一个坑：`codex-resets.com` 在 runner 上也是 403

历史回填用的 `https://codex-resets.com/api/v1/resets` 在**本机**返回 200，
在 **runner 上同样被 CF 挑战**。由于历史回填只在冷启动执行，这个失败此前从未暴露。

### `with_replies` 与 `search` —— 未登录只返回空壳，**登录态可用**

想拿「他的回复」最自然的入口是 `x.com/<user>/with_replies`。未登录时它返回的是一张
826 行的「JavaScript is not available」错误页 —— 没有 RSC payload，一条推文都提不出来。

| 入口 | 字节 | `full_text` 出现次数 | 结论 |
|---|---|---|---|
| `x.com/<user>` 桌面 UA | 215,199 | **7** | ✅ 可用 |
| `x.com/<user>` 手机 UA | 215,731 | **7** | ✅ 同样可用（不是更少） |
| `x.com/<user>` Googlebot UA | 0 | 0 | ❌ 403 |
| `x.com/<user>/with_replies`（未登录） | 298,643 | **0** | ❌ 空壳错误页 |
| `x.com/<user>/with_replies`（**登录态**） | — | — | ✅ **正常工作，见下** |
| `x.com/search?...` | 299,101 | **0** | ❌ 空壳错误页 |

> ⚠ 别用 `grep -c 'full_text:'` 数这个 —— 它数的是**行数**，而这类 HTML 常整个写在一行，
> 会给出「1 条」这种假数字。用 `(html.match(/full_text:/g) ?? []).length`。

⚠ **上面这张表只说明了「未登录」这一侧的边界，不能从中推出「这条路是死的」。**
登录态下 `/with_replies` 完全可用：CDP 驱动已登录 Chrome 打开
`x.com/thsottiaux/with_replies`，标题是「Tibo (@thsottiaux) 的回复 / X」、
`loggedIn: true`，小步滚动能一路翻到 09-12（上一次重置那天）。实测一轮收下
**52 条回复**、覆盖 30+ 个被回复者。

**这条结论曾经被误读，代价是绕了一大圈**：把「未登录空壳」当成「拿不到回复」，
于是去建了「回复雷达」——抓别人推文的详情页反着找（抽样、命中 0，见 §5）。
**教训：未登录态的边界不等于登录态的边界**，而这个项目的主链路本来就是登录态
（§4）。判断某条路通不通之前，先确认是在哪一侧测的。

**未登录态下**，profile 首屏仍是唯一能拿到推文列表的入口，而它只给最近 7 条原创
（实测 Tibo 那 7 条跨 3.45 天，Udi 那 7 条跨 3.03 天）。

### 推文详情页 —— 可读，但只给部分回复

`x.com/<account>/status/<id>` 未登录可读，且**带回复列表**。这是唯一能拿到回复的入口。
边界有两个：

- 只渲染**部分**回复。实测一条有 50 条回复的推文，页面上只有 3 条。
- 需要先知道推文 id（只有首屏或雷达候选里有）。

payload 里配对作者靠的是**物理顺序**：一条推文的作者 `screen_name` 出现在它的
`full_text` **之前**（实测距离 1.9k–3.7k 字符），所以「前向最近的 `screen_name`」
就是该条正文的作者。解析在 `parseTweetDetail()`，契约由 `scripts/test-parse.mjs` 锁定。

## 4. 采集主链路：本机登录态浏览器

### 4.1 为什么必须登录

未登录的 profile 首屏只给 **7 条**原创。这不是「少一点」——2026-09-12 那次重置的
**5 条全部落在 7 条窗口之外**（含 "Reset all propagated"），观测台一次都没看见
它本该盯住的那件事。7 条是 X 的权限设计，不是换请求头能解的问题（已穷举验证，见 §3）。

改走登录态后，同一时间点的抓取对比：

| 口径 | 覆盖到 09-12 当天的重置帖 | 09-11 以来条数 |
|---|---|---|
| 未登录首屏 | ❌ 0 条 | 7 |
| 登录态时间线 | ✅ 全部 5 条 | 16 |

**采集下界 = `resets.json` 里最近一条 `type: "reset"` 往前推 24 小时。**
（实现在 `src/lib/collect.mjs` 的 `resetFloorMs()`。）

为什么不硬切在重置那一刻：重置当天的前序预告常早于最终确认推文。09-12 那组就是
—— 03:20 的「Hi Astra users. A reset and a quick update…」在前，08:09 的
「Reset all propagated」在后，相隔 5 小时。硬切在 08:09 会把 03:20 那条切掉，
而它恰恰是本轮最该被看见的一条。

### 4.2 怎么跑起来

走 Chrome DevTools Protocol（`src/lib/browser.mjs`）：不需要 Apple Events、
不需要任何系统授权、不读 cookie 文件。

```bash
# 一次性：起一个独立 profile 的 Chrome，在里面登录 x.com
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --user-data-dir="$HOME/.tibo-reset-chrome" --no-sandbox \
  --proxy-server="127.0.0.1:7890" \
  --remote-debugging-port=9222 --remote-allow-origins='*' \
  "https://x.com/login"
```

之后 `node scripts/collect.mjs` 会自己接上去：端口已在监听就**复用**（不打扰你开着的
窗口），否则用同一个 profile 起一个 headless 实例，采完自己退出。
登录态留在那个 profile 目录里（**在 `$HOME` 下，绝不进仓库**）。

四个踩过的坑：

| 坑 | 现象 | 处理 |
|---|---|---|
| headless 的 UA | x.com 稳定返回 **403**（正文 53B） | 加 `--user-agent=<真实 Chrome UA>`。**别把 403 归因到代理出口 IP** |
| 默认 profile | 远程调试被禁用（Chrome ≥136 起） | 必须用独立 `--user-data-dir` |
| 跳屏滚动 | **静默丢条目**：同一窗口跳屏拿到 12 条，小步拿到 16 条 | 小步滚动（一屏的 85%），不能用 `scrollTo(0, scrollHeight)` |
| host sandbox | Chrome 自身沙箱初始化失败 | 加 `--no-sandbox` |
| 冷启动慢 | 首次起一个 profile 实测 **>18 秒**，等待预算给小了会误判成「起不来」 | 端口就绪预算给到 120 秒（`browser.mjs` 里 400×300ms） |

一次采集的耗时：热启动（Chrome 已开着，直接复用）约 25–30 秒；冷启动（自己起
headless）约 60 秒。**大部分是滚动等待**（每步 0.8 秒），不是网络慢。

失败时错误信息会带上 **Chrome 自己的 stderr**（截尾 12 行，滤掉 macOS 的显示噪声）。
少了这一层，起不来只会报一句「端口未就绪」，而真正的原因（profile 被占用、
参数不认识）就在 Chrome 写的那一行里。

### 4.3 免登录 HTML 的已知缺陷：不能用来判断推文归属

这条降级路径把 RSC payload 里出现过的 `full_text` 全部收下，而 payload 里**混着
别人的推文**。实测有两条被记成 Tibo 的，实际分属 `@sama` 与 `@j_dekoninck`
（把原始 URL 打开，X 会直接跳到对方主页）。

浏览器路径没有这个问题：只收 `article` 里带 `/thsottiaux/status/<id>` 的条目。
所以 `data/tweets.json` 里 `foundVia: "timeline"` 的行属于**低可信度历史数据**，
`foundVia: "timeline-browser"` 才是可归因的。

### 4.4 增量优先，但必须周期性全量回补

已采到的推文**保存下来、不废弃**；下一轮只更新未读的时间段。

```bash
node scripts/collect.mjs                # 默认增量：翻到连续两整屏都已知即停
node scripts/collect.mjs --full          # 强制全量
node scripts/collect.mjs --full-scan-hours=24
```

**为什么是「翻到已知就停」而不是「查某段时间」**：X 没有任何「给我某段时间的推文」的
查询入口。时间线只能从最新往下翻，所以「只取未读部分」只能这么实现 ——
`isKnownScreen()` 判断一整屏是否**全部**已在库（`known` 集合），连续
`knownScreensToStop = 2` 屏命中才停。要求连续两屏而不是一屏，是为了容忍置顶推文
造成的错位。

**每次采集都会打印停在哪：**

```
  采集模式  增量（翻到已知推文为止）
  本轮新增  0 条
  停止原因  连续 2 屏都是已入库的推文
```

`data/stats.json` 的 `collect.stoppedBy` 记同样的东西：`known`（增量正常停）/
`floor`（到时间下界）/ `no-more`（X 没更多了）/ `exhausted`（兜底上限）。

**为什么不能只有增量。** 增量假设时间线连续且单调，而两个事实都不成立：

| 洞 | 后果 |
|---|---|
| X 的列表虚拟化，跳屏那一下渲染掉又卸载的条目**永久丢失** | 整屏漏采 |
| 他会删推 | 删掉的条目消失，但「已知」集合仍认为这段翻过了 |

这些洞**增量永远补不回来** —— 它看到已知的就停了，不会往回查。所以
`DEFAULT_FULL_SCAN_HOURS = 72`：距上次全量超过 72 小时（或库为空）时自动退化成全量。
`stats.json.last_full_at` 记上次全量的时刻。**动这块时不要拿掉全量回补。**

### 4.5 出口代理必须实测探测

`src/lib/proxy.mjs` 逐个候选端口发一次真实请求，第一个能连上 x.com 的胜出：

```
7890 → 7891 → 1087 → 10809 → socks5h://1080 → 8888 → 6152 → 8118 → $HTTPS_PROXY（兜底）
```

实测命中 `http://127.0.0.1:7890`，耗时 0.58 秒。

| 规则 | 说明 |
|---|---|
| 判据是「位置码 ≠ 000」而非「200」 | 403 也证明代理是通的，只有连不上才返回 000 |
| 环境变量排在**最后** | 本机 `HTTPS_PROXY` 被沙箱设成 `127.0.0.1:57119`，那是**沙箱自己的出口端口**，`curl -x` 它拿 x.com 是 **HTTP 000 / 0 字节**。真实代理在 7890 |
| `X_PROXY` 显式设置即权威 | `X_PROXY=off` / `none` → 强制直连，不探测 |
| 不用「端口开着」判断 | 端口在听 ≠ 连得通 x.com（57119 就是反例）。只有真发一次请求才算数 |

**这个坑的隐蔽处**：它时好时坏。复用一个**手动以 7890 起的**登录窗口时，连接根本不经过
我们传的代理参数，一切正常；一旦脚本自己起 Chrome（定时任务的常态），参数才真正生效，
结果是**静默拿到 0 条** —— 不报错、不崩溃，只是空。

### 4.6 他给时间的方式（实测，决定解析器要认什么）

这份清单来自 2026-09-22 那轮真实语料（69 条）。**他极少把时间写成一个正规日期**，
大量线索是「星期 + 钟点」的组合、散落在不同推文里：

| 日期 | 类型 | 原文 | 属于重置吗 |
|---|---|---|---|
| 09-15 | 原创 | `Tuesday is for random swag drops on your door handle` | 否（玩梗） |
| 09-16 | 原创 | `11pm on a Tuesday, big startup energy` | 否（作息自嘲） |
| 09-19 | 回复 | `OK fine. But it's also still coming in Tuesday` | **是**（上下文是 banked reset） |
| 09-21 | 回复 | `3am on a tuesday` | 否（回复「GPT-6 社区之夜」） |
| 09-22 | 原创 | `We are almost Tuesday and I promised a reset for Tuesday` | **是** |

三条结论：

1. **「Tuesday」在这一轮里出现了 5 次，分属三种语境**（玩梗 / 别人的活动 / 真承诺）。
   所以聚合必须按**目标日期**归簇，不能按「词」—— 09-15 那个周二和 09-22 那个周二
   根本不是同一天，混在一起会得出荒谬结论。
2. **钟点（11pm / 3am）全部落在非额度语境里**。这意味着：即便解析器认识钟点，
   这一轮也不该用它收窄窗口。**「看见了但不采信」要能说出来**，而不是假装没看见。
   这条被要求改成「采纳 3am 当窗口时刻」过一次（D-019）。**没有照做**，因为那条回复的
   被回复原文是 `the GPT-6 Community Night was 🔥` —— 他在聊社区活动办到几点。
   顺手查了另一条路「用他历史上的典型钟点当默认值」，同样不成立：
   `data/resets.json` 里 53 次重置铺在 **19 个不同小时**上，峰值（洛杉矶 17:00）也只占
   13.2%。**没有任何钟点可以当默认值。** 结论：这一轮的窗口只能是「当地时间一整天」，
   开启时刻落到北京时间 09-22 15:00。
3. **裸星期很常见**（`Tuesday`，没有 next/this 修饰）。解析器对它的处理是
   「最近的未来那个」；这在周三说 `a Tuesday` 时天然有歧义，必须标注待考。
   同时它**必须被当成具体表达**（`SPEC.weekdayBare`），否则会被「窗口过半」的
   过滤规则在当天下午整条丢弃 —— 这是 2026-09-22 修掉的一个静默漏检。

### 4.7 长推文只采到前半段（正文截断），以及怎么补回来

**边界本身**：X 对长推文在时间线/搜索页只渲染前约 **280 字符**，"Show more" 之后的节点
**不在 DOM 里**。采集取的是 `innerText`（`browser.mjs`），所以拿到的正文天然只有前半段。
这不是我们哪一行 `slice` 写错了 —— 是页面就不给你后半段。

**它为什么会变成一个真问题**：重置的宣告经常不是一条短推文，而是长公告里的**最后一句**。
2026-09-22 那条 GPT-6 公告正文 477 字符，前半段在讲模型与 API 降价，
「And one more thing. We are loading a banked reset into all accounts of our Plus, Pro and
Business users.」落在被切掉的后半段里 —— 采到的 273 字符里 `banked` / `reset`
**一个词都没有**，词表再全也读不出这是重置，整条被当作无关推文排除。

**怎么补**：历史 API（`codex-resets.com`）返回的是**完整正文**。所以每轮刷新历史时
顺手用它的正文回填本库里同 id 的推文（`patchTruncatedTexts`），补过的标 `text_full: true`。
两条纪律：

- **只在更长时替换**。上游偶有摘要化，用短的去覆盖长的会让识别能力无声退步。
- **归一化口径与推文库一致**（`\s+` → 单空格），避免同一份库里混进两种格式。

## 5. 采集的分工与触发

```
本机（住宅出口）— 定时任务触发
  node scripts/collect.mjs        # CDP 驱动已登录的 Chrome，增量收割（72h 自动全量）
  node scripts/build.mjs          # 构建产物（兜底页面 + OG 卡 + 小程序快照）
  node scripts/push-ingest.mjs    # 数据**直推后端** → 页面刷新即新
  git add data miniprogram && git commit && git push    # 留档
        │
        ▼
后端容器（机房出口 · reset.example.com）
  POST /api/ingest 落盘 → GET / 请求时用当前数据实时渲染整个页面

GitHub Actions（机房出口 · **只有改代码才触发**）
  push 代码 → 构建产物 → 发布 Pages（异地备份入口，不是主入口）
```

### 定时任务

| 项 | 值 |
|---|---|
| 调度 | WorkBuddy 自动化「Tibo Reset 采集（本机出口）」 |
| 工作目录 | `~/projects/tibo-reset` |
| 做的事 | 采集 → 构建 → **推两路**：git（留档）+ `POST /api/ingest`（线上立即生效）|
| 允许改动的范围 | 只允许 `data/` 与 `miniprogram/`，别的文件一律不碰 |

⚠ 数据**不经过 CI**。原先的路径是「push 上来 → CI 构建 → CI 转发 POST 给后端」，
2026-09-22 改成直推（D-025）：一是「数据变化触发构建」这件事本身已无产出（页面是请求时
渲染的），二是绕一圈反而让数据链多一个能断的地方。直推凭据在 `~/.tibo-ingest.env`，不进仓库。

**「实质变化」的判据**（这条决定了会不会产生垃圾提交）：
出现新推文（含回复流带来的）、推文时间被纠正、`resets.json` 变化、
某条推文的 `role` 从 `post` 变成 `reply`（说明这一轮才配上被回复的内容）。
**只是时刻字段变化不算** —— `tweets.json` 的 `updated_at`、`stats.json` 的
`generated_at` / `last_full_at` / `collect` / `days_since_last`、`signal.json` 的
`generatedAt`、以及由构建时刻派生的 `miniprogram/data/snapshot.js`。
为时间戳生成提交没有意义，只会污染历史（这也是 CI 那侧走「新鲜度短路、短路时不写文件」的同一个理由）。

**已知边界**：这个调度依赖 WorkBuddy 在跑。要「开机就采、完全脱离 WorkBuddy」，
可以改成 macOS `launchd`（`~/Library/LaunchAgents` 下的 LaunchAgent，`StartInterval = 28800`），
把上面那串命令写成脚本即可 —— 但**两者不要同时开**，否则会重复采集。

⚠ **CI 上完全不采集，一次都不试。** 它跑在机房 IP 上，必然被 Cloudflare 挑战 ——
所以「试一次」的净产出只有一条注定失败的记录，外加一面让读者麻木的横幅。
原先那条「数据陈旧时再试」的兜底采集已于 2026-09-22 移除（D-023）。

### 回复流（`/with_replies`）—— 回复的主路径

他的关键承诺大量落在「他回复别人的帖子」里。2026-09-22 一轮实测：原创流 17 条、
回复流 **52 条**、覆盖 30+ 个被回复者。最硬的一条证据是
「OK fine. But it's also still coming in Tuesday」—— **原创流里一个字都没有**，
而且它本身不含任何额度词，是靠被回复的内容才被读成预告的。

采集方式是**和原创流并列的一条流**，在同一个浏览器会话里跑（`collectStreams`）：

| 流 | 路径 | 失败语义 |
|---|---|---|
| 原创 | `/<handle>` | 主链路，挂了整轮判失败 |
| 回复 | `/<handle>/with_replies` | 补充，挂了记 `replyError`，**不**判失败 |

**上下文必须在收割当时配对**（`pairReplyContext`）。`with_replies` 把
[被回复的推文, 他的回复] 成对渲染，而 X 的虚拟列表滚过去就卸载 ——
DOM 顺序是配对关系的**唯一载体**，事后再看只剩一堆散条目，配不出谁回了谁。
配对结果存进 `inReplyTo`，识别侧靠它读额度语境（`signals.mjs` 的 `viaContext`）。

配对的两条防呆（**宁可漏配，不要错配**：假上下文会把无关推文的内容当成他的
回复语境，直接污染识别）：
- 被回复的推文必须**早于**回复 —— 时间倒挂的一律不认；
- 作者解析不出来的条目，既不当作他的，也不拿来当上下文。

```bash
node scripts/collect.mjs                  # 默认收两条流
node scripts/collect.mjs --no-replies     # 只收原创（排查用）
```

CLI 会打印回复流的采集形态（模式、停止原因、收下多少条、其中多少条带上下文）：

```
  库内推文  69 条（其中 52 条来自回复 —— 别人的帖子底下）
  回复流    增量（known） · 收下 2 条，其中带被回复内容 2 条
```

### 回复雷达（已默认关闭）

雷达是**在「`/with_replies` 未登录是空壳」这个误读下建的旁路**：盯住一批
「他会去回复的人」（`RADAR_ACCOUNTS`，默认只有 `udiWertheimer`），抓他们首屏推文
→ 抓这些推文的详情页 → 在回复列表里找他。

它**默认关闭**（`--radar` 才开）。实测它池里只有 1 个账号、一轮扫 6 条详情页命中 0，
而回复流一次收 52 条。留着默认开只会白花请求，更麻烦的是日志里多一行「命中 0」的
噪音，让人误以为回复采集没工作，而真正在工作的那条通道反被盖过去。

```bash
node scripts/collect.mjs                  # 默认不带雷达
node scripts/collect.mjs --radar          # 打开（兜底 / 排查）
node scripts/collect.mjs --radar-accounts=a,b
node scripts/collect.mjs --radar-limit=6  # 每轮每个账号最多开几次详情页
```

仍保留的两个设计决定（**改它时别丢**）：

- **候选按线索「排序」，不是「过滤」**。2026-09-21 那条预告，他回复的原推文是
  「你们这周没发布什么有意思的东西」—— 额度词出现在同一串推文的下一段里纯属运气。
  过滤式闸门会把它整条丢掉，回复里的承诺也跟着丢（`rankRadarCandidates`）。
- **命中时连同被回复的原推文一起入库**（字段 `inReplyTo`）—— 这条现在由回复流
  大规模供给，雷达只是零星补充。

**它是抽样，不是穷举**：详情页只给部分回复，所以「没命中」**不能**推出「他没回复过」。
X 会把高影响力账号的回复往上顶，这是它能工作的前提，不是保证。

### 「新鲜度短路」与数据陈旧判据

采集入口支持 `--max-age=<分钟>`：数据比这个时限还新时，**连请求都不发**。

```bash
node scripts/collect.mjs                 # 本机定时任务，总是采
node scripts/collect.mjs --max-age=180   # 手动重跑时避免白跑一轮
```

⚠ **它现在没有自动调用方**：原先是给 CI 兜底采集用的（CI 采不到，只能靠它在数据足够新时
提前退出），那套兜底 2026-09-22 已移除（`decisions.md` D-023）。能力保留，供手动使用。

短路时**不写任何文件**。否则 `stats.json` 的 `generated_at`（采集运行时刻）每轮都变，
而那个变化与「数据有没有变」无关 —— 提交判据是 `scripts/data-changed.mjs`，不是字节级 diff。

#### 数据陈旧由页面判定（取代原先「CI 每 30 分钟体检」）

「本机是不是还在跑」这件事，原先由 CI 的定时体检发现（它采不到，但能发现数据陈旧并挂横幅）。
那个定时器已移除，判据挪进了页面：

| 量 | 值 | 出处 |
|---|---|---|
| 本机采集周期 | **120 分钟** | `src/lib/render.mjs` 的 `LOCAL_COLLECT_INTERVAL_MINUTES`（**实测值**，见下） |
| 页面陈旧阈值 | **240 分钟** | 同一文件里用上面那个值 `× 2` 算出来 |

页面加载时（以及之后每秒）拿「当前时间 − `data/tweets.json` 的 `updated_at`」与阈值比较，
超过就显示「数据未更新」。取两倍周期，是因为本机采集有调度抖动、机器休眠后补跑等情况 ——
一倍余量会把「只是晚了一轮」也报成陈旧。

⚠ **时间锚点必须是 `tweets.json` 的 `updated_at`**（只在采集**成功**时推进），
不能是 `stats.json` 的 `generated_at` —— 后者采集失败时照样推进，拿它当「数据多新」会撒谎。

⚠ **周期这个数字对不上，如实记录**：WorkBuddy 自动化配置声明的 rrule 是 8 小时，而
`~/.workbuddy/logs/automation.log` 里六组 `lastRunAt → nextRunAt` 间隔**全部精确等于
2.00 小时**。仓库按**实测值 120 分钟**记录，成因未确证（没有去读 App 的内部调度存储）。
若哪天自动化真按 8 小时跑，页面会常态化显示「数据未更新」—— 那时改上面那一处常量即可。

`scripts/test-collect-warning.mjs` 有回归断言守护这条推导关系（含「阈值在源码里是**引用**
周期算出来的，不是字面量」）。

**旧设计的教训（保留）**：阈值曾硬编码 120 而周期是 480，于是每个周期里有 360 分钟超阈值
→ CI 每 30 分钟真去采一次、必然 403、必然写 `errors`、必然提交一条，**页面 75% 的时间
挂着「数据采集异常」横幅**。而它的成因是设计已知的，那面横幅于是从告警退化成噪音 ——
真出问题时你大概率已经习惯它了，这比不告警更糟。

### 本机提交什么，以及「有没有实质变化」怎么判

只提交 `data/` 与 `miniprogram/`（定时任务的改动范围，见上表）。

`miniprogram/data/snapshot.js` **跟着一起提交** —— 它内嵌了构建时刻（`generatedAt` / `now`
及其派生的全部预测值），每次构建都不同，但小程序要它才能离线首屏，所以 `.gitignore` 里
那行是有意注释掉的。污染历史的防线不在「不提交」，而在下面的判据：它自己变了不算数，
只有 `data/` 出现实质变化时才整体提交一次。

⚠ 原先这条写的是「**刻意不含 `miniprogram/data/snapshot.js`**」，那是 CI 提交时代的规矩 ——
CI 每 30 分钟自己构建一次，不排除它就会变成「48 条提交/天」。2026-09-22 起 CI 不再提交
任何东西，本机一轮一次，这条规矩随之作废（D-025）。

提交判据是 `scripts/data-changed.mjs`，**不是** `git diff --staged --quiet`。
后者是字节级判据，而 `data/` 下有字段每轮必然不同、却与「数据有没有变」无关：

| 文件 | 每轮必变的字段 | 为什么 |
|---|---|---|
| `stats.json` | `generated_at`、`last_full_at` | 采集**运行**时刻，失败轮照样推进 |
| `stats.json` | `stats.days_since_last` | 由 `now` 减 `last_at` 得到，每轮都在涨 |
| `signal.json` | `generatedAt`、`windowFrom`、`windowTo` | 时间窗跟着 `now` 滑 |
| `tweets.json` | `updated_at` | 只在采集**成功**时才推进 |

脚本抹掉这些字段再比：退出码 **0 = 有实质变化（提交）**、**1 = 只有时间戳在动（跳过）**。
反过来**必须**提交的是：出现新推文、推文时间被纠正、`role` 从 `post` 变 `reply`、
`resets.json` 变化、`errors` 内容变化。

⚠ `errors` 这条要按「首次失败必须落档、重复的失败不重复落档」来理解：

| 情形 | 判据 | 为什么 |
|---|---|---|
| 首次失败 `[]` → `[403]` | **提交** | 否则「线上挂着横幅」在仓库里没有痕迹；下一轮从仓库检出就成了「数据陈旧但页面一切正常」—— 页面会说谎 |
| 连续两轮同样失败 `[403]` → `[403]` | 跳过 | 状态已经在仓库里，下一轮检出照样挂得住横幅 |
| 错误内容变了 `[403]` → `[503]` | **提交** | 这是新信息 |

⚠ 脚本自己出错时**返回 0（按有变化处理）**：漏提交等于数据丢档，
「多提交一次」远好过「该提交的没提交」。

## 6. 日常怎么用

### 本机采集（正常情况）

前提：本机有一个已登录 x.com 的 Chrome profile（`$HOME/.tibo-reset-chrome`，
登录一次即可，见 §4.2）。

```bash
npm run collect        # 采集（默认增量）
npm run build          # 构建
git add data miniprogram && git commit -m "chore(data): ..." && git push
```

采集结束会打印**覆盖范围**：

```
--- 覆盖范围 ---
  来源      ✓ 登录态浏览器（完整时间线）
  采集模式  增量（翻到已知推文为止）
  本轮新增  0 条
  采集下界  2026-09-11T08:09:17.000Z（上一次重置 - 缓冲）
  库内推文  16 条
  信号识别  已发生 2 · 预告 0 · 线索 5 · 其余 9（共 16 条，时间窗自 2026-07-24）
```

看到「⚠ 免登录首屏（降级，只有最近 7 条）」就要当回事：数据确实写进去了，
但覆盖不到上一次重置 —— 那等同于回到了「漏掉 09-12 那次重置」的状态。
`data/tweets.json` 里的 `source` / `degraded` 字段会一起记下这件事。

**怀疑增量漏了东西**（页面上出现了库里没有的推文、或者数字对不上）：

```bash
node scripts/collect.mjs --full    # 强制全量重扫，一次补齐所有洞
```

采集跑完，数据由 `scripts/push-ingest.mjs` **直推后端**，页面刷新即新 —— 不需要重新构建，
也不需要等 CI。CI 只在代码变更时触发，与数据无关（D-025）。

### 怀疑采集坏了

```bash
node scripts/probe-sources.mjs     # 通道体检：六个候选组一次探完
```

它会给出每条通道的状态码、是否含推文正文、失败原因分布。

⚠ **探针用的是原生 `fetch`，不走代理**；而真实采集链路走的是 CDP + 真实 Chrome（跟随系统代理）。
所以本机跑探针会看着「全通道超时」，**这不代表真实链路不通** —— 本机经代理到 x.com 实测是 200
（`curl -s -o /dev/null -w '%{http_code}' -x http://127.0.0.1:7890 https://x.com/`），采集也一直在成功。

探针要回答的是另一个问题：「这条通道**本身**能不能用」。那仍然得在 runner 上问 ——
**用 `gh workflow run probe-sources.yml`**。两个环境的失败模式完全不同（本机超时、runner 403），
互相推不出来，而「谁被 Cloudflare 挡了」才是决定要不要换通道的依据。

### 页面挂着「数据未更新」

这是**页面自己算出来的**（不是 CI 报的）：最近一次**成功**采集距今超过了阈值
（240 分钟 = 两个本机采集周期）。说明那台跑采集的机器没在采 —— 关机、休眠，
或自动化任务停了。依次查：

1. 本机能不能采：`node scripts/collect.mjs`，看报错
2. 出口是否正常 —— **别用 `echo $HTTPS_PROXY` 判断**，它在本机指向沙箱自己的端口
   （`127.0.0.1:57119`），那个端口连不通 x.com。正确做法是直接看采集日志里
   `resolveProxy()` 探到了什么，或手动验一次：
   `curl -s -o /dev/null -w '%{http_code}\n' -x http://127.0.0.1:7890 https://x.com/`
   返回 `200` 才对（`403` 也算通，只有 `000` 是连不上）
3. 若本机代理正常但 X 改了页面结构 → 参考 `scripts/test-parse.mjs`，
   它锁定了 payload 的结构契约，改动前后跑一遍就知道有没有破坏解析
4. 自动化任务还在不在跑：在 `~/.workbuddy/logs/automation.log` 里搜任务 id
   `3800132b`，看它最后一次 `run finished` 是什么时候。**注意**：机器休眠期间调度器
   不会补跑，醒来后那几轮在日志里直接就是缺失的。

### 页面挂着「数据采集异常」

说明**采集真的失败过**（`stats.json` 的 `errors` 非空），且失败记录还没被一次成功的采集
清掉。错误文本就在横幅里逐条列着 —— 先读它，再按上面同样的顺序查。

## 7. 已知的未解项

- **采集只有本机这一条路径**（CI 不采集，见 D-023）。本机长期关机时数据会停更，
  页面会挂出「数据未更新」。这是**有意的**：宁可显示陈旧，也不假装新鲜。
- **`resets.json` 依赖上游收录，上游漏了就统计不到**。它现在**每轮都从
  `codex-resets.com` 刷新、按 id 合并**（本地是缓存、上游是权威；正文取更长的），
  不再只在冷启动回填一次 —— 后者会让本地库冻结在首次回填那一刻，上游新增的重置
  **永远进不来**：2026-09-22 那次 banked reset 就是这么丢的，用户看到卡已经发下来，
  观测台还说「距上次重置 10 天」（详见 §4.7）。
  刷新失败时按「本地有没有记录」分级：本地为空才算整轮失败，已有数据只记进
  `stats.json` 的 `history.error` 并打警告 —— 否则上游抽风会让页面上贴出
  「数据采集异常」横幅，而数据本身是好的，那是误导。
  不过**仍有一条单点**：上游没收录的重置，本地就没有。识别侧本来就能从推文里认出
  重置**事件**（`signals.occurred`），却只做展示、**没有回写进 `resets.json`** ——
  于是上游漏收录时，页面会出现「信号区认出来了、核心数字没跟上」的不一致。
  要彻底摆脱这条单点依赖，下一步得把 `occurred` 回写成记录。
- **增量存在结构性盲区**（见 §4.4）。虚拟列表抖动丢整屏、他删推，这两类洞增量补不回来，
  只能靠 72 小时一次的全量回补兜。**回补窗口内**的洞能补上，超过 72 小时没开机就永久丢了。
- **snapshot.js 的构建时刻内嵌问题只是被「判据」挡住了，没有从根上解决** ——
  它每轮构建都变，但不自造提交，靠的是「只有 `data/` 出现实质变化才整体提交一次」。
  根治需要把 `generatedAt` / `now` 改成取自数据时间戳，会改变小程序端的预测基准，
  所以留待单独确认。注意本机这条链路是**要提交** `miniprogram/` 的（见 §5），
  所以它靠的就是上面那条判据，而不是「不提交」。
- **回复雷达已退为兜底、默认关闭**（见 §5）。它是在「`/with_replies` 未登录是空壳」
  这个误读下建的旁路：天生抽样（详情页只给部分回复，实测 3 条而那条实际有 50 条），
  且对象池要人工维护。回复的主路径已改为直接收 `/with_replies`。
  而它曾经的**向前覆盖**限制也一并消失了 —— 雷达靠「抓的时候推文还在首屏 7 条窗口内」
  才能拿到 id，滑出约 3 天就再也拿不回来（2026-09-21 那条预告就是这么错过的）；
  `/with_replies` 直接列他的回复，实测能一路翻到 09-12。
- **回复流覆盖的是「他发起的回复」**。他在别人帖子下被回复、自己没再回，不在流里 ——
  那属于「别人对他说了什么」，本产品不跟踪。另外它同样受虚拟列表影响，
  增量 + 72 小时全量回补的机制与原创流一致。
- **`radar.json` 的 `targets` 不再接进主流程**。它当初的用途是「自动扩雷达对象池」，
  而回复流自己就带着「他回复了谁」（`inReplyTo.account`）——不再需要从命中记录里反推。
  这份文件保留，作为 `--radar` 打开时的留档。
- **未被采用的钟点线索目前只呈现、不参与计算**（`hypothesis.clockHints`）。
  这是刻意的：把语境无关的钟点算进窗口会造出没有依据的精确时间（见 `decisions.md` D-017）。
  但没有做「**钟点趋同检测**」—— 如果同一个钟点在线索里反复出现，那本身可能就是信号。
  2026-09-22 那轮的两个钟点（3am / 11pm）差别很大，本来也无法趋同，所以这条尚无机缘验证。
- **`hypothesis` 只产出单一锚定日**，取「最近一条含日期的硬证据」那一天。
  他若同时预告两个不同日期，较远的那条会**自己撑起一条预告**（`forecasts` 里退化为
  单条证据），两条互不合并 —— 合并只在「同一个 `dayNum`」之内发生（见 D-018）。
  当前语料里没出现过两个窗口并存的情况。
- **呈现层只读 `forecasts`**（`buildForecasts(signals, hypothesis)` 的产物），
  不再自己按时间戳去重、也不再自己拼证据链。两边各算各的正是本项目反复吃亏的地方。
