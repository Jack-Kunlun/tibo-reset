| 项 | 内容 |
|---|---|
| 产品名 | 等 TIBO 按按钮（Reset Observatory） |
| 一句话 | 记录 Codex 额度重置的历史节奏，告诉你「距上次重置多久」「大概还要等多久」「Tibo 有没有提前预告」 |

| 载体 | 网页（主站）+ 微信小程序（第二载体） |
| 状态 | **M0 已通过**（2026-09-21 评审确认，见第十一节） |

## 一、定位与目标

### 1.1 为什么做（外部事实，详见 `research.md`）

这个品类已经有 2 个微信小程序 + 7~8 个网站在做，其中「概率预测」这一层已被占。
靠同一个功能入场没有意义，所以本项目的差异化不在功能数量，在**三件别人没做对的事**：

1. **不讲「平均 7 天」。** 53 条真实记录里平均间隔 6.93 天，但**中位只有 3.22 天**，标准差 11.40 天。
   均值被两次极端等待（49.7 / 67.7 天）拉高——用均值做倒计时是错的。
2. **公开模型的成绩，包括它做不到的部分。** 时间分位数校准良好（说 50% 分位，历史命中 50.0%），
   但「7 天内是否发生」的区分度**低于盲猜**（Brier skill −2.3%）。两个数字都上页面。
3. **节奏在加速这件事，只有我们发现。** 平均间隔 12.39 → 4.92 → 3.03 天（三段，
   见 `model.md`）。任何基于全历史外推的预测都会系统性高估，我们在产品里先说出来。

### 1.2 目标（可判定）

| # | 目标 | 判定方式 |
|---|---|---|
| G1 | 有一个能直接给同行/招聘方看的公开链接，打开即见效 | 链接可在任意浏览器/微信内打开，首屏 1 秒内出数字与图表 |
| G2 | 有技术传播点：至少 3 个可被别人引用/讨论的结论 | 「中位 3.22 天」「节奏加速 76%」「校准 vs 区分度」三条结论在页面上可见 |
| G3 | 有可分享的物料，不依赖用户「记住这个站」 | 分享卡片（标题 + 关键数字 + 预览图）在微信/微博/X 内可正常展开 |

### 1.3 非目标（明确不做）

| 不做 | 原因 |
|---|---|
| 商业化：会员、付费、广告位 | 定位是作品；流量主门槛（UV≥1000）与 CPC 收入对本品类不成立 |
| 代充 / 额度买卖导流 | 微信侧必被处理，且与「当作品」的定位冲突 |
| 给「下次将于 X 时重置」的确定性时间承诺 | 触发开关在 OpenAI 手里，不在推文里。给确定时间就是把猜测包装成承诺 |
| 要求用户登录 / 授权 / 绑定 OpenAI 账号 | 采集用户自己的额度数据需要凭证，属账号安全红线 |
| 深色主题 | 与个人视觉体系冲突（水墨风浅色基调） |

## 二、用户与场景

| 角色 | 诉求 | 触发场景 | 频次 |
|---|---|---|---|
| Codex / ChatGPT 重度用户（主要） | 额度用完了，想知道还要等多久、值不值得现在开长任务 | 额度耗尽时 | 平均 8 天一次（由事件频率决定） |
| 同行 / 招聘方（作品受众） | 看这东西怎么做的、数据从哪来 | 一次性浏览 | 低 |
| 内容创作者 | 找可引用的数字 | 写稿时 | 低 |

**必须接受的产品事实：这是事件驱动型工具，用户平均每 8 天才想起一次。**
因此设计原则是「**打开就有答案，不需要学习**」，并且**不假设用户每天来**——
所以 G3 的分享物料比「留存」重要。

## 四、页面结构（信息层级）

```
① 顶栏        品牌 + 观测状态（当前北京时间，跟时钟走）
② 信号区      ← 只有存在「明确预告」时才占用视觉重量；否则一行冷状态
③ HERO        距上次重置的滚动倒计时（天/时/分/秒）+ 现在处在历史什么位置
④ 指标条      记录数 / 中位间隔 / 最长等待 / 当前已过天数
⑤ 还要等多久  中位剩余 + 区间 + 各窗口概率 + 校准成绩 + 节奏分段
⑥ 等待生存曲线
⑦ 每次间隔的离散分布
⑧ 最近记录    带原文链接的时间线
⑨ 页脚        数据来源与更新频率
```

**设计原则**：②③ 是「答案区」（进来就要拿到答案），⑤⑥⑦ 是「凭证区」（凭什么信你）。

## 五、功能详述

### F1 · 动态倒计时

| 项 | 规则 |
|---|---|
| 粒度 | 天 / 时 / 分 / **秒**。含秒是必要的——只到时/分时数字最快 60 秒才动一次，看不出「动态」 |
| 动效 | 每一位是 0–9 的竖向条，靠位移滚动；只滚动发生变化的位 |
| 位数变化 | 「天」从 9→10 时直接跳到目标位，**不做滚动动画**（否则看起来像发生了一次重置） |
| 无脚本 | 初始位置写在行内样式里，脚本被禁用时数字仍正确，只是不滚动（渐进增强） |
| 计时起点 | 最近一次重置的**公告时间**（口径见第六节） |

### F2 · 重置信号提示

这是风险最高的功能：**误报一次，整个产品的可信度归零。**

| 级别 | 触发条件 | 呈现 |
|---|---|---|
| `explicit`（预告） | 推文同时含【额度意图 ≥3 分】+【可解析的未来时间】 | 顶部醒目告示：「距窗口开启」跳动倒数（锚点写明北京时间）+ 预告时间窗口 + 双时区换算 + **依据 N 条推文**（挂在同一条预告里） |
| `occurred`（已发生） | 推文含重置词，且语境指向**已经发生**（`Reset all propagated` 这类过去陈述，或 `A reset` / `the reset` 这类名词化陈述），**且句中不含具体的未来时间**，也不落在假设 / 将来完成时语境里 | **不呈现** —— 只做内部判定（见下） |
| `hint`（线索） | 只有额度意图、或只有时间，两者凑不齐 | **只在没有预告时兜底展示一条带窗口的**；线索档配色与 badge 独立，不与预告混淆 |
| `none` | — | 一行冷状态：「时间窗内 N 条推文中没有检测到重置预告」 |

**信号区只讲未来。** 已经发生过的重置**不在页首列举** —— 它是往回看的事实，而这一区回答的是
「下一次什么时候」。同一段事实已有三处载体：顶部「距上次重置 N 天」倒计时、下方「最近记录」、
以及每轮采集日志。再在页首铺原文卡片，既把倒计时挤出首屏，也只是复述。

**但「已发生」的识别必须保留**（`signals.occurred`：识别 + 计数，不参与呈现）。
它与呈现是两件事：判定的作用是**保证不漏检** —— 数据里要能看见 09-12 那次重置。
不要因为不展示，就把识别一并删掉。

**识别必须可复核**：判定读取的是**时间窗**（下界 = `min(now − 回溯天数, 上次重置 − 24h)`），
窗口本身写进结果（`windowFrom` / `windowTo`）。**超窗的推文只是不参与本轮判断，一条都不删。**

**不静默截断**：硬结论（预告 / 已发生）全量保留；线索与未命中列表有上限，
但一旦触顶必须显式标记 `truncated`，让「你看到的是全部」这件事可被验证。

**综合分析（不只抓到一条 reset 就结束）**：除逐条判定外，还要产出**时间假设**——
把指向**同一当地日历日**的推文收成一条证据链，并分明强度：

| 强度 | 来源 | 作用 |
|---|---|---|
| `hard` | 含额度承诺（`explicit`） | **决定窗口** |
| `soft` | 只有时间、没有额度语境 | 仅作旁证，**不改窗口** |

- **为什么要聚合**：他习惯把时间线索分散在多条推文里（实测 09-16 提过一次「11pm on a Tuesday」、
  09-21 又提「3am on a tuesday」）。单条看都不是承诺，但多条并置时，「这个日期在他嘴里反复出现」
  本身就是证据。系统此前**从不看推文之间的关系**。
- **为什么软线索不改窗口**：那等于「他随口提到某个周二 → 页面报一个重置时间」。
  漏检伤的是覆盖，假信号伤的是可信度 —— 后者不可逆。
- **同日多条硬证据要收敛到最精确的那条**：一条说到「天」、一条说到「钟点」时取钟点。
- **未被采用的钟点线索要显式列出并说明原因**。「系统没看见」与「看见了但判它语境无关」
  是两种完全不同的沉默，用户必须能区分 —— 前者是缺陷，后者是判断。
- **呈现：一条预告 = 一个时间窗口，支撑它的推文挂在这条里面。**

  | 端 | 依据推文 | 理由 |
  |---|---|---|
  | 网页（≥760px） | **展开** | 证据是这条预告的可追溯性，不是可选的复核材料 —— 藏着等于要用户先信结论再验 |
  | 网页（<760px） | 收起（摘要行可见） | 单列铺开会把倒计时顶出第一屏 |
  | 小程序 | 收起（摘要行可见） | 同上 |

  摘要行写「依据 N 条推文 · X 条承诺 · Y 条同日提及」，归属关系一眼可见。
  **同一个窗口只有一条预告**；他若给了两个不同的日子，那就是两条预告。
  ⚠ 页面上**不再出现**「另有 N 条…不重复列出」这类行 —— 那是实现细节，不是信息。

**时间精度**：支持「星期 + 钟点」的联合表达（`3am on a Tuesday` → 当地 09-22 03:00，
精度 `instant`）。钟点必须钉在**同句的日期**上；句中无日期时才取最近的未来那一刻。

**窗口的文案按粒度定形 —— 具体时刻优先，区间只留给本来就含糊的粒度**（见 D-019）：

| 粒度 | Tibo 当地时间 | 北京时间 |
|---|---|---|
| `instant`（真说了钟点） | `2026.09.22（周二）03:00` | `2026.09.22（周二）18:00` |
| `day`（只说到哪天） | `2026.09.22（周二） 全天` | `2026.09.22（周二）15:00 起` |
| `week` / `week-part`（含糊） | 区间 | 区间 |

**不许把「全天」展开成 `00:00 – 23:59`** —— 那是把天粒度硬撑成钟点区间，读起来像他定在
当地午夜重置，属于凭空长出来的精度。同理「起」字不能省，否则 `09.22 15:00` 会被读成
「他定在 15:00 重置」。跨自然日的事实写在窗口块的页脚（`rangeNote`），不占主位。

**「距窗口开启」倒数**：预告卡内、窗口块上方，每秒跳动，**锚点写在标签上**（例：
`距窗口开启 · 北京时间 2026.09.22（周二）15:00`）。页首那个跳动的数字是「距上一次重置」，
是往回看的；往前看的这条是另一个。窗口开启后换成「窗口已开启 · 随时可能重置」，
不再报读数。两端文案同一套。

**额度意图计分**：单独一个 reset 词算 3 分；「额度词 + 新给词」合起来算 3 分。
只有额度词、没有「重新给」含义的（例如「我们在调 usage limits」）不得升级为明确信号。

**负向规则（必须有）**：真实数据里存在一条
`the main thing i was excited about launching this week will be next week instead` ——
含 `next week` 但讲的是**发布延期**。这类不得报成重置信号。

**时间呈现（用户明确要求）**：一律同时给出

- **北京时间**（用户所在）
- **Tibo 所在时区当地时间**（默认 `America/Los_Angeles`，公开报道其在旧金山办公；此为推定，代码里可配置）
- 两者时差

不做「翻译成北京时间就完事」这种丢信息的处理——推文原文用的是发推者的时间语境。

**歧义处理**：英文相对时间词（`next Tuesday` / `next week`）本身有歧义。
主解读给出确定窗口，若存在第二种合理解读则一并标注，不掩盖。

### F3 · 时间预测

用户明确要求「做出 reset 预测」。做法与边界：

| 项 | 规则 |
|---|---|
| 输出 | 剩余等待的**中位 + 区间**（80%），以及 24h / 3d / 7d 的发生概率 |
| 模型 | 分段常数风险模型（按已等待天数分桶）+ 样本外平移校准 |
| 校准 | 平移量由 out-of-sample 残差中位数算出，非人工拍定 |
| 披露 | 页面必须公开校准成绩，**包括失败的那一项**： |
| | ・「50% 分位」名义 50% → 实测命中 50.0% ✓ |
| | ・「7 天内是否发生」区分度 −2.3%，**不如直接猜会** ✗ |
| 计算时刻 | 预测是构建时/请求时快照，页面必须标注计算时刻，否则用户看到的是过时数字 |
| 禁止 | 不给「将于某天某时重置」的确定时间点 |

### F4 · 历史分布视图

两张图，都是「描述过去」而非「预测未来」：

| 图 | 内容 | 硬要求 |
|---|---|---|
| 生存曲线 | 纵轴「到第 X 天为止，历史上多少比例的重置已发生」；用户当前位置标在曲线上 | 超出绘图范围的极端值（>14 天）必须用**虚线尾巴 + 单独标注**表达，不得挤在某个刻度上造成「恰好卡在第 14 天」的错觉 |
| 间隔点阵 | 每次间隔一个点，按天数横向排布 | 横轴**线性等距**（曾用平方根压缩，导致刻度间距不等、会误导读者，已废弃）；超长等待单独排在右侧 |

### F5 · 历史记录时间线

- 每条：日期 + 类型标签（重置 / 发券）+ 原文摘要 + 原文链接
- 时间一律按**北京时间**显示并标注时区（部署在 UTC 机器上时不得显示 UTC 时间）

### F6 · 数据自动更新与降级

| 项 | 规则 |
|---|---|
| 频率 | 本机每 **8 小时**一轮（主链路）；CI 每 30 分钟一轮（兜底，机房 IP 必被拦） |
| 失败语义 | 采集失败**不影响已有数据**；错误写进状态文件，并在页面顶栏以降级样式暴露 |
| 数据来源 | 冷启动回填公开归档接口；日常走**增量**（只取未读时间段），**每 72 小时自动全量回补**一次 |
| 已采数据 | **保存且不废弃**。分析按**时间窗**读（下界 = `min(now − 回溯天数, 上次重置 − 24h)`），窗口写进结果可复核；超窗的推文只是不参与本轮判断，一条都不删 |
| 硬约束 | Cloudflare 拦的是**云机房 IP 段**，不是「境外 IP」—— GitHub Actions runner 必返回 403，本机住宅出口经代理实测 200。早期「境内不可直达 → 采集必须由境外执行」的结论已被推翻，主链路改为**本机登录态浏览器** |

### F7 · 双端一致

| 项 | 规则 |
|---|---|
| 一致性对象 | 数字口径、信号判定规则、图表几何**必须同源** |
| 图表 | 几何计算抽成与渲染目标无关的图元描述；网页序列化为 SVG，小程序画到 canvas |
| 布局 | 小程序**按自身宽度重新布局**，不得把 900px 宽的桌面图等比缩小（11px 图内文字会缩成 4px，等于没有） |
| 文案 | 两端共用同一套文案生成逻辑，避免两边说法不一致 |

## 六、数据口径（所有数字的定义）

口径不写清，数字就没法被质疑也没法被信任。**这是本文最重要的一节。**

| 项 | 定义 |
|---|---|
| 记录单位 | 一次「额度变化公告」= 1 条记录 |
| 类型 | `reset`（直接重置额度）/ `credit`（发额度券）——**两者都计入**，但在时间线上分别标注 |
| 计时起点 | 公告的发布时间（**不是**生效时间）。理由：用户感知到的是公告那一刻 |
| 间隔 | 相邻两条记录的时间差，按天计（含小数） |
| 当前已过 | 现在 − 最近一条记录的公告时间 |
| 纳入范围 | 全部记录，不做剔除。极端长等待（49.7 / 67.7 天）**保留并在图上标注**，不静默丢弃 |
| 已知分歧 | 各站口径不同（平均间隔有 7.2 / 8.0 / 8.7 天三个版本），差异源于「哪些算一次重置」无公认定义。本文口径与 `model.md` 一致 |

**反向要求**：任何统计数字在页面上出现时，必须能追溯到本节的某一条定义。

### 11.3 M2 技术选型（2026-09-21 确认）

完整文档见 `tech-selection.md`。已确认的资源前提：

| 项 | 结论 |
|---|---|

| 后端域名 | 另有已备案域名（非本仓库内） |

由此确立的架构是**境内外分离 + 单次采集双通道分发**：采集只在境外（GitHub Actions）发生一次，
产物分两路 —— git 提交供 GitHub Pages 构建，POST 推送供境内服务落盘 —— 两边共用同一份数据与同一套模型代码。

选型不改变本文的功能范围，只决定 F1–F12 用什么实现。其中两处需要你知道的结论：

- **F8（分享卡片）**：主站放 GitHub Pages 是已确认的选择，但 GitHub Pages 在境内的可达性不稳定。
  因此架构里加了一个境内镜像入口，**对外分享时用境内域名**，GitHub Pages 作为作品集入口。
- **F9（订阅消息）**：微信的长期订阅只对特定类目开放，工具类目拿不到，所以 F9 只能做成
  「一次授权对应一次通知」。F9 的定位因此是**重要事件提醒**，不是持续订阅推送。

**确认结论（2026-09-21）**：按 `tech-selection.md` 进入 M3。
