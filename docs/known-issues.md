### KI-008 bootstrap 的不确定性区间每次重算都不同（随机源是 `Math.random`）

**状态**：未解决 —— 用户看不到，影响很小；登记是为了防止它继续当「隐形前提」被人误判。

**根因**：`src/lib/predict.mjs:402` 的 `const rng = opts.rng ?? Math.random` —— 它是
`bootstrapCI` 的随机源（1000 次有放回重采样）。全库**没有任何一处**给 `rng` 传过实现，
所以每次调用都会得到一组新的分位数。

**影响范围**：

| 位置 | 影响 |
|---|---|
| `/api/state` 里的 `prediction.p.{lo,mid,hi}` 与 `medianDays.{lo,mid,hi}` | 每次缓存刷新都略有不同。页面与小程序**都不渲染这几个字段**（`render.mjs` / `buildForecast` 均未引用），所以用户看不见 |
| `miniprogram/data/snapshot.js` | 让这份构建产物**永远不可能稳定** —— 它是 D-027「不入库」的两条依据之一 |

**实测**：同一份数据 + 同一个 `BUILD_NOW` 连续构建两次，`lo/mid/hi` 依然不同；把这几行
排除掉之后，两次产物**逐字节一致**（这也是重构 `src/lib/snapshot.mjs` 时的等价性证据）。

**修法（未做，需要时再做）**：给 `bootstrapCI` 注入可复现的伪随机数（例如以 `now` 为
种子的 `mulberry32`），让「同输入 → 同输出」。前提是先确认没有调用方**依赖**这点抖动
（目前看没有）。⚠ 它**只**让产物可复现，不会让快照变得适合入库 —— 构建时刻内嵌那一半
仍在（D-027）。

## 已修复

### KI-001 时间窗口选取会挑到「更早但更含糊」的表达

**状态**：已修复（2026-09-21）。修法落实在 `src/lib/signals.mjs`，
回归用例见 `scripts/test-signals.mjs` 的【2.5】区块（9 项）。

**发现方式**：为 M1 评审构造明确信号样例时暴露。样例推文为

> `Good news: we will reset everyone's usage limits next Tuesday. Enjoy the weekend.`

解析结果 `timeWord = "weekend"`，窗口落在 **2026.09.19–09.20（已过去）**，
而推文真正承诺的是 `next Tuesday`（2026-09-22）。**一条未来预告被展示成了过去的窗口。**

**根因（两处，都在 `src/lib/signals.mjs`）**

1. **排序规则只看时间先后，不看表达的具体程度。**
   `parseTimes` 把「命中到的所有时间表达」都塞进 `out`，`to >= refTs` 过滤后用
   `sort((a, b) => a.from - b.from)` 取第一个 —— 于是**最早开始的窗口**胜出，与推文里
   哪个表达才是真正的主体无关。`weekend` 分支是无条件 push 的，
   连「Enjoy the weekend」这种寒暄都会生成一个候选窗口。

2. **「未来窗口」的判定过宽。** 只要求 `w.to >= refTs`，
   于是**大部分已经过去**的窗口仍然算「未来」。本样例中周末窗口在洛杉矶时区
   结束于 09-20 23:59（UTC 09-21 06:59），刚好晚于发推时刻，就被当成有效未来窗口。

**影响**：F2（重置信号提示）是本产品**风险最高**的功能——误报一次，可信度归零。
本条不产生「假信号」，但会产生**错窗口**（把 A 时间说成 B 时间），严重程度不低于误报。
当前真实数据下没有明确信号，所以线上表现尚未暴露。

**修法（已实施）**

1. **给每个时间表达加具体程度权重 `spec`**，同时记录它在原文中的位置 `idx`。
   选取顺序改为：**具体程度优先 → 原文位置靠前优先 → 时间靠前优先**。
   分档：

   | 档位 | 值 | 例子 |
   |---|---|---|
   | 绝对日期 | 100 | `2026-10-03`、`Oct 3` |
   | 带修饰的星期 | 92 | `next Tuesday`、`this Tuesday` |
   | `in N hours/minutes` | 88 | `in 2 hours` |
   | 裸星期 / 明天 | 86 | `Tuesday`、`tomorrow` |
   | 今晚 / 今天 | 72 | `tonight`、`today` |
   | `in N days/weeks` | 62 | `in 3 days` |
   | 半周（early / end of week） | 55 | `end of next week` |
   | 整周 | 40 | `next week`、`this week` |
   | 周末 | 28 | `weekend` |

   于是 `next Tuesday`（92）必然压过寒暄里的 `weekend`（28）。

2. **含糊表达（`spec ≤ 50`，即整周与周末）收紧未来判定**：要求**窗口还剩一半以上**
   （窗口中点仍在未来），否则视为在说已经过去的那一周/那个周末。

   > 注意这里刻意没有把「半周（55）」并入含糊档：`early/end of next week` 指的是下一个
   > 自然周内的固定区段，不会指向过去；而 `this week` / `weekend` 才有「说的可能是刚过去那个」的歧义。

   反向保护也补了用例：**没有更具体表达时，`weekend` 仍须正常作候选**，不能一刀切禁掉。

**回归用例**（`scripts/test-signals.mjs`【2.5】，9 项）

| 用例 | 断言 |
|---|---|
| 样例句（周五发推） | 时间词 = `next tuesday`，窗口 = 9/22 |
| 样例句（周日晚上发推） | 已过半的周末被剔除，主解读仍是 9/22 |
| 只说周末且该周末已过半 | 无未来窗口，且不升级为信号 |
| 只说 weekend 但无更具体表达 | 仍正常产出窗口（防止过度收紧） |
| `tomorrow` + `weekend` 并存 | `tomorrow` 胜出 |

**同类风险提示**：任何「从多个候选中挑一个」的逻辑，都要先问「候选之间的优劣维度是什么」。
只按单一维度（这里是时间先后）排序，等价于把选择权交给巧合。

### KI-002 上游新增的重置永远进不了库；长推文正文被截断，重置语义跟着丢

**状态**：已修复（2026-09-23）。修法落实在 `src/lib/collect.mjs`
（`mergeHistory` / `patchTruncatedTexts`），回归用例见 `scripts/test-history.mjs`（37 项）。

**发现方式**：老大报「重置卡已经发放了，你怎么没统计到」。当时页面上「距上次重置」
显示 **10.5 天**、记录总数 **53**，而 09-22 那次 banked reset 早就发放了。

**根因（两处独立，只修一处都不够）**

1. **历史记录只在冷启动回填一次。** `runCollection` 第 1 步的守卫写作
   `(opts.bootstrap || history.records.length === 0)` —— 于是 `resets.json` 一旦有内容，
   就再没有人去拉上游，本地库**冻结在首次回填那一刻**。上游（`codex-resets.com`）
   09-22 当天就收录了那条 banked reset，本地永远是 53 条。
   这一条**在 `docs/data-source.md` §7 里被当成「设计边界」写着**（原文：
   「`resets.json` 不会自动发现新的额度重置。历史回填只在冷启动执行」）——
   它是个 bug，不是边界，只是症状（数字停在旧值）从不报错，所以没人把它跟投诉连起来。

2. **长推文正文被 X 页面截断到约 280 字符。** 采集取的是 `innerText`
   （`src/lib/browser.mjs`），而 X 对长推文在时间线/搜索页只渲染前约 280 字符，
   "Show more" 之后的节点**不在 DOM 里**。09-22 那条 GPT-6 公告正文 477 字符，
   前半段讲模型与 API 降价，「And one more thing. We are loading a banked reset into all
   accounts…」**落在被切掉的后半段**里 —— 采到的 273 字符里 `banked` / `reset`
   一个词都没有，词表再全也读不出来，整条被信号识别当无关推文排除。

   > 这一条尤其值得记：**修法的第一版是错的**。当初想的是「把最后一个空格换成不换行空格」，
   > 拿真实数据一跑才发现值里根本没有可用的断点。同理，这条也不是靠读代码想出来的 ——
   > 是把上游正文与本地正文**逐字节对齐**才看见的。
   >
   > ⚠ **这一处只修了一半**：回填的原料来自上游，**上游没收录时无从补起**。
   > 2026-09-29 那次丢数据正是「本地截断 + 上游也滞后」两个条件叠加 —— 见 **KI-009**
   > （改成从推文详情页取全文，不再依赖上游是否收录）。

**影响**：观测台的头号问题就是「上次重置是什么时候」。这条坏了等于不回答主问题，
且**表现完全正常**（页面照常渲染、图表照常画、没有任何错误），只有数字是旧的。
另有一处口径分裂：信号区认出了这条（`occurred`），核心数字却停在 09-12，
两处自相矛盾。

**修法（已实施）**

1. **历史每轮刷新并按 id 合并**（`mergeHistory`）。本地是缓存、上游是权威，
   但**不能无条件覆盖**：唯独 `text` 取两者中**更长的**（上游偶有摘要化，
   用短的去覆盖长的会让识别能力无声退步）；缺 id 或时间非法的条目直接跳过。
2. **用上游的完整正文回填被截断的推文**（`patchTruncatedTexts`），
   补过的标 `text_full: true`。只在更长时替换；归一化口径与推文库一致
   （`\s+` → 单空格），避免同一份库里混两种格式。
3. **短路判断带上「历史有没有变」**：`if (skippedFresh && !historyChanged && textPatched === 0)`。
   否则会出现一个死结 —— 本轮因数据够新而短路、拉到的历史不落盘，
   而下一轮同样短路，这条新记录**永远**进不了库。
4. **上游失败按「本地有没有数据」分级**：本地为空才算整轮失败；已有数据只记进
   `stats.json` 的 `history.error` 并打一行警告 —— 否则上游抽风会让页面上贴出
   「数据采集异常」横幅，而数据本身是好的，那是误导。

**被否掉的选项**

| 选项 | 否掉的理由 |
|---|---|
| 保留「只在冷启动回填」，靠人工发现后手动跑 `--bootstrap` | 依赖人记得。09-22 这次就是没人发现，直到用户看到卡发下来 |
| 历史整体以上游覆盖本地 | 会丢掉本地更完整的正文（上游偶有摘要化），识别能力会无声退步 |
| 从推文识别出 `occurred` 后自动回写 `resets.json` | 方向对，但推文侧判据本身还不完备（长推文截断就是反例），现在回写会把误判固化进历史。**留作后续**，记在 `data-source.md` §7 |

**回归用例**（`scripts/test-history.mjs`，37 项）：合并的新增/更新/更长正文保留/脏数据跳过、
回填的补全与「更短不动」、以及**源码级接线断言**（「历史刷新不再被
`history.records.length === 0` 守护」「短路条件包含 `historyChanged`」）——
这一组断言是刻意的：这两个 bug 都是**静默缺失**，纯函数单测全绿也可能调用点被删。

**顺带修掉的测试夹具缺陷**：`scripts/test-shared.mjs` 曾把 `NOW` 写死成
`2026-09-21T02:00Z`，而 `sinceDays` 是「最新记录 → now」的右删失区间 ——
本次新增 09-22 记录后它变成负数，生存曲线的时间轴也把数据点甩到画布外，
两个不相干的断言一起红。已改为「最新记录 + 6 小时」：永远成立，且保持确定性
（不用 `Date.now()`，否则失败无法复现）。

**同类风险提示**：**「只在首次执行」的初始化逻辑是这类 bug 的高发区**。
写 `if (xxx.length === 0)` 时先问一句：这个条件成立过一次之后，
后续还需要它吗？需要的话，判据应该是「有没有变化」，而不是「是不是空的」。
另外，**任何把「已知限制」写进文档的地方，都该回头确认它到底是限制还是 bug** ——
这条限制在文档里躺了三天，期间一直在丢数据。

### KI-003 两处对「上一次重置」的定义不一致（发券型算不算）

**状态**：已修复（2026-09-23，口径决定见 D-028）。

**现象**：同一条 09-22 记录，两处结论不同。

| 位置 | 定义 | 09-22 之后的结果 |
|---|---|---|
| `buildStats` / 页面「距上次重置」（`chart-data.js`） | **所有**记录（含 `type: 'credit'` 发券型） | 锚到 09-22，显示 0.29 天 |
| `resetFloorMs`（采集下界 / 信号窗口下界） | **只认 `type: 'reset'`** | 仍锚到 09-12，下界 = 09-11T08:09Z |

**这不是笔误，是被测试钉住的刻意设计**：`scripts/test-parse.mjs` 显式构造了一条
`{ type: 'credit', announced_at: '2026-09-14…' }` 并注释「更晚，但不是重置」，
断言下界仍锚在最近一次 `reset`。所以当初登记时写明「改动它等于推翻一条既有设计，
不是修 bug，需要产品口径确认」。

**决定（2026-09-23）**：**发券型算一次重置。** 判据是产品要表达的那件事 ——
对用户而言，普通重置与发券型都是同一件「额度被补充了」，页面文案（`render.mjs`
的「普通重置」/「发券型」标签）与 `buildStats` 也都按同一件事处理。
两者口径统一到「含 credit」，与页面一致。

**顺带纠正了本条当初的定位**：它被登记成「需要产品口径确认」，但**这个口径早就在
PRD 里定过** —— §6 数据口径写「`reset` / `credit` **两者都计入**，但在时间线上分别标注」，
§11.1 的 M0 需求基线 #4 又把「`credit` 是否计入统计」正式确认为「计入」。
所以它不是待拍板的产品问题，而是**实现与已确认基线不一致** —— 页面按 §6 做了，
采集下界没跟上。登记时低估了它（详情见 D-028）。

**修法**：`resetFloorMs` 的过滤器由 `r?.type === 'reset'` 改为
`RESET_LIKE_TYPES.has(r?.type)`（`new Set(['reset', 'credit'])`）。
**显式列两种类型，而不是写成「任何带 `announced_at` 的记录」** —— 将来上游若新增
别的类型（故障声明、维护通知…），它该不该推进采集下界是另一个问题，不该被那一行默默决定；
`test-parse.mjs` 补了一条 `type: 'maintenance'` 的守卫用例钉住这点。

**影响的量级（实测，都不是推测）**：

| 面 | 变化 |
|---|---|
| 采集下界 | 09-11T08:09Z → 09-21T18:23Z（09-22 那条发券 − 24h 缓冲）。**少回扫约 10 天** —— 这正是原条目里说的那笔代价，现在没有了 |
| 信号窗口 | **不变**。窗口下界取「now − 60 天」与「下界」里更早的那个，60 天（07-25）远早于两者，所以下界动不了它。实测重建快照：`windowFrom` 只差构建时刻的 12 秒（`04:04:15` → `04:04:27`），与口径无关 |
| 页面 | 无变化（本来就是对的） |

**连带改动**：`scripts/test-parse.mjs` 里原本复用 `floor` 的那组 `normalizeTimelineItems`
用例改为自带写死的 `sinceMs` —— 它测的是去重 / 排序 / 裁剪本身，不该被 floor 的口径牵着走。

**留下的坐标**：两处口径统一了，但 `resetFloorMs` 与 `signals.mjs` 的 `latestEventMs`
仍是两个函数 —— 用途不同（一个答「该从哪儿开始扫」，一个答「额度有没有落到账」），
别因为口径统一就把它们合并（见 KI-004 那节里的说明）。

### KI-004 已兑现的预告仍以「随时可能重置」展示

**状态**：已修复（2026-09-23）

**现象**：页面「明确信号」区块一直挂着

> 距窗口开启 · 北京时间 2026.09.22（周二）15:00 · **窗口已开启 · 随时可能重置**

而那次重置**已经在 09-23 02:23 真的发生了**（第 54 条记录，发券型 credit）。
一条**已经兑现**的预告被展示成「还没发生、随时会发生」—— 这比不显示更糟，
它把读者的判断方向整个带反。

**根因**：`src/lib/signals.mjs` 里那段「未来窗口」过滤

```js
const future = times.filter((w) => {
  if (w.to < refTs) return false;
  ...
});
```

只跟**推文自己的发布时刻** `refTs` 比。它回答的是「他发这条时，说的那天还在不在未来」——
那个判据当时是对的，但它是**静态的**，不会随时间失效。于是预告兑现之后，那条推文
仍然留在 `explicit` 里 → `buildForecasts` 照旧产出预告 → 页面照旧渲染。

**影响范围**：只要他预告过、且预告兑现（或窗口走完），页面就会一直挂着那条预告。

**修法**：`detectSignals` 新增 `opts.lastResetAt`（毫秒），两道判据任一成立即视为过期：

| 判据 | 含义 |
|---|---|
| `window.to < now` | 窗口已走完（落空或已兑现，都不该再作为「未来预告」挂着） |
| `lastResetAt >= window.from` | 窗口开启之后已发生过额度事件 → 预告兑现了 |

三处关键实现选择，都不是随手写的：

- **过滤位置在构造 `hypothesis` 之前**（用 `live` 而不是 `analyzed`）：一条预告只有一个去处，
  撤回它就要把它挂着的同日提及一起撤回。否则页面会既说「没有预告」、又列着 4 条依据。
- **口径用新的 `latestEventMs`（不分 reset / credit），刻意不复用 `resetFloorMs`** ——
  当时后者只认 `type === 'reset'`（就是 KI-003 那个口径），而这次兑现的恰恰是发券型；
  混用会让这条修复在真实数据上根本判不出来。
  （2026-09-23 补注：`resetFloorMs` 的「发券型算不算」口径已按 D-028 统一为**算**，
  但这两个函数**仍然分开** —— 用途不同：一个答「额度有没有落到账」（不分类型、不减缓冲），
  一个答「该从哪儿开始扫」（按类型过滤、往前减 24h）。本条修复不因那次统一而可以简化。）
- **`server/index.mjs` 的缓存 key 必须同时含 `lastResetAt` 与「当前小时」**：前者让
  「预告兑现」立刻失效，后者让「窗口已过去」这个**时间驱动**的判据也能失效。
  少了任一项，修复等于没做（页面看着正常，只是永远停在旧结论上）。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 在渲染层过滤（`render.mjs` 跳过过期 forecast） | 只治页面，`/api/state` 与小程序仍拿到过期预告 —— 同一份数据两个结论，正是 KI-002 那类问题的形状 |
| 在 `analyzeTweet` 里就丢掉 | 它拿不到 `now`（只有 `refTs`）。那是「这条推文的历史判定」，改它会污染历史回顾 |
| 一律不展示 explicit（修过头） | 观测台会彻底失去预告能力，而这个错误在真实数据上**看不出来** —— 当下恰好没有未来预告，页面一样是空的。所以补了两条反向用例把它钉住 |
| 只按「窗口是否已过去」判 | 本次场景里窗口到 09-23 14:59 才结束，而重置 02:23 就发生了 —— 只看窗口会漏掉主角 |

**回归用例**：`scripts/test-signals.mjs` 第【7】组（10 项），含两条反向用例
（未来预告必须保留、重置发生在窗口开始之前不算兑现、不传 `lastResetAt` 时不动旧行为）。

**后续（2026-09-23 已补）**：这条修复**改掉了「页面上一定有预告」这个前提**，
但 `scripts/check-consistency.mjs`【⑤ 倒计时锚点自洽】里那句「页面必须有 `.sig-cd`」
没跟着改，于是从修复那天起它一直红着：`✗ 页面上的倒计时块可解析（0 个）`。
**页面没毛病，是判据少了个前提** —— 没有预告时页面走 `sig-idle` 静默态，
本来就不该有倒数块（`render.mjs:212` 只在 `forecasts` 非空时才渲染 `forecastBlock`）。

修法：**先看页面处于哪一档，再决定断言方向** —— 存在预告块
（`data-level` 非 `hint` 的 `.sig` section）时要求有 `.sig-cd`；
不存在时**反向断言**「不得出现 `.sig-cd`」（这样本条的过滤将来若失效，它会红）。

判据刻意**不用**静默态标记 `sig-idle`：它在「留档触顶」那条小提示上也在用
（`render.mjs:187`），预告在场时同样会出现，拿它判静默会误伤。

双向反向验证过：静默态下注入假 `.sig-cd` → 红；注入假预告块但不带倒数 → 红；还原即复绿。

> 教训：**修复「不再显示某个东西」时，一定要顺带搜一遍「有没有断言它必须显示」。**
> 这类断言平时不会失败，恰好在你修复生效的那一刻第一次失败 —— 很容易被当成
> 「修复搞坏了什么」而往错的方向查。这与 KI-006 是同一形状：**防线自己写错了前提**。

### KI-005 时间窗起点把 ISO 串直接渲染到页面上（真机可见）

**现象**：小程序「静默态」那一行的副行显示

```
时间窗自 2026-07-25T02:15:29.011Z 起
```

机器格式，而且串长到把右对齐的副行**顶出卡片边界**（真机截图，不是推测）。

**根因**：`miniprogram/utils/view.js` 的 `buildSignal` 把一个**原始值**直通进了模板：

```js
windowFrom: sig.windowFrom || '',   // 数据层给的是 ISO 串
```

数据层输出 ISO 串这件事本身是对的 —— `signals.mjs` 的 `windowFrom` 是「本轮实际取用的
时间窗」，保留原始值才可复核。**漏的是渲染层的解析**：同一个文件里 `evidenceView`
处理推文时刻时做了解析（`new Date(e.createdAt).getTime()`），这一处没有，
于是机器格式一路漏到了界面上。

**顺带暴露的两端不一致**：网页端同一行写的是
`String(sig.windowFrom).slice(0, 10)` —— 它「碰巧」看得过去，但有两处偏差：

| 偏差 | 说明 |
|---|---|
| 切的是 **UTC** 日期 | 窗口起点落在 UTC 16:00–24:00 时会显示**前一天**，而页面上其它时间全是北京时间 |
| 格式不统一 | 输出 `2026-07-25`，页面别处是 `2026.07.25` |

小程序修好之后两端会**显示出不同的日期**（一个 `2026.07.25`、一个 `2026-07-25`），
这个差异反而比原来更容易被发现。

**修法**：

- `miniprogram/utils/format.js` 新增 `toTs(v)`（ISO 串 / 时间戳 → 时间戳，取不到给 `NaN`）
  与 `fmtDay(v)`（→ 北京日期 `2026.09.12`，取不到给空串）。**解析规则只留一份**。
- `view.js` 内四处手写的 `new Date(x).getTime()` 统一收敛到 `toTs`，`windowFrom` 走 `fmtDay`。
- `index.wxml` 给副行加 `wx:if` —— 取不到起点时整行不出现，否则会渲染成「时间窗自  起」。

**回归用例**：`scripts/test-miniprogram.mjs` 第【11】组（6 项）。刻意用**合成输入**而
不是真实数据 —— 真实窗口起点天天在变，拿它当断言基准，测试会自己过期。含一条反向用例：
`2026-07-25T18:30:00.000Z` 必须得到 `2026.07.26`（这条能区分「按北京切」和「按 UTC 切」），
以及「任何输入都不许吐出 `T` / `Z` / 连字符」。

**网页端同一处也已改**：`src/lib/render.mjs` 的 `sig-idle` 分支原本是 `.slice(0, 10)`，
现改用该文件里现成的 `fmtDate(iso)`（按 `Asia/Shanghai`、输出 `2026.07.25`），
取不到起点时整行不出现，与小程序端对齐。本机起服务已验：`时间窗自 2026.07.25 起 · 共扫 86 条`。

⚠ **这两端的生效方式不同，别混为一谈**：

| 端 | 生效方式 |
|---|---|
| 小程序 | 代码在包里，微信开发者工具**重新上传版本**即生效（数据本来就联网取） |
| 网页 | 由容器内的后端**实时渲染**，改代码不改镜像等于没改 → 要 `ship-image.sh` + `update-image.sh` |

所以网页端这一处虽然代码已经改了，**没重建镜像之前线上仍是旧行为**（显示 `2026-07-25`）。

### KI-006 复制原推链接在授权被拒后静默失效（点下去什么都不会发生）

**状态**：已修复（2026-09-23）

**现象**：在隐私弹窗里点过「拒绝」的用户，之后点「复制原推链接」**没有任何反应** ——
不弹提示、不报错、界面也不显示链接本身。用户既拿不到链接，也不知道为什么拿不到。

**根因**：`wx.setClipboardData` 是**隐私接口**。微信官方《小程序用户隐私保护指引内容介绍》
的接口映射表里，它是和 `wx.getClipboardData` 一起挂在「读取你的剪切板」这一条下的
（**写与读被合并归类**，措辞粗糙但确实如此）。未声明（errno 112）或用户拒绝授权（103/104）时
**不会走 success**。而两处调用点都只写了 `success`：

| 位置 | 问题 |
|---|---|
| `pages/index/index.js` → `onCopySource` | 只有 `success` |
| `pages/history/index.js` → `onCopy` | 只有 `success` |

**为什么这条值得留个坐标**：它属于「静默失效族」，但比前几例更隐蔽 ——
**连界面上的降级路径都不存在**。「复制原推链接」那四个字是 `<text bindtap>`，
完整的 URL 从不渲染，所以失败时用户连「长按手动复制」这条退路都没有。

**顺带澄清一个会被误读的地方**：隐私指引里展示的条目名是「读取你的剪切板」，
很容易被读成「这个小程序在偷看我的剪贴板」。本项目实际**只写不读** ——
全库零 `getClipboardData`。那句话是微信把两个 API 合并归一类的产物，开发者改不了措辞。

**修法**：新增 `miniprogram/utils/clipboard.js`，由 `copyText(url)` 统一收口
success / fail / toast；两个页面各删掉手写实现，改为一行调用。

**刻意把两类失败分开**（因为用户能做的事不一样）：

| 错误 | 文案 | 理由 |
|---|---|---|
| 103 / 104（用户拒绝） | 需要同意隐私授权，请再点一次 | 他有权改主意；官方弹窗被拒后 10 秒内不会重弹，「再点一次」是可执行的 |
| 112（未声明）/ 未知 | 复制失败，请稍后重试 | 用户做什么都没用，不该把他引向隐私弹窗 |

**回归用例**：`scripts/test-miniprogram.mjs` 第【12】组（9 项）。核心是一条**遍历式守位** ——
6 种失败形态（含回调给 `null`、给空对象，真实环境不保证字段齐全）**每一种都必须留下一句
非空提示**，即把「静默」本身当作被测对象。另有一条源码级断言：两个页面都不许再出现
`wx.setClipboardData(` ——「同一份逻辑写两遍」正是这个 bug 同时存在于两处的原因。

**反向验证过**：把首页改回手写单调用，立刻 3 项红（失败无提示全红、无 url 也会调接口、
复用断言红）—— 证明这些断言是有效守位，不是装饰。

**生效方式**（与 KI-005 那条要分开看）：只影响小程序包，**不需要重建镜像或动服务器**——
全库 `clipboard` 命中都在 `miniprogram/` 下，网页端没有复制功能。重新上传小程序版本即生效。

**本次没做的一件事**：用户若坚决不授权，这个功能对他仍永远不可用（现在至少会说清原因）。
真正的降级是「把 URL 显示出来让用户长按选中复制」，需要改 `wxml` 增加可见文本 ——
超出本次修复范围，留作后续。

### KI-007 敏感信息只扫了「当前树」，漏掉「历史」（两处已在公开历史里）

**状态**：防线已补（2026-09-23）；**已公开的残留不可撤回，登记为已接受**。

**现象**：仓库是 PUBLIC。上一轮脱敏（`21885f8`）把真实域名、服务器 IP、实例 ID、账号名等
100 处替换为占位符，事后核验「已提交树扫 9 类真实标识 **0 命中**」—— 结论本身正确，
但**作用域不够**：脱敏是靠「再提交一次」做到的，而提交是只增不减的，**早先那些提交照旧留在
公开历史里**。按「树」的判据去扫，永远扫不到它们。

按历史重扫后查出两处，都在 `origin/main` 的祖先上（即已经推送出去）：

| 位置 | 内容 | 范围 | 是否仍在 HEAD |
|---|---|---|---|
| `docs/data-source.md` §5 的表格行 | 本机工作目录 `/Users/<用户名>/…` | 7 个 blob 版本 / 14 个提交 | 否（该行已**整行删除**） |
| `docs/acceptance.md` 开头与 A10 行 | 验收时的构建锚点地址 | 2 个 blob 版本 | 是（`<user>.github.io/<repo>` 形态） |

**根因**：**判据的作用域错了**。`test-secrets.mjs` 扫的是工作区 + 暂存区（「这一刻要提交的
内容」），对「防止现在提交进去」够用，但它天然回答不了「以前提交过什么」。

**为什么残留不可撤回**（三个硬约束，缺一个都会让人误以为能「清干净」）：
1. `git push` 只增不减 —— 已推送的提交仍在远端，删文件、再提交一次都改不了它；
2. 即便用 `git filter-repo` 重写历史再强推，**远端旧提交仍可按 SHA 直接访问**一段时间，
   要彻底清除得联系平台 Support；
3. 别人已有的 fork / 本地克隆里那份，你无法回收。

所以「改写历史」的收益是**降低可见性**、不是**抹除**。对本仓库这两处（一个是 macOS 用户名；
一个是可由公开仓库地址直接推出的 Pages 地址）不值得为此重写 66 个提交并打断所有 clone。

**处置**：
- 新增 `scripts/check-history-secrets.mjs`：扫**所有 ref 可达对象**，判据全部是**结构性**的 ——
  本机绝对路径、私钥/证书正文、appid 形态、openid 键值对、部署地址是否为保留域。
  **不写任何真实值**，否则防线自己成为泄露源。
- 已接受的残留**登记在脚本的 `ACCEPTED` 里**（路径 + blob 数基线 + 理由），断言变成
  「**只拦新增**」：命中必须落在登记路径上、且版本数不得超基线。清单与理由每次运行都会
  打印 —— 登记不是「忽略」。
- 顺带回收本地 `.git` 的不可达对象：其中 `89c3ca3e` 是带真实域名的 `config.js` 旧版本。
  这类对象 GitHub 上没有（`push` 只传引用可达的对象），但**拿到项目目录的人能挖出来**。
  已执行 `git reflog expire --expire=now --all && git gc --prune=now`（`.git` 1.8M → 928K，
  不可达对象归零）。
- 挂在 `npm run check`，**不进 `npm test`**：CI 是 `fetch-depth: 1` 的浅克隆，扫历史会
  「全绿但什么都没查」（静默空转）。脚本自己识别浅克隆并**显式** `⊘ 跳过`。

**为什么没有「公网 IP」这条规则**：试过，11 个文件全命中且**没有一处是泄漏** ——
`Chrome/120.0.0.0`、`Chrome/153.0.0.0`（UA 里的版本号与 IP 完全同形）、文档里记录的
「DNS 被解析到的实测地址」、apt 报错里的 IP、注释里的示例 `1.2.3.4`。没有通用判据能把
真实地址挑出来，误报率高到会让人忽略整条防线，所以宁可不要。同理，域名只从
`apiBase` / `SITE_URL` / `INGEST_URL` 这几个**键**入手，不扫全部 URL。
（另有个坑：粗筛正则 `o[0-9A-Za-z_-]{27}` 会把 `package-lock.json` 里
`integrity: sha512-…` 的 base64 片段报成 openid —— openid 必须按**键值对**匹配。）

**回归验证**：在临时分支造 4 类违规（本机路径写进新文件、假 appid、非保留域 `apiBase`、
非哨兵 openid）+ 1 次「基线变多」，**5 条断言全部报红**，且失败文案只给「路径:行号」、
不回显命中值；删分支 + 回收后复绿。

**教训（跨项目）**：**「树干净」与「历史干净」是两件事**。凡是「脱敏 / 删文件 / 忽略规则」
类修复，验收时必须**分开报这两个范围** —— 只讲「扫了 0 命中」而不说扫的是哪一层，
等于把漏判包装成已核验。

### KI-009 上游没收录时，截断的正文无从补全（补全只挂在「上游收录」这一条上）

**状态**：已修复（2026-09-29）。修法在 `src/lib/browser.mjs`（详情页取全文）与
`src/lib/collect.mjs`（`text_full` 挡板），回归用例见 `scripts/test-fulltext.mjs`（39 项）。

**发现方式**：老大报「那次重置已经到账了，页面却还没有更新」。查下来是两个条件叠加：
本地那条长推文的正文只有前半段（截断），而上游 `codex-resets.com` **也还没收录**它 ——
于是 KI-002 修好的那条回填通道没有原料可用，正文永远停在半句上。

**与 KI-002 的关系**：同一条硬边界（X 在时间线只渲染前 ~280 字符）的两个缺口。
KI-002 修的是「上游收录之后能回填」；这一条是「上游没收录的那段时间，本地就是瞎的」。
只修前者，等于把补全能力**外包给一个不在我们控制内的东西**。

**根因**：采集取的是 `innerText`，而页面就不给后半段。要拿全文只有一个地方 ——
**推文详情页**（"Show more" 指向的目标）。而详情页此前只在回复雷达里被用过（抓别人的
回复），从没用来取正文。

**影响**：额度语义经常落在长公告的最后一句。实测 09-12 那条重置公告的库内版本断在
「preventing the model from checking its work.」，全文末尾是
「**And of course, a reset is also landing by midnight today.**」——
「今天午夜前还有一次重置」这半句一个字都没采到。09-29 那条 Pro $200 变更更极端：
库内 277 字符，全文 1917 字符。

**修法**：

1. 采集时（同一个 Chrome 会话）对**疑似被截断**的推文逐条开详情页取全文。判据两条取或：
   页面上还挂着「展开」入口（DOM 硬判据），或正文长度 ≥ 240 字符（实测截断点在 275–278）。
2. 取到的正文**先并进来再 classify** —— `kind` 是从正文里读出来的，用半句分类、用全文入库
   会留下「库里写着 banked reset、kind 却是 other」自相矛盾的记录。
3. 库里那条补全过的推文标 `text_full: true`，并加一道挡板：**全量回补重采到更短的半句时
   不覆盖它**（默认每 72 小时回补一次，没有这道挡板就是把全文每三天打回原形）。
4. 历史遗留（修好之前就入库的推文）走手工通道 `scripts/backfill-fulltext.mjs`（幂等）。

**实测结果**：库里 4 条 275–278 字符的推文 → 详情页给出 426 / 430 / 1087 / 1917 字符。

**被否掉的选项**

| 选项 | 否掉的理由 |
|---|---|
| 继续只靠上游回填 | 上游收不收录不由我们决定。09-29 这次就是上游也滞后 |
| 用第三方只读接口（fxtwitter 之类）取全文 | 引入一个自己不可控的外部依赖，且它是**另一条**出故障的路；本地已有登录态可用 |
| 从详情页 HTML 的 RSC payload 里抠 `full_text` | 实现过、实测证伪：详情页是纯 CSR，`outerHTML` 里 `client:` / `full_text` **一个都不出现**。详见 D-029 |
| 把详情页补全挂进自动链路（每轮对全库长推文扫一遍） | 必然为「本来就完整、只是恰好超过门槛」的推文白开详情页 —— 每轮固定无效请求 |

**同类风险提示**：**「入库时拿到的就是全部」是个需要单独验证的假设**。任何从页面
`innerText` 取文本的采集器都要先问一句：这个容器会不会只渲染一部分？截断**不报错**，
长度看起来也很正常，只有跟权威来源逐字节对齐才看得见。

### KI-010 已兑现的预告被整条撤走时，把「重置确实发生过」也一起带走了

**状态**：已修复（2026-09-29）。修法在 `src/lib/signals.mjs`（`hasOccurredPart` +
`detectSignals` 的降级分支），回归用例见 `scripts/test-signals.mjs` 第 9 组（13 项）。

**发现方式**：KI-009 的补全上线后，重算信号时发现 09-12 那条重置公告从「已发生」列表里
**消失了** —— 补全正文反而让页面少了一条真实的记录。

**根因**：一条推文可以同时说两件事 —— 前半段「A reset and a quick update…」（已发生），
末句「And of course, a reset is also landing by midnight today.」（预告）。
`analyzeTweet` 里 explicit 优先于 occurred，于是它被升级成 explicit；接着
「已兑现的预告不再展示」（那段规则本身是对的，见 KI-004）把它**整条**过滤掉，
连它承载的「重置发生过」也一起没了。

**为什么以前没暴露**：库里那条只有前半段 —— 看不到末句，它就老老实实是 occurred。
补全正文把这个盲区照了出来。

**修法**：被撤走的 explicit 若正文里**有一整句**构成「已发生」的陈述，就降级成 occurred
（清空 `window`、补 `occurredAt`、留痕 `downgradedFrom`），而不是整条丢弃。

**判据踩过的坑（记下来）**：第一版用 `hasOccurredReset(text)` 逐句判，结果**误降级**了
一条纯预告：「We are almost Tuesday and I promised a reset for Tuesday.」——
它一个未来语气词都没有（`RE_FUTURE` 表里没有 "Tuesday"），名词化弱证据「a reset」于是直接成立；
而整条判的时候，是**别处**的 `soon` 把它压住的。改用「逐句跑**完整**判定」
（`hasOccurredPart`，即逐句调 `analyzeTweet`）才正确 —— 它会走到「句中有具体未来时间 →
不是已发生」那一关。时态是**句子级**的属性，但判据不能只取时态那一段。

**安全性验证**：全库 124 条，改动前后**只有那一条**换档；
用补全前的数据跑新旧两版，归属差异 **0 条**（等价性）。
反例验证：换回整条判据 → 2 项报红；整段删掉降级 → 7 项报红（含既有的
「四类计数之和 = 扫描条数」不变式，说明旧代码在新数据下会**静默丢条目**）。

**教训**：修一个「数据变全了」的 bug 时，要顺手重算**所有下游派生结果**并逐条比对 ——
一条更完整的输入，可能让某个原本靠「信息不足」侥幸成立的判断失效。
这次是 `signal.json`，下次可能是别处。

### KI-011 带窗口的「线索」不受过期判据约束，窗口过了还占着页首

**状态**：已修复（2026-09-30）。修法在 `src/lib/signals.mjs`（`staleWindowReason`
取代只认 explicit 的 `isExpiredForecast`），回归用例见 `scripts/test-signals.mjs` 第 10 组（26 项）。

**发现方式**：用户报「重置已经到账了，你现在还是在预告状态，这种 bug 问题太大了」。

**根因**：`analyzeTweet` 里 `intent >= 3 ? 'explicit' : 'hint'` —— 额度意图只有 2 分的推文
**带着时间窗口**落进 `hint` 档。而 KI-004 加的过期判据只挂在 explicit 上：

```js
if (a.level !== 'explicit' || !isExpiredForecast(a)) return a;   // 修复前
```

渲染层两个端（`src/lib/render.mjs`、`miniprogram/utils/view.js`）挑线索都是
`.find((s) => s.window)` —— 于是**只要有一条带窗口的线索**，它就会占着页首，
不管那个窗口是不是已经过去、里面是不是已经重置过。

**实测症状**：09-29 那条 DevDay 发布会推文（时间词是「today」，窗口 = 当地 09-29 全天，
北京 09-29 15:00 → 09-30 14:59）。09-30 晚上页面页首仍是：

> 线索 · 有一条与额度相关的时间线索 · 窗口到北京 2026.09.30（周三）14:59 为止

而那个窗口 6 小时前就结束了，窗口里还真的落地了一次重置（北京 09-30 03:00）。
下方倒计时与「最近记录」都是对的，只有页首在说「还在等」。

**修法**：把过期判据从「只认 explicit」提升为「**所有带 window 的信号**」，两种档位处置不同：

| 档位 | 语义 | 过期后 |
|---|---|---|
| `explicit` | 承诺 | 有了结的处置：正文里另有「已发生」整句 → 降级成 occurred（KI-010）；否则整条撤走 |
| `hint` | 只是「他说过这一天」 | **只撤窗口，推文留档**（撤 `window`、写 `windowExpired`、理由进 `reasons`） |

撤回判据仍是那两条（与 KI-004 同源）：① 窗口已过去（`to < now`）；② 窗口开始之后
已发生过重置（`lastResetAt >= from`）。

**为什么不复用 `candidateWindow` 装撤下来的窗口**：那个字段的语义是「还没被采用的候选」，
`buildHypothesis` 会把它当**可用证据**捞起来 —— 装一个已失效的窗口进去，等于让聚合逻辑
把过期时间当证据用。所以另开 `windowExpired`（含 `from` / `to` / `why` / `checkedAt`）。

**安全性验证**（反例注入，实测）：

| 注入 | 结果 |
|---|---|
| 把判据改回「只过滤 explicit」 | **13 项报红**（含渲染层断言与真实语料断言） |
| 还原 | 151 项全绿 |

**教训一：同一个判据要问「还有谁满足它的前提」。** KI-004 修 explicit 时，判据的前提是
「这条推文带着未来的窗口」—— 而 `hint` 档同样满足。当时只按**档位**过滤，漏掉了按**字段**过滤。

**教训二：症状在渲染层，断言就必须落在渲染层。** 这次的 bug 是「数据里有 window，
渲染层无条件挑它」—— 只断言数据层字段的话，把 `window` 撤回而渲染层改用别的字段，
测试照样绿。所以第 10 组直接断言 `renderSignal()` 的输出里有没有 `sig-win`。

**教训三：恒绿的对照断言要一起写。** 「过期就撤」极易做过头成「一律不展示」，
而这种错误在真实数据上**看不出来**（当前恰好没有未来线索，页面一样是空的）。
所以每组都配了反向用例：窗口还在未来 + 期间无重置 → 必须保留。

### KI-012 完成句式只认单数：`Reset all propagated` 判对，`Resets …` 被静默丢掉

**状态**：已修复（2026-09-30）。修法在 `src/lib/signals.mjs` 的两处词表；回归用例见
`scripts/test-signals.mjs` 第 11 组。

**发现方式**：修 KI-011 时顺手全库扫「形状像已完成」的推文 —— 不是用户报的，是扫出来的。

**根因**：两个正则叠加，缺一不可。

```js
// ① RE_PAST 不认复数：主语是「Reset(s)」这个事件名词，单复数全看他当天怎么写
/\breset\s+(?:all\s+)?(?:propagated|…)\b/          // 修复前
// ② RE_FUTURE_PERFECT 的尾巴不要求任何词 —— 任何 `will be …` 都能否决整条
/\b(?:will|shall|going\s+to|gonna)\s+(?:have|be)\b/   // 修复前
```

**受害推文**：`2103911959544610829`「**Resets** all propagated. That **will be** all.
Have a fantastic weekend.」（09-27 02:17 北京）—— ①② 同时命中，两处都拦。
对照组 `2098685367058612394`「**Reset** all propagated. Sweet dreams.」（09-12）一直判对，
**只差一个 s**。

**后果**：它既不是 `occurred`、又会作为「过期预告」被撤走 → 两条链路都不认它。页面被
上游历史层兜住（「最近记录」标的仍是「普通重置」），只有信号层的「已发生」列表少一条 ——
典型的**静默丢数据**，不改代码永远看不出来。

**修法**：`RE_PAST` 的 `reset` 改 `resets?`；`RE_FUTURE_PERFECT` 要求 `have` / `be`
之后必须落到 reset 上（可隔一个副词）：

```js
const RE_PAST = /\bresets?\s+(?:all\s+)?(?:propagated|…)\b|…|\bresets?\s+(?:has|have)\b/i;
const RE_FUTURE_PERFECT =
  /\b(?:will|shall|going\s+to|gonna)\s+(?:have|be)\s+(?:(?:been|now|also|then|fully|all|already)\s+)*reset(?:s|ting)?\b/i;
```

**影响面**（旧版 vs 新版逐条 diff 全库 171 条）：

| 项 | 旧 | 新 |
|---|---|---|
| level 发生变化的推文 | — | **1 条**（就是它：`explicit` → `occurred`） |
| `counts.occurred` | 3 | 4 |
| 其余各档 | — | 不变 |

**教训一：判据要按「形状」写，不按他某天恰好用的那个写法。** 单数/复数不会报错，
只会少一条数据。凡是句子主语可能是「事件名词」的词表，都该写成 `s?`。

**教训二：词表里「不要求任何词」是一个隐式的万能匹配。** `RE_FUTURE_PERFECT` 里
`(?:have|be)` 后面不接内容，等于给所有 `will be …` 的句子（含「That will be all」
这类收尾寒暄）发了一张否决票。收紧它之所以安全，是因为「未来语气」那层有 `RE_FUTURE`
兜底 —— 先确认兜底存在，再收紧。

**教训三：修完要逐条 diff 全库，不是只验那一条。** 只跑定点用例的话，「改动有没有
波及别处」这件事没有任何证据。做法是把改动前的模块 copy 一份到同目录（保住相对 import），
让新旧两份同时 import 进来对跑。

### KI-013 展示类脚本漏传 `lastResetAt`、漏给 `LOGO_URI`

**状态**：已修复（2026-09-30）。回归用例见 `scripts/test-signals.mjs` 第 11 组
（「每个调用点都传了 lastResetAt」）。

**共同形状**：**生产路径给了，旁边的展示类脚本没给** —— 结果是「本地产物显示的状态」
与「真实系统里的状态」不一致，而脚本本身不报错。

| # | 位置 | 漏了什么 | 症状 |
|---|---|---|---|
| 1 | `scripts/preview-miniprogram.mjs` | `lastResetAt` | 已兑现的预告被显示成**仍然有效**的预告 |
| 2 | `scripts/make-prototype.mjs` | `lastResetAt` | 同上（原型页是拿去评审的，等于给评审看一个真实系统不会出现的状态） |
| 3 | `scripts/make-prototype.mjs` | `LOGO_URI` | 模板占位符留着 → `injectTokens` 抛错 → **一个页面都产不出** |

**证据（第 1 条，同一份数据、同一时刻）**：

```
不传 lastResetAt → level=explicit, forecasts=1  (窗口 2026-09-28T07:00Z → 10-05T06:59Z)
传   lastResetAt → level=occurred, forecasts=0
```

修前 `npm run preview:mp` 的产物正显示「明确信号 · 本周 · 9.28 起」，
同一时刻快照里 `explicit: 0 / forecasts: 0`。

**第 3 条是既有缺陷**，与本次信号修复无关 —— 用 HEAD 版本跑同样报
`存在未替换的占位符：<!--__LOGO_URI__-->`。`renderAll` 不产出这个键，它由
`renderPage` 事后补上（品牌标内联成 data URI）；直接调 `renderAll` 的调用方必须自己补。

**教训：这类「参数漏传」缺陷，行为断言守不住 —— 要用文本扫描守调用点。**
行为断言只能守住你已经知道要测的那条路径，**新写的调用点照样恒绿**。
所以第 11 组直接扫 `src/lib` / `scripts` / `server` 下所有 `detectSignals(` 调用点，
要求每个都带 `lastResetAt`（测试文件按 `test-` 前缀豁免）。

这条扫描**当场就抓出两处我没预料到的漏传**（`make-prototype.mjs`、以及一处传空数组的
测试）。配套还要有一条「扫描确实扫到了 ≥3 处调用点」的自证断言 —— 否则扫描本身写错时
（比如正则不匹配），那条守卫会恒真。

**副作用**：`scripts/test-collect-warning.mjs` 传的是空数组（无信号可判），
按 `test-` 前缀整体豁免，不再逐个判断。

### KI-014 `RE_FUTURE` 表里没有未达动词，名词化弱证据会把预告读成事实

**状态**：已收敛（2026-10-08，见 D-040）。闸门只加在**两处句级判据**上
（`resetSentencesOccurred` / `hasOccurredPart`）；`hasOccurredReset` 的整条路径
**仍留着缺口**。实测全库 **0 / 305** 命中，所以目前不产生任何影响 —— 登记它是因为
它是一处「靠巧合成立」的判据。

**根因**：`src/lib/signals.mjs` 里 `hasOccurredReset` 的**名词化**是一条弱证据
（`RE_ANNOUNCE` 的「A/the reset」），它唯一的闸门是「句中不能有未来语气」（`RE_FUTURE`）。
而 `RE_FUTURE` 表里有 will / soon / next / tomorrow，**没有 coming / landing / arriving**。
于是：

> 「**A reset is coming** for everyone. See you tomorrow.」

逐句判时，「A reset is coming for everyone.」这句自己一个 `RE_FUTURE` 词都没命中
→ 弱证据成立 → 被读成「刚刚重置过」。

`RE_ANNOUNCE` 的注释里其实早写过同一件事：「早先这一版之所以没暴露，是因为真实那句话里
恰好有 "See you soon"，命中了 `RE_FUTURE` 才侥幸走了预告分支 —— **靠巧合成立，不是判据
成立**」。这条 KI 就是那句话的兑现：把巧合去掉，它立刻复现。

**影响范围**（收敛前）：

| 路径 | 后果 |
|---|---|
| `analyzeTweet` 的句级兜底（D-040 新增） | 一条真预告被判成 occurred，页面上「最近记录」多一条假的「重置发生过」 |
| `hasOccurredPart`（KI-010 的过期降级通道） | 同一条推文在窗口过期后被降级成「事实」—— 同一个病，晚 29 小时发作 |
| `hasOccurredReset` 整条路径（**仍留着**） | `classifyEvent` 会把这类推文的 `kind` 标成 `'reset'`，而信号侧判 explicit —— 同一份数据两个结论 |

**修法**：新增 `RE_RESET_NOT_YET`，只认「be + 未达义动词」这一个结构
（`com(?:e|ing)` / `land(?:ing)?` / `arriv(?:e|ing)` / `approaching` / `inbound` /
`due` / `expected` / `scheduled` / `on the way`），加在两处句级判据的拆句处。

词表**必须**按语义类划，不能按语法结构划：`We are loading a banked reset…` 里的 `loading`
与 `coming` 在语法上都是 be + V-ing，能分开它们的只有动词的语义（load 是动作、come 是趋向）。

**为什么没直接补 `RE_FUTURE`**：它是通用表，被 `hasOccurredReset`（→ `classifyEvent`
→ `resets.json` 的 `type`）与「含未来语气」的 reasons 文案共用。补它会从信号层扩到
数据层，超出 D-040 要修的范围。

**回归用例**：`scripts/test-signals.mjs` 的【14】反例② 与反例②b —— 前者守「当场不误判」，
后者守「过期后不误降级」。反例验证：去掉这道闸门 → 4 项报红。
