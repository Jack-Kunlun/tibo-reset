## D-053 OG 分享图改由「随数据推送」送达；并更正一处会常态化误报的防线口径

**背景**：2026-10-09 让「发布一下」时顺手复核线上，把两张 OG 分享图（主入口 vs Pages 备份）
捞下来**实际读了图上的数字**：

| 图上印的（主入口） | 当前真实值 |
|---|---|
| 距上次重置 **2 天 16 小时** | 1 天 2 小时 |
| 历史记录 **57 次** | 60 次 |
| 最近一次采集 **2026.10.02 18:10** | 2026.10.09 14:31 |

**主入口那张停在 10-02、滞后 7 天、三个数字全错**（备份入口那张是当天 CI 重建的，正确）。
容器侧实锤、不是缓存：容器内 `/app/dist/og-image.png` 的 mtime 是 `2026-10-02 11:06:50 UTC`，
sha 与线上**实际发出**的那张完全一致；同目录的兜底页 `dist/index.html` 也是同一时刻。

**根因**：D-025 / D-026 把「卡片停在最后一次构建的数值」记为**已知且接受的代价**，
前提是「部署 = 一次构建」。而线上真正走得通的那条部署路径（**diff + `docker commit`**，
因为 SSH 不通、服务器不出网）**从不重新执行构建** —— 前提被悄悄弄没了，
代价于是从「差一次构建」变成「无限期」。

**决策**：

| # | 决定 | 直接后果 |
|---|---|---|
| 1 | 卡片改走**已有的数据通道**：本机 `build.mjs` 产出 PNG + `og-meta.json`，由 `push-ingest.mjs` 随 `data/` 一起 POST | 载荷多一个**可选**字段 `og`；不需要新通道、不需要 SSH、完全不动 CI |
| 2 | 落点在**数据卷**（`DATA_DIR/og/`） | 容器里除挂载卷之外都是镜像层，换容器即丢；⚠ `data/og/` 必须进 `.gitignore`（否则每小时 `git add data` 会提交一个 ~100KB 二进制） |
| 3 | 服务端**优先发推送那份**，回落镜像里的 `dist/`；`getOgMeta()` **不再「启动时解析一次就缓存」** | 回落是「新容器刚起来、还没收到第一轮推送」的**兼容窗口**，不是稳态。缓存住就等于把旧 bug 原样搬进新实现 |
| 4 | 卡片的形状校验与数据**同一条判据**：坏 `og` 整份拒收（422） | 与「坏数据绝不能落盘」同一原则。「收下但静默丢弃」会让卡片停在旧图而数据已更新 —— 正是本项目最怕的静默不一致 |
| 5 | `/api/health` 报 `og.source` / `builtAt` / `bytes` | 卡片是运行期产物，它有多新**在页面上看不出来**（页面文字跟数据走），必须有个地方能问 |
| 6 | 顺带更正 `check-history-secrets.mjs` 的扫描范围（见文末） | 它原来把**本地工具的工作区快照 ref** 也算成「会被公开读到」，常态化报红 |

**为什么是这个方案（四条路的账）**：

| 路 | 结论 |
|---|---|
| 把新图 base64 分块送进容器 | 通道可用（第一轮验证过），但 106 KB → 约 90 次调用，**重**；而且修完下一轮就又旧了 |
| `og:image` 指向 Pages 那份 | **不是修复**：`collect.yml` 的 `paths` 里没有 `data/**`（D-025 移除的），CI **只在推代码时跑** —— 代码一周不动，指向 Pages 就一样旧一周 |
| 让容器自己渲染 | 要引 `@resvg/resvg-js` 进运行镜像，撞 D-002「运行镜像零依赖」（D-026 已否） |
| **随数据推送（选定）** | 零新通道、零运行时依赖、不碰 CI；且图与数据来自**同一次构建** —— 卡片数字与页面数字不可能对不上 |

**额外收益**：主入口的 `og:description` 此前一直是**兜底文案**（无数字）。原因是描述和
`ogNumbers()` 一起住在 `scripts/og-image.mjs` 里，而那个文件顶层 import 了 resvg ——
后端一调它就把原生二进制拖进运行镜像（撞 D-002）。现在描述随 `og-meta.json` 送来，
**这个问题一并消失**，且图与文字必然同源 —— 正是 `og-image.mjs` 自己写的
「图与文字不能各算各的」。

**代价（要认）**：
- 卡片的新鲜度从此绑在**本机自动化**上。本机停跑时卡片与数据一起停；页面会提示「数据未更新」，
  但**卡片没有对应提示** —— 只能靠 `/api/health` 的 `og.source` 问。
- `POST /api/ingest` 载荷变大（多约 140 KB base64），仍在 8 MB 上限内。
- **平台侧的卡片缓存不受我们控制**：URL 不变时微信可能继续用缓存过的卡片。这一层在页面上
  看不见、也解决不了，如实记在这里而不是假装已解决。

**反向验证**（每条都实跑过；还原后与干净基线逐字节一致、`TEMP-COUNTERFACTUAL` 残留 0）：

| 断言 | 反例做法 | 观察到的失败 |
|---|---|---|
| test-og「描述取推送那份」 | 让 `resolveOgMeta` 不认推送件 | **恰好 1 红**，失败详情正是「描述丢了」 |
| test-og / test-ingest 的尺寸判据 | 摘掉 `decodeOgPng` 的 IHDR 检查 | test-og 1 红；test-ingest **2 红** —— 第二红是「坏了 9 次之后卡片一字未动」，即**坏图真的覆盖了卡片**，说明那条断言确实在盯写入路径 |
| 端到端「描述跟着推送变」 | 把 `getOgMeta()` 改回启动时缓存 | 页面仍显示旧描述（`跟着推送那份走 = false`）—— 证明「不缓存」是承重的 |
| 端到端「发出的是数据卷那份」 | 让 `serveOgImage` 总是发 `dist/` | 探针 `true → false`。⚠ 两份**刻意做成不同字节**：早先那版探针两份相同，「一致」什么也证明不了 |
| `build.mjs` 清掉过期描述 | 强制 `og = null`（模拟缺字体） | `dist/og-meta.json` 被删除，日志里没有出图那行 |
| test-secrets「`data/og/` 被忽略」 | 摘掉那条 ignore 规则 | **恰好 1 红** |
| 历史敏感信息防线 | 扫描范围改回 `--all` | 原来那条红原样回来（见下） |

**顺带更正一处防线口径**（`scripts/check-history-secrets.mjs`）：它原来用 `rev-list --all`，
于是把**本地工具的检查点 ref**（`refs/codex/turn-diffs/checkpoints/*`，指向**工作区快照**、
`git push` 从不发送）也算成「会被公开读到的部分」。实测 2026-10-09 它因此**常态化报红**，
而且那条红**无法靠改代码消除**（工作区的 `miniprogram/config.js` 长期带真实域名，那是设计）。
改为只扫 heads / remotes / tags，那些对象连同其余不可达对象一起由【3】段报（仅本地，只提示）
—— **没有任何内容不再被扫描**，只是不再判失败。用项目自己的话：常态化报红等于没有防线。

**要记住的**：这一轮两件事是**同一个毛病** —— 「约定」与实际路径对不上，而且没人对账。
D-025/D-026 的「已接受的代价」默认了「部署 = 一次构建」，而落地走的是**不重建**的那条路；
`rev-list --all` 默认了「所有 ref 都会被推送」，而实际不会。
**写下「已知且接受」时，必须同时写下它成立的前提，以及谁在守那个前提。**

## D-052 「依据边界披露」必须有**可见**落点；判据里的正则会静默失效

**背景**：2026-10-09 清三处挂账时发现它们**同源** —— 「判据 / 覆盖率与实现对不上，而且没人对账」。

1. **A1 报「缺一句话依据摘要」**：判据写死 `/class="pc-brief"/`，而实得是
   `class="pc-brief am-sr-only"`。多个类名，正则就落空。
2. **更要紧的是内容，不是判据**：D-050 把整句藏进 `am-sr-only` 之后，可见的依据区换成了
   **另一组数字**（覆盖率 / 平均间隔），而「本轮扫描 N 条推文、M 条时间线索均不足以构成预告」
   这条披露**没有承接者**，视觉上直接消失。`render.mjs` 自己的注释把它列为要求
   ——「否则读者无法区分『系统没看见』和『看见了但不够格』」。
3. **A8 的留档自 D-050 起一直写「页面时间为 ?」**：取值写死 `/id="gen">/`，而模板是
   `<span id="gen" class="am-mono">` —— 同一个病。更糟的是三份字节相互比较在「三边都取不到」
   时**照样成立**，所以取值失败**不会自己变红**，只会把 `?` 写进验收记录。
4. **另一处不是判据问题，是覆盖不全**：小程序 `_programMeasure` 守卫的后半条
   `measure !== this._programMeasure` 此前**没有任何用例** —— 实测「只摘掉一半」时 258 项全绿，
   摘掉整条才变红。

**决策**：

| # | 处置 |
|---|---|
| 1 | A1 判据放宽 —— 允许 `pc-brief` 之后再接类名，不再要求引号紧跟 |
| 2 | 披露句抽成 `scanClause(o)`，**一处实现、两处消费**：主卡的读屏句（`pc-brief`）保留，另在依据摘要面板加**可见**的 `.am-basis-note`（公告档换成「依据来自公告本身，与这些统计无关」）。A1 新增一条判据盯这个元素：要求 `class="am-basis-note">` **紧跟文字**，所以谁把它改回 `am-sr-only`、或把文字清空，都会红 |
| 3 | A8 取值改为容忍标签上的其它属性，并**把取值成功纳入判定**（`shownOk`）—— 否则页脚时间整块消失也能一路全绿 |
| 4 | `test-miniprogram.mjs` 补一条：`onToggleProgram()` → `page.onUnload()` → 手动触发迟到回调 → 断言 `programHeight` 仍为 0。`onUnload` 不清 `programOpen`，所以这条**只可能**由 measure 守卫挡住 |

**为什么披露要可见、而不是只留读屏**：读屏句是给无障碍用户的，不是替代品。一条「我们扫了
321 条、一条都没够格」的披露，如果视力可见的读者读不到，那么页面上剩下的就只有一组好看的
统计数字 —— 读者会更倾向于相信模型，而不是知道它其实什么都没看见。它与三张依据卡回答的是
**不同问题**：卡回答「算得准不准」，这条回答「有没有资格算」。

**代价（要认）**：依据摘要面板多一行 11px 小字。刻意**不加边框** —— 上面 `.am-basis-row`
自带 1px 上边框，再加一条就会与它凑成「相邻两个有边框的块」，被 A7b 判成贴线。A8 多一个
判定条件：`#gen` 的模板结构若再变，A8 会**红**，而不是静默把 `?` 写进记录。

**反向验证**（每条都实跑过；还原后与干净基线逐字节一致、无残留标记）：

| 断言 | 反例做法 | 观察到的失败 |
|---|---|---|
| A1「依据边界披露（可见）」 | 把落点改回 `am-sr-only` | A1 红，**唯一一条** ✗ |
| test-outlook 两条（可见披露） | 把 note 清空 | **恰好 2 红**，无连带 |
| test-miniprogram 新断言 | 只摘 `measure` 一半 | **恰好 1 红**（值 512），旧三条全绿 |
| 同上 + 旧断言 | 整条守卫失效 | 2 红（旧 + 新）—— 两半互补，各自只认自己那半 |
| A8 取值 | 把 `#gen` 正则改回不容忍属性 | A8 红，唯一一条；**同一句里仍写着「字节完全一致」**，正好证明取值失败原本是隐形的 |

**要记住的**：正则写死「第一处」属性 / 类名，会在模板多一个属性时**静默失效**；而只要那个值
**不参与判定**，失效就永远不会被看见。凡是用来**报数**的正则，要么容忍其它属性，要么把
取值本身纳入判定 —— 否则它只是把错误写进留档，还写得很像正常。

## D-051 小程序更新下载完成后提示，用户确认才重启

**背景**：2026-10-09 用户要求补充小程序版本更新与重新进入提示。

**决策**：App 启动注册一次微信 `UpdateManager`；由微信检查、下载，收到
`onUpdateReady` 才提示「立即重启 / 稍后」。确认后调用 `applyUpdate`，不自动强制重启。
后台完成的更新在返回前台后提示，同次前台最多提醒一次；稍后更新可在下一次前台继续提醒。
朋友圈单页不弹重启提示。失败保留当前使用状态并给出检查网络、稍后重新打开的说明；
不增加轮询、版本号接口、清缓存或删除小程序的流程。

**验收边界**：本机宿主桩与开发者工具模拟分别验证；正式跨版本下载与切换需在后续发布后真机验证。
当前不带此逻辑的已安装旧包，仍需先按微信原有机制获取带本功能的版本。

## D-050 三端采用带动效的极光观测台

**背景**：2026-10-09 用户选定极光观测台示意并要求增加动画，随后授权按最终示意修改
PC、手机网页和微信小程序，要求一比一还原。

**决策**：使用浅紫、薄荷绿、冰蓝的缓慢极光，中央渐变日期、椭圆轨道与光点，配合
日期入场翻转和数字卷轴。网页增加指针光晕与轻微倾斜，小程序采用触摸光波。
网页提供暂停并保存偏好、响应系统减少动态效果；按用户追加要求，小程序不展示暂停按钮，
默认开启动效并随页面隐藏自动暂停。网页暂停不冻结当前时间。

小程序首页采用自定义导航，让极光延伸到状态栏；标题按系统胶囊位置留白，历史页保留
原生返回栏并统一浅紫背景。首页实时观测状态作为标题副行，与品牌图标组成紧凑导航，
不再另起右对齐的状态行；去掉英文副标题与状态胶囊，避免左侧出现整块空白。

首屏保留真实「距上次重置」四组读数，但按新示意压成信息行；视觉重心交给下一次预测。
倒数显示最高两级单位，完整时长仍由真实锚点计算。顺序保持「距上次 → 预测 → 信号 →
每日窗口 → 依据」，每日窗口可展开。桌面采用图表与依据双列，手机改为单列。
小程序窗口展开区改用完整宽度的双时区卡片：北京时间显示真实开始、结束时刻，
当地时间保持日历日范围，来源双时区另列。展开与收起按内容实际高度过渡，配合淡入和
箭头旋转；快速切换时忽略过期测量，不重新撑开已经收起的内容。
近期节奏和三条最新记录在默认页面展示，完整回测、概率、分布与更多记录在展开区保留。
这些视觉尺寸和卡片形态替代 D-045–D-049 中旧版的固定高度及三卡布局，数据口径仍然有效。

示意中的日期与数字不写死：网页继续请求期服务端渲染，小程序继续快照先行再联网。
新增节奏图复用自包含的 `rhythmScene`，经 build 同步到小程序；没有第二套浏览器数据推导。
公告窗口与模型 80% 区间分别标注，双时区、原文入口、数据陈旧与采集异常提示均保留。

**验收边界**：网页实际浏览器和 HTML 小程序预览分开验证；预览不能代替微信真机验收。
本轮范围为本地实现，不包含部署、上传体验版或发布。

## D-049 「每日重置窗口」提到预测下方：仍在信号之后，但排在依据之前

**背景**：老大先要「每日重置窗口也需要往前提一点」，随即指明落点 ——

> 「把他放在预测下方」

改前它在**预测依据之后**（2026-10-08 第二轮定的，见 D-041 正文）。

**决策：两端把它从「预测依据之后」提到「信号区之后、预测依据之前」。**

| | 改前 | 改后 |
|---|---|---|
| 网页 | 已经等了多久 → 结论 → 信号 → **依据** → **每日重置窗口** → 历史规律 → 样本摘要 | 已经等了多久 → 结论 → 信号 → **每日重置窗口** → **依据** → 历史规律 → 样本摘要 |
| 小程序 | `.hero` → `.pred` → `.sig`/`.sig-idle` → **`.bc-grid`** → **`.prog`** → `.hr-grid` | `.hero` → `.pred` → `.sig`/`.sig-idle` → **`.prog`** → **`.bc-grid`** → `.hr-grid` |

**为什么不是「又搬回去」**：它划的是**结论的边界**，不是「结论算得准不准」。
读者读完主卡的「预计 10.13」之后，最先要确认的是**这个日子有多硬**，而「这 28 天里
每天要么发一个改进、要么给一次完整重置 —— 期间任何一天都可能重置」正是那个前提。
「算得准不准」（中位剩余等待 / 样本外回测 / 节奏分段）才是三张依据卡回答的。
两件事分属不同问题，所以它该夹在中间。

**为什么**仍然**在信号之后**：信号区（预告横幅 / 「没有检测到预告」提示条）是**结论的
附属读数** —— D-018 与 D-044 都定过它紧贴主卡，读者的下一问就是「有没有公告」。
把窗口块插进 `.pred` 与 `.sig` 之间，会把「公告贴在结论下面」这个关系切断。

**D-041 那条「窗口后置」的理由没被推翻，是前提没了**：当时它排在信号之后，
实测 375×812 下露出大半，而首屏要留给「下一次什么时候、还有多久」。现在它上面
多压着整块 `.hero`（「已经等了多久」，219px，D-047 的产物），于是重测（预览 +
无头 Chrome，iframe 固定视口，375px 下 1rpx = 0.5px）：

| 视口 | `.prog` 的位置 |
|---|---|
| 320×568 / 360×780 | 整块在首屏之外 |
| **375×812** | 只露出 **15px** —— ≈ 它自己的上边框 + padding 上沿，读不到任何字 |

## D-048 「已经等了多久」的页首数字改成四位卷轴（口径与 `spanOf` 同一个表达式）

**背景**：老大原话 ——「已经等了多久也应该有时间滚动效果」。

D-047 刚把这块提到页首，它就成了**全页最显眼的数字**——但它是一串静态文本
（`fmtSpan(sinceDays)`，如「5 小时 44 分」），全页只有它不会动：主卡那个倒数在滚、
小程序端同一个数字也在滚。最显眼的那个反而冻着，是 D-047 之后留下的自相矛盾。

**决策：网页端页首改成四位卷轴（天/时/分/秒），复用 `.grp` / `.reel` / `.strip`；
渲染层新增 `renderElapsedCounter(m)`。**

| | 改前 | 改后 |
|---|---|---|
| 形态 | 纯文本「5 小时 44 分」 | 四位卷轴「0 天 06 时 01 分 14 秒」 |
| 动效 | 无（每分钟才变一次字） | 秒位每秒滚一格（与主卡倒数同一条缓动曲线） |
| 口径 | `spanOf`（round-first，紧凑输出） | **同一个 `total`**，改按单位拆位 |
| 实现 | `render.mjs` 的 `ELAPSED` token 直接给字符串 | `renderElapsedCounter` + 页首 div 里四个 `.grp` |
| 小程序 | 本来就是卷轴（`reelGroups`） | 不动 |

**关键在口径，不在动效**：卷轴要按单位拆位，最顺手的拆法是现成的 `parts()`——
但它是**先把毫秒 floor 到秒**再拆，`spanOf` 是**先 round 再拆**。差这一秒只在
`23:59:59.6` 这类临界点上显形（每天 0.6 秒的窗口），届时页首写「23 时 59 分 59 秒」、
「历史规律」那道「现在 X」标签写「1 天」—— 手工点不出来，线上撞上了也解释不清。
所以取 `Math.round(days * 86_400)`，**与 `spanOf` 同一个表达式**：两边结构上不可能
不一致，而不是靠「通常撞不上」。

> 这条同时**解掉了 D-034 里「页首不能用卷轴」那个理由**：D-034 否掉的是
> 「让内联那份复用 `parts()`」，不是「用卷轴」。换成 round-first 之后，那个动因消失。

**连带删掉的东西**：内联 `<script>` 里的 `spanFromMs`（唯一调用点没了）。
`test-shared.mjs` 第 7 节随之从**四处实现**收敛为**三处**，并补上一条新的对拍：
「页首卷轴位与 `spanOf` 同口径」——把 `renderElapsedCounter` 产物里的
`translateY(-N em)` 还原成四位数字，与 `spanOf` 内部那个 `total` 逐位比。
`DAYS` 里原先为 `spanFromMs` 准备的 `86399.6 秒`（floor/round 分歧点）现在直接为
这条服务 —— **删实现不能连用例一起删**，那条用例是这一整节里唯一能挡住差一秒的东西。

**代价（要认）**：

1. **页首数字变宽**。四位 + 四个单位最宽是「天两位数」形态（8 位数字）。
   无头 Chrome 实测：320px 视口下栏宽 208px，一位天数 189px、两位数 207px（余 1px）；
   753px 视口 321/642、960px 视口 368/849。字号下限从 30 收到 28 —— 与主卡的
   `.pc-wait .counter` 同档（它也是四位卷轴、也在这条边界上）。
2. **显示精度变了**：从「5 小时 44 分」变成「0 天 05 时 44 分 55 秒」，多了秒位。
   这是要的（不然每分钟才动一次，「滚动效果」等于没有），但首屏确实更吵。
3. `flex-wrap:wrap` 是**刻意留的兜底**：天到三位数（等过 100 天）时 320px 那档会换行。
   换行只是难看，横向溢出会让手机上出现横向滚动条 —— `.counter` 同族一直这么兜。

**机械核对**：`check-consistency.mjs` 新增三条 —— ① 找得到四组（前置，缺组时
`reels[k]` 是 undefined 但页面上「看着还行」）；② 卷轴位还原 == `digest.sinceDays`
（逐位比，报错行写成「h：页面 15 vs 期望 5」）；③ `data-last` 与 `digest.sinceDays`
相差不到 1 秒。原「可见文字含距上次重置时长」保留，但它的来源已换成「历史规律」那道
「现在 X」标签（页首那串字提取不出来）—— 注释里写明了，免得下一个人以为它在验页首。

**反向验证（实跑过）**：
1. `renderElapsedCounter` 的 `Math.round` 改成 `Math.floor` → 「页首卷轴位与 spanOf 同口径」
   红，10 例不一致（含 `60 秒` 那条：实得 `00分 59秒` vs 期望 `1分 00秒`）；
2. 把页首「时」组某一位 +1 → 「h：页面 15 vs 期望 5」；
3. 把「分」组改名为 `x` → 前置那条「找得到四组卷轴位」红（无假绿）。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 保留静态文本，只给它加一层 CSS 逐字动画 | 与「同一个量只该有一种动法」冲突：页面上会出现第二种数字动效，而它长得像卷轴却不是 |
| 沿用 `parts()` 的 floor 拆 | 差一秒，页首与「历史规律」的「现在 X」标签会在临界点各说各话（见上） |
| 只改网页端，小程序端保持纯文本 | 小程序端**本来就是卷轴**，这次是网页端去对齐它 |
| 天数为 0 时隐藏「天」那一组 | 省 0.88em，也确实顺 `spanOf`「保留最高非零单位」的口径；但小程序端 `reelGroups` 恒返四组，隐藏即两端分叉。两端语义一致优先于省这点宽度 |
| 去掉秒位（只留天/时/分） | 那就还是每分钟才动一次，「时间滚动效果」等于没有 —— 否掉的是这个需求本身 |



## D-047 「已经等了多久」提到页首：事实在前、推断在后

**背景**：老大原话 ——「已经等了多久放在最上面去」。

此前它在**页尾**（顶栏之下第四块）。D-041 定的排序规则是「往前看的在上、往回看的在下」，
理由是「结论必须独占首屏」—— 那条规则的前提是**首屏只放一块**。

**决策：两端把这块提到顶栏之下第一块，预测总览（`.pred`）紧随其后。**

| | 改前 | 改后 |
|---|---|---|
| 网页 | 结论 → 信号 → 依据 → 每日重置窗口 → 历史规律 → **已经等了多久** → 样本摘要 | **已经等了多久** → 结论 → 信号 → 依据 → 窗口 → 历史规律 → 样本摘要 |
| 小程序 | `.pred` → `.sig` → 依据 → `.prog` → 历史规律 → **`.hero`** → 样本摘要 | **`.hero`** → `.pred` → 其余不变 |

> ⚠ **2026-10-09 部分更正（见 D-049）**：本表「改后」那一列里**窗口的位置已被取代** ——
> 「每日重置窗口」由「依据之后」提到「信号之后、依据之前」。本表其余内容（`.hero`
> 提到最前、两端顺序一致这两条）仍然有效。

**为什么反过来不算退步**：顺序的判据换成一条更硬的 —— **事实在前、推断在后**。
「已经等了多久」是**已发生的事实**（上次重置到现在的实测差值，不含任何模型推断、
没有概率也没有区间）；预测总览是**推断**。读者先知道「我现在处在什么位置」，
再看「下一次什么时候」才有参照物。D-041 担心的那个毛病（第一眼读到的是规则或射程、
而真正的问题被挤下去）在这里不成立 —— 排在第一的既不是规则也不是射程，
就是那个问题的一半。

**代价（要认）**：预测总览不再独占首屏，首屏变成「事实 + 结论」两块。可接受的理由是
带推断的那块仍是全页视觉重量最大的（薄荷底 + 唯一的状态色前缀），一块不带边框的白卡
排在它前面不会把它压下去。

**两端形态不同，顺序必须相同**：网页端是「大数字 + 右栏对账（上次重置 / 判定 / 落点）」，
小程序端是「大数字 + 进度尺」。版式各自适配，**顺序与语义一致**——
这是「同一件事一份实现」的边界：能共享的判据共享（`outlook.mjs`），排版不强行统一。

**连带改的两处**：
1. 入场动画的先后（小程序 `rise` 的 `animation-delay`）—— `.hero` 改成最小（0.04s）、
   `.pred` 顺延到 0.06s。入场的先后顺序本身就在说「先看这块」，不改就是自相矛盾。
2. 页首那个区块标题的 `margin-top` 沿用 56rpx（区块间距），与顶栏之间读起来不空 —— 实测过，
   没为「第一块」单独开特例。

**机械核对**：断言方向跟着反转，并且**两条一起**钉：
`iHero < iPred`（事实在推断之前）+ `iHero < iBc && iHero < iHr`（确实不再后置到页尾）。
只钉一条的话，「挪一半」（删了旧位置、忘了插新位置，或插到了别处）可能不报。
`.hero` 同时加进「找得到六块」那条前置断言 —— 锚点消失时 `indexOf` 给 `-1`，
而 `-1 < x` 恒真，不兜底就会静默变绿（同 D-046 记的那条教训）。

**反向验证（实跑过）**：
1. 把 `.hero` 改名 → 3 条红（前置 + 两条顺序），无假绿；
2. 把 `.hero` 挪回页尾 → 恰好那两条顺序断言红。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 只在网页端改，小程序端保持原顺序 | 两端顺序不同会让「同一件事」在两边讲成两件事；改的是**顺序**，不是版式 |
| 把它做成吸顶条 / 塞进顶栏 | 顶栏是观测状态（时间、观测中），塞进去两个信息源共用一行，两边都读不清 |
| 压缩它到一行小字 | 它是首屏唯一不含推断的数字，压成小字等于把「事实在前」这条判据做成装饰 |
| 同时把「样本摘要」也提上来 | 没被要求，且它是六个统计量、读的是**分布**不是**当下**，与这块的性质不同 |

## D-046 依据卡的判据必须**透传**到视图层，不能停在结论对象里

**背景**：依据卡②底部那句结语（「样本量、覆盖率与重采样波动中有 N 项未达标 / 都在容差内」）
的**主语就是 `checks` 本身**，所以在 D-044 里把它从「两端各自拼句」上移到了 `outlook.mjs`。

小程序端接的时候只做了一半：`buildForecast(prediction, outlook)` 从 `o.checks` 取结语、
从 `o.evidence` 取「重采样波动」那一行的原料，而 `buildOutlookView` 的返回值**只列了视图字段**、
没把这两个带出去 —— `o.checks` 是 `undefined`，结语被 `?? ''` 兜成空串。

**症状**：不报错、不塌版、测试全绿（当时的断言还停在旧字段名上）。页面上唯一的差别是
卡②底部**少了一句话** —— 一张把「准不准」写成四行百分比、却不给结论的卡。

**结论**：结论对象（`outlook.mjs`）到视图模型（`buildOutlookView`）是一次**显式列举**的
转换，加字段时容易只加「渲染要用的」、漏掉「判据要用的」。所以定两条规矩：

1. `checks` 与 `evidence` 一律**原样透传**，视图层不重算、不挑字段；
2. 断言从「字段名对不对」升级为**同源断言** —— 用页面上看得见的判据（`n` / `minN`、
   覆盖率行、波动行）反推那个 N，再与结语里的 N 比对。结语若来自另一份实现，等式立刻破。
   ⚠ 反推时**只数那三项**：50% 分位覆盖率与 7 天区分度**不在**这句话的主语里，算进去会把 N 说大。

**顺带记一个反向教训**：模板顺序断言原先钉在 `.fc` 上，锚点消失时 `indexOf` 返回 `-1`，
而 `-1 < x` 恒真 —— 「A 排在 B 之前」这类断言在锚点消失时会**静默变绿**。
所以每条顺序断言都要额外配一条「找得到」的前置断言，且比较本身也要 `>= 0` 兜底。

## D-045 三列布局的三个尺寸口径：断点、格数、行高都必须写死

**背景**：设计稿（841×1870）里的依据卡与历史三图都是**三列**。落地时三处默认值
都会安静地给出错的答案 —— 页面照常渲染，只是形态与稿子不同。

| 处 | 默认行为 | 为什么错 | 改成 |
|---|---|---|---|
| 降列断点 | `@media(max-width:1000px)` 降两列 | 断点高过设计稿宽度，稿子在自己那个宽度上就掉成一列 | 800 降两列、620 降一列。**断点必须落在稿宽（841）之下** |
| 样本摘要列数 | `repeat(auto-fit,minmax(132px,1fr))` | 841 下（内容宽 793）只装得下 5 格，第六格单独掉到第二行、右边空一大片 | 格数恒定 6，写死 `repeat(6,minmax(0,1fr))`，窄屏按 3 / 2 降 |
| 依据卡行高 | 继承页面基线的 1.7 | 20px 的数值被撑成 34px 行盒，一行三句就多出 40px —— 四行累计让这张卡比同排另外两张高出 160px | 三行各自写死 `line-height`（1.4 / 1.15 / 1.5） |

**每日重置窗口的日期区间也被同一类问题咬到**：`.sig-prog` 原先是 `1fr / 1.05fr`，
右栏 370px 里 `.sw-v` 只剩 174px，而「2026.10.04（周日） — 2026.10.31（周六）」要
163px 起 —— 实测断成三行、末行只剩「六）」。改比例到 **`1fr / 1.2fr`**（右栏 394px、
值列 203px）后就地变成设计稿里的两行；`.sw-v` 上同时加
`word-break:keep-all;overflow-wrap:anywhere` 兜底，保证再窄也只是整块折行，
不会断在「周」和「六」之间。

**「数字 + 单位」不许被拆开，但 `keep-all` 只能给它那一张卡。**
卡③结语「…降到 3 天 4 小时。」在 217px 的内容宽上正好断在「小」和「时」之间。
`word-break:keep-all` 能把断点限制到空格处 —— 但它**不能扩大**断点集合：
卡②的结语是 26 个汉字连写、只有一个顿号，keep-all 会把顿号当断点，把它从 2 行
撑成 3 行、第一行只剩「样本量、」（实测）。所以这条收窄到
`.bc[data-bc="pace"] .bc-note{word-break:keep-all;overflow-wrap:anywhere}`，
`anywhere` 兜底「整词都放不下」的情形。

**三列形态下图表字号必然偏小 —— 这一点要如实记下来，不要靠「重新排版」的措辞糊过去。**
图内文字的实际字号 = `基准字号 × fontK(W) × (列宽 / W)`，而 `fontK = min(1, W/340)`，
所以当 `W ≤ 340` 时两项相乘**退化成 `列宽 / 340`，与 `W` 无关** —— 换一个
`CHART_W` 只会改变排版密度，不会改变字号。三列布局下每列 ~217px，于是图内文字
恒为基准的 **0.64 倍（~7px）**。217px 里要放 8 个刻度标签，字号再大就会互相压，
所以这不是 bug 而是三列形态的固有代价（设计稿在同一宽度下也是这个量级）。
两端因此**不一致且必须承认**：小程序按 345px 重新排版后 1:1 画到 canvas，图内
11px 字不打折；网页端只能缩。结论写进了 `scripts/acceptance.mjs` 的 A7 脚注
（那里是「代价」唯一会被反复读到的地方），`.chart` 的 CSS 注释里有同一段。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 认为 841 是设计稿尺寸、不必逐像素对齐，接受单列 | 稿子给的正是三列形态；退成单列会连带把历史三图拆散，「图表缺少统一组织」这条要求随之落空 |
| `.metrics` 用 `repeat(5,…)` 凑成整行 | 5+1 比 6 更难看；格数本身恒定（`renderMetrics` 只出 6 格），写死最省事 |

## D-043 共享模块从 1 个扩到 2 个：准入条件是「自包含」

**背景**：移动端要做与网页端同口径的预测总览，需要同一套「ETA / 置信度 / 依据摘要」
的推导。按 D-009 以来的一贯做法，**同一件事只许有一份实现** —— 但在两端各写一份
正是本项目反复吃过亏的地方（词表分裂、时间戳口径不一致，见 D-032 / KI-005）。

**决策**：`scripts/build.mjs` 的同步清单从单个 `scene.js` 扩成
`SHARED_MODULES = ['scene.js', 'outlook.mjs']`，逐字复制到 `miniprogram/utils/` 并加
「勿手改」文件头；`test-shared.mjs` 逐字节核对两侧一致。

**新增模块的准入条件：必须自包含（`outlook.mjs` 零 import 仓库内其它模块）。**
理由不是洁癖 —— 同步是**逐字复制**，被复制过去的模块里若有 `import '../../src/lib/x.mjs'`，
在小程序运行时那条路径不存在，而失败方式是**模块加载期抛错**：页面白屏，但
`build` 与 `test-*` 全绿（它们在 Node 里跑，路径是通的）。这属于「看不出坏了的坏法」。

**同步的自然边界**：`SHARED_MODULES` 只能放**纯计算**模块。`scene.js` 是几何、
`outlook.mjs` 是推导 —— 都不碰 DOM / canvas / `wx.*`。渲染两侧各写（网页走
`svg.mjs`，小程序走 `draw.js` 画 canvas 2d），这是**有意的**：渲染目标的差异是真实的。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 两端各写一份推导 | 同口径逻辑分叉后，两边的「置信度」会给出不同档位 —— 而页面之间不可能互相校验 |
| 让 `outlook.mjs` import `predict.mjs` 的常量 | 破坏自包含，跨端复制即失效。需要的常量在 `outlook.mjs` 里就地定义 |
| 小程序侧 `require` 一个构建期生成的 bundle | 引入打包步骤；而 `build.mjs` 现在只是复制文件，零依赖、零工具链 |

⚠ `AGENTS.md`「共享代码的同步规则」一节原先写「`src/lib/scene.js` 是唯一真源」，
已同步更正为两个。

## D-042 预测数字必须可复现：bootstrap 固定种子 + 展示取整到天

**背景**：A8（三个时区各构建一次，产物**逐字节**相同）突然变红：

| 时区 | `.ps-v` 的 80% 区间 |
|---|---|
| Shanghai | 17 天 23 小时 – 19 天 17 小时 |
| UTC / New_York | 18 天 1 小时 – 19 天 19 小时 |

**根因**：`bootstrapCI` 用未播种的 `Math.random` —— 在 D-027 那批里这只是一句
「不影响显示」（当时 `p.lo/hi` 两端都不渲染），而**这次我把 `medianDays` 画上了页面**。
后端是**按请求实时渲染**的，于是同一个页面在不同时刻请求会给出不同区间。

**决策**：

| # | 决定 | 理由 |
|---|---|---|
| 1 | `bootstrapCI` 换成确定性流：`mulberry32` + `BOOTSTRAP_SEED = 0x9e3779b9` | 「每次刷新略有不同」对一个**展示出来的**数字是不可接受的：用户会读成数据在变 |
| 2 | 展示层取整到天并加「约」（`约 18 – 20 天`） | 跨种子抖动实测 0.19 天 —— 报到小时是把噪声当精度 |
| 3 | `adjusted` 正式产出 `q10`（此前是死代码）；80% 区间改 `q10–q90` | 见下 |
| 4 | 校准行改叫「**80% 区间覆盖率**」，用 `covBand80` | 见下 |
| 5 | `scripts/test-outlook.mjs` 新增第 ⑦ 节，直接断言**值** | 见下 |

**单侧 vs 双侧覆盖率（口径必须分清）**：`cov80 = P(T ≤ q80)` 是**单侧**上界；
页面展示的是 `q10–q90` 这个**双侧**区间，它自己的覆盖率是
`covBand80 = P(q10 ≤ T ≤ q90)`。拿单侧的 83.3% 去标注两侧区间，是把两个口径混成一个。

**反例验证暴露了一个更值得记的事**：把 `bootstrapCI` 改回 `Math.random` 之后，
三时区构建**依然逐字节相同** —— 因为展示已取整到天，跨种子抖动（0.19 天）
**小于一天的粒度**。也就是说 **A8 已经抓不住这个根因了**（它现在守的是别的东西）。
所以新增的第 ⑦ 节直接比对 `predictAll` 两次调用的 `uncertainty` 原始值：

```js
JSON.stringify(u1) === JSON.stringify(u2)   // 展示取整后 A8 看不出来，这里能
```

**这是「恒绿的断言 vs 有效的断言」的一个实例**：改动本身是对的，但**守它的断言
换了位置** —— 只改实现、以为 A8 还在守着，等于把这条不变量交还给运气。

**被否掉的选项**：保留 `Math.random` 并给 A8 开豁免（等于承认「构建不可复现」，
而 A8 是当前唯一在守这件事的判据）；把区间改成固定字面量（数据变了不会跟着动）。

**后续**：D-027 表格里「bootstrap 用 `Math.random`」与它末尾的「见 KI-008」
描述的是**当时**的事实，已被本条取代。

> 明确信号 · Tibo 已预告**下一次**额度重置 · 距窗口开启 2026.10.08（周四）15:00

而这条预告的来源（10-07 19:19Z）说的是「…**Loading a banked reset** in everyone's paid
accounts. See you again **tomorrow**!」—— **当天正在给所有付费账号发一张预留重置卡**。
同页下半部还写着「上次重置 2026.10.07 11:35 · 已过 21 小时 52 分」，两处口径打架。

**根因：两处判据都按「整条推文」看时态，而这条推文里两个时间词都与重置无关。**

| 时间词 | 出处 | 权重 |
|---|---|---|
| `today` | 「today is also a little celebration day」 | 72 |
| `tomorrow` | 「See you again tomorrow!」—— 他从 Day N/ 系列推文里的日常告别语（前一天那条结尾也是 "See you tomorrow for Day 3!"） | 86 |

1. `hasOccurredReset` 里 `if (RE_FUTURE.test(t)) return false` —— `tomorrow` 就在 `RE_FUTURE`
   表里，**一票否决**整条的「已发生」；
2. `occurred = occurredShape && !future.some((w) => w.spec > VAGUE_SPEC)` —— `today`(72)、
   `tomorrow`(86) 都过阈值(50)。

**对照证据**（跑真函数的反事实，不是读代码推的）：

| 文本 | occurredShape | 判定 | 窗口 |
|---|---|---|---|
| 线上原文（today + tomorrow） | false | explicit | 10-08 |
| 只留正文 today，去掉末句 | true | explicit | 10-07 |
| today→the day，留末句 tomorrow | false | explicit | 10-08 |
| 两个时间词都去掉 | true | **occurred** | 无 |
| 09-22 同句式（"…loading a banked reset… **Let's go!**"，无时间词） | true | **occurred** | 无 |

**为什么已有机制没兜住**：`hasOccurredPart`（KI-010 的降级通道）**本来能救** ——
实测对这条返回 `true` —— 但它只挂在「预告已过期」那个分支上（`staleWindowReason` 非空），
而窗口是 10-08 15:00。后果是**页面先挂 29 小时假预告，到 10-09 14:59 才自愈**；
更糟的是 10-08 15:00 一开窗，`data-over` 由 0 翻 1，页面会从「距窗口开启」切成
「**窗口已开启 · 随时可能重置**」，一路挂到明晚 —— 比不修更误导。

**决策**：

1. **时间词与重置做句子级绑定，但带一道前提**：
   ① 正文里存在一整句构成「已发生」的陈述（`resetSentencesOccurred`）；
   ② **只有①成立**，才把时间词收缩到「讲重置的那些句子」里（`scopedTimes`）。
   为什么必须有①：不然任何真预告都会被削掉窗口 ——「A reset is coming. See you tomorrow.」
   里那个 `tomorrow` 也可能就是承诺时点，单看文本分不出「告别」与「约定」（下面反例②）。
   而一旦确认这条推文的主旨在**已发生的事**，寒暄句里的时间词作为「重置承诺」的置信度
   就极低了。这与 KI-010 是同一个思路，区别只在**时机**：那条等过期才触发，这条当场做。
2. **不动 `hasOccurredReset`**。它服务的是「这条推文的**主旨**是不是宣告已发生」，按整条
   判在那个语义下是对的（见它自己的注释）。改它会经 `classifyEvent` 牵到 `resets.json`
   的 `kind` —— 影响面从信号层扩到数据层，超出这次要修的范围。
3. **补一个 `RE_RESET_NOT_YET`（未达语态）闸门，只加在两处句级判据上**
   （`resetSentencesOccurred` 与 `hasOccurredPart`）。这是**写用例时实测出来的第二个坑**：
   「**A reset is coming** for everyone.」靠名词化弱证据（`RE_ANNOUNCE` 的「A/the reset」）
   会被读成「刚重置过」—— `RE_FUTURE` 表里有 will/soon/next/tomorrow，**却没有
   coming / landing / arriving**。`RE_ANNOUNCE` 注释里那句「靠巧合成立，不是判据成立」
   说的正是这件事（真实语料里恰好有 "See you soon" 压着才没暴露）。
   词表刻意**窄**，只认「be + 未达义动词」这一个结构：
   `We are loading a banked reset…` 里的 `loading` 与 `coming` 语法上都是 be + V-ing，
   分开它们的只有语义，所以词表躲不掉 —— 只能把它限制在一个语义类里。
4. **`hasOccurredPart` 同步加闸门**。不加的话，一条真预告会在窗口过期后顺着 KI-010 那条
   通道被降级成「重置发生过」—— 同一个病，晚 29 小时发作。

**验证**：

| 项 | 结果 |
|---|---|
| 反事实四例 | 见上表；目标那条 explicit → occurred、窗口清空 |
| 全库 305 条逐条 diff（`analyzeTweet`） | **只有 1 条变化**，正是目标那条；zero 误伤 |
| `detectSignals` 四个时刻 diff | 10-08 有差异（explicit→occurred、forecasts 少「2026.10.08（周四）」）；**10-09 / 10-12 / 10-20 零差异** |
| 反例验证（三个方向还原） | 去掉 `occurredInScope` → 4 红；去掉时间词收缩 → 5 红；去掉未达语态闸门 → 4 红（含「过期后」那一半）。恢复后哈希逐字节一致 |
| 回归用例 | `scripts/test-signals.mjs` 新增【14】14 项，含 3 个反例；全套 **218 项**通过 |
| 端点确认 | 那条推文 `downgradedFrom === undefined` —— 是**当场**判成 occurred，不走过期降级 |

**被否掉的选项**

| 选项 | 否掉的理由 |
|---|---|
| 改 `hasOccurredReset`（把未达语态加进它的否决条件） | 它被 `classifyEvent` 共用 → 会改 `tweets.json` 的 `kind` 与 `resets.json` 的 `type`。这次要修的是信号层判据，不该把数据层一起搅动 |
| 把 `coming` / `landing` 补进 `RE_FUTURE` | 同上：`RE_FUTURE` 是通用表，被 `hasOccurredReset` 与「含未来语气」的 reasons 文案共用 |
| 无条件收缩时间词（去掉①那道前提） | 任何真预告都会被削掉窗口 —— 反例② 实测变红 |
| 不修，等 29 小时自愈 | 中间 29 小时页面在说假话；10-08 15:00 后还会切成「窗口已开启 · 随时可能重置」 |
| 把 `hasOccurredPart` 的调用提前到「不用等过期」 | 会改 `explicit` 的语义、牵动整条识别链；而本条的修法只需要在**判定当场**多一个句级判据 |

**已知边界（记下来，别当成已解决）**：`RE_RESET_NOT_YET` 只加在两处**句级**判据上，
`hasOccurredReset` 的整条路径仍留着那个缺口（`hasOccurredReset("A reset is coming…")`
照旧返回 true）。实测全库 **0 / 305** 命中，所以目前不产生任何影响；但它是理论上存在的
不一致（同一条推文采集侧标 `kind:'reset'`、信号侧判 explicit）。见 KI-014。

## D-039 页面不再复述「留档触顶」，并把顶栏正下方那一块的上边距补上

**背景**：老大看到线上页面顶部这行字 ——

> 「留档超出上限 · 排除项保留了最近的 200 / 共 241 条
> 这种系统内部设计为什么要在页面展示？」

同一次还报了另一个毛病：「卡片和顶部下边框线都重叠了」。

**这行提示是上一批留下的**，出自 D-021 的决策 2 与 3：那轮把 `MAX_LISTED` 60 → 200，
并**重写**了这行文案（原来写成「只保留了前 9 / 60 条」，把两个不同列表的长度并排在一起，
读起来像「60 条里只留了 9 条」），还把它提到早退路径上，免得「本轮一个信号都没有 + 留档触顶」
被静默吞掉。

**它错在哪**：红线的落点从来不是页面。AGENTS.md 的原话是「`signals` / `occurred` 全量保留；
`hints` / `rejected` 有上限但**触顶会置 `truncated: true`**」—— 要求的是**数据**里说得出来，
而这由检测层与采集日志负责。页面复述它有两处说不通：

| 问题 | 具体 |
|---|---|
| 报的是**读者看不见的**东西 | 它列的是 `rejected`（排除项），而这个列表**两端都不渲染** —— 网页不渲染，小程序快照里也被清成 `[]`。向读者汇报一份他看不见的档案的容量，他既核不了也对不上，只会把它读成故障（它长得本来就象状态栏） |
| 措辞是**档案口径** | 「保留了最近的 200 条」描述的是留档，不是视图。即便换成 `hints`（页面确实用到），页面展示的也是 **0 或 1 条**线索、从不展示 200 条。视图该保证的是**它自己给出的数字是真的** |

**而且它已经从「偶发」变成「常驻」**。D-021 当时按「窗内被拒 62 条 / 60 天」外推，
说「要涨到 3.2 倍才再触顶，按当前节奏约 194 天」。实测（`data/signal.json` 的提交历史）：

| 日期 | scanned | rejected | truncated |
|---|---|---|---|
| 09-24 12:20 | 90 | 76 | false |
| 09-29 23:44 | 124 | 99 | false |
| 10-03 06:17 | 204 | 164 | false |
| 10-05 05:46 | 236 | 189 | false |
| **10-06 03:55** | 249 | **202** | **true** |
| 10-07 10:38 | 295 | 241 | true |

**13 天就触顶了，不是 194 天**。错在哪很明确：`rejected` 随**窗内推文量**走、不随天数走
（`scanned` 一周内从 90 涨到 295）。09-22 那个「62 条」是窗口还没铺满时的读数，不是稳态。
所以「提高上限」是条跑步机 —— 再提一次也只是把「常驻」推迟几周。

**决策**：

1. **页面不再显示留档触顶提示**。`truncationNote` 整个删掉，两条渲染路径都不再拼它。
   `truncated` 与 `counts.rejected` / `counts.hint` **照旧写进 `data/signal.json`**；
   采集日志另打一行 `⚠ 留档触顶：…`（`scripts/collect.mjs`）—— 红线要求的「不静默」落在
   **运维看得见的那一面**，而不是读者那一面。
2. **顺手修一处会静默变小数字的地方**：闲时那行的线索数原先取 `(sig.hints ?? []).length`，
   那是 `slice(0, MAX_LISTED)` **之后**的长度。一旦线索也触顶，页面就会把「260 条线索」
   写成「200 条线索」—— 不报错、不崩溃，只是数字变小。改用 `counts.hint`（未截断的真实条数）。
   这条比第 1 条要紧：第 1 条只是少一行提示，这条错了页面就在说谎。
3. **`MAX_LISTED` 维持 200**。它是纯体积保护；第 1 条之后它已经不影响读者，再提只会把
   「常驻」推迟，而「常驻」现在只体现在日志与仓库文件里。

**另修一个独立毛病：顶栏正下方第一块的上边距**。`header.top` 自带 `border-bottom:1px`，
而 `.sig-prog` 是它下面的第一个元素，`margin-top` 却是 0 —— 两块的上下边框正好落在同一像素行上，
看起来像顶栏那条线被加粗了。实测（真实渲染 + iframe 固定宽度，`--window-size` 不可信：
无头 Chrome 最小窗口宽约 485px）：

**新验收 A7b**（`scripts/check-layout.mjs`）：`.wrap` 的直接子元素里，**相邻两个各自带

这个 bug 存在时横向一切正常。只查「两块都有边框」这一种组合：`.hero` 这类无边框块靠 padding
撑开、与上一块的间距本来就是 0，按「所有兄弟都得有间距」写会立刻误报。

## D-038 每日重置窗口：跨多日的「规则」单独一档，且**不许进预测模型**

**背景**：2026-10-04 他发了一条与以往任何预告都不同**形状**的公告 ——

> `Over the next 28 days, each day we'll either ship one thing that is a clear improvement and relevant for most codex/work users or ship a full reset. Let the improvements begin.`

在此之前系统对它**零命中**：`src/`、`docs/`、`predict.mjs` 里搜不到任何相关处理。
它既不是 `explicit`（没给具体哪一天），也不是 `occurred`（不是已完成陈述），
`hint` 只会说「有额度意图但没给出时间」—— 于是页面照旧报「没有检测到重置预告」，
而**他刚说过未来 28 天每天都有一次重置摆在桌上**。

**判定三条同时成立**（`detectProgram`）：**天数 + 二选一（`either … or`）+ reset**。
少一条就会把别的话吞进来 —— 只认「28 days」的话，任何提到天数的话都会成立。
天数另加 2–400 的合理界，防「未来 500 天」这种量级被当成窗口。

**呈现：单独一块（`.sig-prog`），与横幅解耦。** 两者回答的不是同一个问题：

| 这条 | 那条（预告） |
|---|---|
| 这 N 天里**每一天**都在射程内 | 下一次是**哪一天** |

所以它**不能挂在 `signal.show` 那道门里** —— 没有预告时恰恰是最需要它的时候
（没有预告 + 还剩 26 天，读者最容易读成「这段时间不会重置」）。
实测两端**三条返回路径**（空态 / 有线索 / 有预告）都带它，测试逐条钉死。

**窗口文案走 `span` 粒度，且必须排在 `wholeLocalDay` 之前判。** 否则 28 天的跨度会落进
「含糊粒度」分支，渲染成 `10.04 00:00 → 10.31 23:59` —— 正是 D-019 否掉的那种
**凭空长出来的精度**。实际输出：当地 `2026.10.04（周日） – 2026.10.31（周六）`
（**整行不带任何钟点**），北京 `2026.10.04（周日）15:00 起`，截止退到 `rangeNote`。

**剩余天数按日历日相减**（`throughDay - todayDay + 1`），不是 `(to - now) / DAY` 取整 ——
后者在一天中间会得出 25.2 → 「还剩 25 天」，而这种差一天的错没人会去复核。

**⛔ 28 天计划不进预测模型。** 这是本轮最需要写下来的一条：

| 读法 | 成立吗 |
|---|---|
| 「未来 28 天内**必定**发生一次重置」 | **不成立**。原文是 `either ship one thing **or** ship a full reset` —— **二选一**，他完全可能 28 天全发改进 |
| 「这 28 天里**任何一天都可能**是重置日」 | 成立，但这是**定性**的：原文没有给出任何条件概率 |

把它当约束喂进分段风险模型，等于把「可能」写成「必然」，产出一个没有校准依据的数字 ——
而模型的全部合法性建立在「每次预测只用该时刻**之前**的数据」（见 `model.md` 第六节）。
塞一个没回测过的外部先验进去，那份合法性就没了。
所以：**页面单独展示它，模型照旧只做历史外推**，「还要等多久」那块旁边不出现它的影子。

> 顺带纠一条**外部误读**。库里有一条第三方转述写着
> `Wait what, Codex users get a free reset every day for 28 days if OpenAI doesn't ship a meaningful update?`
> —— 那是**别人的解读，不是原文**，原文没有「每天必有一次重置」的意思。
> 页面文案因此写成「每天要么发一个改进、要么给一次完整重置 —— **期间任何一天都可能重置**」，
> 两次强调「可能」，不留被读成承诺的余地。

**过期即撤**：整段走完（`to < now`）就不再出现 —— 与「过期的预告不再展示」同一条原则。
一条已经结束的承诺留在页面上，只会让读者以为它还在生效。过期判据挂在**字段**上，不挂在档位上。

**双时区由数据层算**（`buildProgram` 产出 `createdZones`，两端只读）。
端上自己换算要依赖 `Intl`，部分安卓机型不可用 —— 这条理由在 `base.createdZones` 上
已经写过一次，不是新规矩。宣布时刻在两端逐字相同：
`发布于 2026.10.05（周一）04:33 北京 · 2026.10.04（周日）13:33 当地`。

**测试**：signals 新增 21 项（三条判定条件各自的命中 / 不命中、真实语料的起止与两个时区、
四个「不命中」反例、过期即撤、渲染层「只出现一块」）；小程序【8c】12 项，

## D-037 民调（poll）进采集：正文之外唯一的量化民意，且**不许扫进词表**

**背景**：老大发来一张投票截图问「这种你觉得属不属于重置信号呢？」——
他的投票「今天算不算好日子」，其中一条选项写着 `🫨 (needs a reset)`，76% 投了它，
他随后回 `I accept your vote`。查证分三层，结论分别不同：

| 层 | 结论 |
|---|---|
| 已核实 | 这条推文正文只有 **`Vote`** 一个词；选项文本、得票率、参投人数**只在 DOM 的 `cardPoll` 里** |
| 已核实 | 系统此前**完全不采它** —— `tweets.json` 里没有 `poll` 字段，所以「76% 想要重置」在库里根本不存在 |
| 已核实 | 判定侧也读不出：`I accept your vote` 一个额度词都没有，而 `ctxIntent` 要求被回复内容含 reset + 范围词，正文 `Vote` 过不了那道门 |

**决策：只补采集，不动判定。** 老大在三个候选动作里勾的就是这一条，原话是
「采集侧补民调选项（选项文本 + 得票率）」。采集实现两件事：

1. **认两种 DOM 形态**（已出结果 / 进行中）—— 只写一种会在另一种上**静默返回空**；
2. **没有民调时不写这个字段**（spread 进来，不是 `?? null`）——
   否则 295 条推文每条多一个 `poll: null`，diff 全是噪音，而它一个字的信息都没带。

**⛔ 不许把选项文本喂进判定。** `needs a reset` 是**观众想要重置**，不是**他说要给重置**。
按词表扫进去会立刻产出「他说了重置」的假信号 —— 而且这条假信号**看起来特别有说服力**
（背后站着 76% 的票数）。要接进判定必须单独开一轮，先定「民意」与「承诺」的强度口径。

**本地化的坑（实测）**：界面语言是中文，页脚是 `74,565 次投票 · 最终结果`。
所以参投人数**只从那一行取数字**（取最大的一个、去千分位逗号），`status` 原样留档、不解释。
按 `votes` 之类英文词匹配，换个界面语言就**静默失效** —— 字段照样在，只是 `totalVotes` 恒为 `null`。
得票率从填充条的 `style="width: NN%"` 取（同一个渲染器画宽度用的值）。
⚠ **百分比可以是小数**（实测 `19.9` / `80.1`），别假设整数。

**测试**：parse 65 → **76 项**（字段透传 7 项 + 抽取表达式的形状扫描 4 项）。
形状扫描注定是弱的 —— 拦得住「有人把这段删了」，拦不住「选择器写错」。
明知弱还留着：**它一旦被删，采集会静默少一个字段，库里没有任何别的断言能发现。**

## D-036 弱证据要过否定 / 备选闸门：两条真实假阳性

**背景**：`RE_ANNOUNCE`（冠词 + reset 的**名词化陈述**）是一条**弱证据**路径 ——
句中看不到具体未来时间时，它把一条推文升级成 `occurred`。实测它在真实语料里把两条判成了「已发生」：

| 推文（2026-10-01 / 2026-10-06） | 系统结论 | 实际语义 |
|---|---|---|
| `Because usage on your primary dot is virtually unlimited at the moment, I can't really give a reset.` | 已发生 | **正好相反**（他给不了） |
| `Four updates or a reset. Or both. How was day 2.` | 已发生 | **规则复述**（二选一里的一个选项） |

**决策**：给这条弱路径加两道**近距离**闸门，命中即 `return false`：

| 闸门 | 匹配 | 为什么必须**近距离**（reset 前 0–3 个词） |
|---|---|---|
| `RE_DENIED` | `can't / won't / not / never / no / unable to … reset` | 全句扫会误杀真事实：`Resets all propagated. Or so I'm told.` 一句里就同时有「重置完成」与否定 |
| `RE_ALTERNATIVE` | `or / either … reset` | 同上；`Four updates **or** a reset` 正是要拦的形状 |

**只闸弱路径，不闸强证据。** `RE_PAST`（`Reset all propagated` / `has been reset`）在
`hasOccurredReset` 里**提前返回**，这两道门碰不到它 —— 所以强事实一条都没丢。
实测 `occurred` **7 → 5**，剩下 5 条逐条复核为真（10-02 / 09-26 / 09-22 那条 banked reset / 09-12 两条）。

**反例测试里差点写成一条恒绿。** 最初那条 `either … or ship a full reset` 用例
**被 `RE_FUTURE` 先拦住了**（原句里有 `we'll`），根本没走到新闸门 ——
它看起来在守新逻辑，实际守的是旧逻辑。补了一条**不含将来时**的变体，
并把原句标注为「由将来时拦下」，两条各守一段。

**残留（已知、未扩大改动）**：这两条现在落进 `hint` 而不是 `none`，
`reasons` 里仍写着「命中「A/the reset」名词化陈述」。影响仅限内部计数
—— 两条的 `window` 都是 `null`，而渲染层**只展示带窗口的线索**（实测带窗口的线索共 0 条），
所以它们上不了页面。**没有顺手去改意图计分**：那要给 `RE_DENIED` 加一条「把意图扣到 0」的
新规则，而它天然会误伤反向表达（`No way I'd forget a reset` 是否定词开头、意思却是肯定）。
收益是一个不上页面的计数，代价是一条影响所有档位的新规则 —— 不值。

**测试**：signals HEAD 那条基线是 `164 通过 / 1 失败`，本批结束后 **197 通过**。
那 1 项失败与本次改动无关，是**夹具老化**：`test-signals.mjs`【11】把 `NOW` 硬编码成
`2026-09-30T15:00:00.000Z`，而 10-02 那条 `Reset all propagated` 落在它之后，
被 `windowTo` 切出窗外 —— 数据每长一天，这条就多红一天。改成锚定数据自身的时间戳
（`Math.max(...stamps) + 60_000`，并过 `Number.isFinite`），此后不再随数据老化。

> ⚠ 【11】里**同一个硬编码值出现了两次**，只有第一处会老化变红（它断言「哪些推文判成
> `occurred`」，必须让最新推文落在窗内）；第二处（`lastResetAt` 的判据五）比较的是
> 「传与不传参数是否得出**不同**状态」，与最新推文在不在窗内无关，所以照旧安全。
> 不是「全都要改」—— 改之前先看那条断言依赖不依赖窗的上界。

## D-035 本机采集改为 1 小时一次，并修正过期的「实测周期」

**背景**：老大要求采集频率改为 **1 小时一次**（原为 8 小时）。改之前先复核了
`~/.workbuddy/logs/automation.log`，因为陈旧阈值由周期推导，周期改错会让页面天天说谎。
复核结果推翻了仓库里记着的一条事实 —— 当时的原文是：

> 配置声明的 rrule 是 8 小时，而日志里六组 `lastRunAt → nextRunAt` 间隔**全部精确等于
> 2.00 小时**。仓库按**实测值 120 分钟**记录，成因未确证。

把全部 23 组读完，真相是那个「2.00 小时」只是 **09-22 当天的取样快照**：

| 时段 | `lastRunAt → nextRunAt` | 组数 |
|---|---|---|
| 09-21 22:34 ~ 09-22 08:41 | 2.00 小时 | 6 |
| 09-22 20:05 ~ 09-30 13:49 | 8.00 小时 | 17 |

即：调度与 rrule 从 09-22 晚上起一直**一致**（都是 8 小时），所谓「成因未确证的不一致」
根本不存在。而常量停在 120、阈值 240 分钟对上 480 分钟的周期 ——
**页面有一半时间挂着「数据未更新」**，整整十天。这不是「已知边界」，是一个静默 bug，
且没有任何测试会红（断言守的是「阈值由周期推导」这条**关系**，关系一直成立）。

**决策**：

| 改动 | 前 | 后 |
|---|---|---|
| 自动化 rrule | `FREQ=HOURLY;INTERVAL=8` | `FREQ=HOURLY;INTERVAL=1` |
| `LOCAL_COLLECT_INTERVAL_MINUTES` | 120 | **60** |
| `STALE_AFTER_MINUTES`（推导） | 240 | **120** |

阈值仍是 `周期 × 2`（连续漏掉一整轮才提示），推导关系不动。

| 选项 | 否掉的理由 |
|---|---|
| 只改 rrule、不动常量 | 阈值 240 对上 60 分钟周期 → 横幅**永不触发**。这不是「页面更干净」，是陈旧检测静默死掉 —— 恰是本项目最想避免的「恒绿等于没有」 |
| 保留「声明 8h / 实测 2h」的记法不改 | 事实错误，且会让人去查一个不存在的调度器 bug。记录实测值必须**连取样区间一起写** |
| 阈值取 1 倍周期（60 分钟） | 一次调度抖动、一次机器休眠补跑就报陈旧 —— 回到旧设计那条教训：常亮的横幅会从告警退化成噪音 |
| 把周期写进页面文案 | 改频率时必然漏改；读者要知道的是「数据多新」，由时刻回答 |

**必须重新出镜像**：`STALE_AFTER_MINUTES` 是在**请求期渲染**时写进 HTML 的
（`data-stale-after`），只改仓库不换镜像，线上仍是 240 —— 而「线上有没有生效」
本地跑多少测试都测不出来。

**代价（如实记录）**：请求量升到 8 倍（每小时驱动一次 Chrome 抓 x.com 登录态时间线），
`data/` 的提交上限从 ~3 条/天升到 ~24 条/天。前者是账号侧的速率风险，后者是 git
历史的噪声 —— 都是频率的必然代价，不是 bug。若观察到风控迹象，回退路径就是把这两个
数字一起改回去（只有一个真值来源，改一处即可）。

## D-034 时长文案的口径定成「最高非零单位 + 下一级精度」，并给四处实现加对拍

**背景**：页面上出现了「0.2 天」「0.86 天」「67.7 天」这类小数天，老大要求换成时/分/秒。
一查才发现，**同一段「时长文案」口径在本仓有四份各自独立的实现**，彼此没有共享构建：

| # | 位置 | 函数 | 性质 |
|---|---|---|---|
| 1 | `src/lib/render.mjs` | `spanOf` | 网页端，权威口径 |
| 2 | `miniprogram/utils/format.js` | `spanOf` | 小程序端，**手写**副本（不是构建同步的） |
| 3 | `src/index.html` 内联 `<script>` | `spanFromMs` | 页首那行「已过 …」，**每秒重算一遍** |
| 4 | `src/lib/scene.js` | `fmtSpanShort` | 图内标签，短口径（只补到下一级就停） |

> **更正（2026-10-08，见 D-048）**：上表第 3 项 `spanFromMs` **已删除** —— 页首那行字
> 改成四位卷轴后没有调用点了（卷轴位置由 `renderElapsedCounter` 写死、此后由 ticker
> 逐位改，不再经过任何「时长文案」函数）。第 7 节因此从**四处**收敛为**三处**，
> 并用一条新对拍顶上：「页首卷轴位与 `spanOf` 同口径」。
> ⚠ 本表下面那条否掉理由（「让内联那份复用 `parts()`」）**依然成立**：`parts()` 是
> floor、`spanOf` 是 round，差一秒。D-048 能上卷轴，是因为它取
> `Math.round(days * 86_400)` —— **与 `spanOf` 同一个表达式**，不是因为它换掉了 `spanOf`。

**决策**：口径统一为「保留最高的非零单位当主数字，下一级只用来补精度」——
`≥1 天 →「6 天 17 小时」`、`<1 天 →「20 小时 41 分」`、`<1 小时 →「41 分 20 秒」`。
四处一起改，并在 `scripts/test-shared.mjs` 新增第 7 节：把 3、2 两个函数**从源码里
抽出来执行**、与 1 逐例对拍，同时校验 4 是 1 输出的**前缀**。

| 选项 | 否掉的理由 |
|---|---|
| 一律换成小时 / 秒 | 6.7 天 = 160.8 小时、最长等待 67.7 天 = 585 万秒 —— 读者得先心算才知道量级，那不是「更直观」，是「更难懂」 |
| 只改网页端，图内标签保持小数天 | 同一页会出现两种读法（正文「已过 21 小时」、图注「0.9 天」），且只在特定取值区间才显形 |
| 让内联那份复用现成的 `parts()` | `parts` 先把 ms **floor** 到秒再拆，`spanOf` 是先 **round** 到秒。差这一秒在 23:59:59.6 这种临界点上会让静态值显示「1 天」、脚本一接管就跳成「23 小时 59 分」—— 同一个数字在一秒内换副面孔 |
| 只加一条「不出现小数天」的断言 | 恒真。这个格式结构上就产不出小数天，真正会漏的是**四处里只改了一处** |

**代价（这次真的踩了）**：`src/index.html` 那行字由内联脚本每秒覆写，**构建期写进去的
静态值根本轮不到显示**。所以改完 `render.mjs` + `scene.js` + 三个测试脚本之后，
五套测试（165 / 25 / 58 / 165 / 25）**全绿**，用无头浏览器一截图 —— 页面上挂的还是
「已过 不足一天」。**绿不等于页面是对的**：测试断言的是模块输出，而这一处的最终输出
由另一份代码在浏览器里决定。

**验证**：`scripts/test-shared.mjs` 从 58 项增到 66 项。新增的 8 条逐条做过反例 ——
分别把两个函数改名、把 `round` 改 `floor`、把短口径改成不再构成前缀、并注入一处小数天
输出，确认每一条都会转红（含「抽不到函数」这条：函数被改名时不能静默放行，
否则防线会因为一次重命名而永久失效，还长着一副全绿的脸色）。

## D-032 完成句式的词表按「形状」写；展示类脚本与生产路径同口径

**背景**：修 KI-011 时顺手全库扫「形状像已完成」的推文，又扫出两处**静默丢失**
（详见 KI-012 / KI-013）—— 一处丢的是数据（少一条真重置），一处丢的是可信度
（本地产物显示的状态不是真实状态）。它们共同的教训值得单列成决策。

**决策一：凡是「主语可能是事件名词」的完成句式，词表一律写 `resets?`。**

`Reset all propagated` 一直判对，`Resets all propagated` 一直被丢 —— 只差一个 s。
单复数不会报错，只会少一条数据。所以判据按**形状**写，不按他某天恰好用的那个写法。

**决策二：`RE_FUTURE_PERFECT` 必须在 `have` / `be` 之后落到 reset 上。**

原写法 `(?:have|be)\b` 后面不要求任何词，等于给所有 `will be …` 的句子发了张否决票，
`That will be all` 这类收尾寒暄就能把一整条已完成句否掉。

**决策三：展示类脚本（`preview-miniprogram` / `make-prototype`）必须与生产路径同口径，
并**用扫描调用点**的方式守住。**

| 项 | 做法 |
|---|---|
| 口径 | 与 `src/lib/page.mjs` 一致：`lastResetAt: latestEventMs(resets.records)` |
| 守卫 | `test-signals` 第 11 组扫 `src/lib` / `scripts` / `server` 下所有 `detectSignals(` 调用点，要求每个都带 `lastResetAt` |
| 豁免 | 仅测试文件（按 `test-` 前缀）—— 它们常用空输入或缺省参数构造场景 |
| 自证 | 另有一条「扫描到了 ≥3 处调用点」—— 否则扫描写错时守卫会恒真 |

**被否选项**：

| 选项 | 否掉的理由 |
|---|---|
| 只改 `RE_PAST`（或只改 `RE_FUTURE_PERFECT`） | 两个正则叠加才造成漏判，改一处那条推文照样被判错 |
| 把 `RE_PAST` 的判定提到 `RE_FUTURE_PERFECT` 之前 | 会让「will have reset **by tomorrow**」被当成已发生 —— 那正是后者存在的理由 |
| 把 `That will be all` 之类寒暄加进排除词表 | 打地鼠：寒暄说法无穷，而根因是「`have`/`be` 后不要求内容」这个过松的尾巴 |
| 用行为断言守 `lastResetAt`（而不是扫调用点） | 只能守住已知的那条路径，**新写的调用点照样恒绿** —— 这次漏的两处就都是这么漏的 |
| 让两个脚本改调 `renderPage` 而不是 `renderAll` | 它们各自要覆写 `generatedAt`、且只取部分片段；为了一个 `LOGO_URI` 做重构不划算，就地补键即可 |

## D-031 分享：标题跟着状态走、分享图用默认截图、并为「朋友圈单页模式」让位

**背景**：老大要求「小程序页面需要加上分享功能」。首页与历史页此前**一个字都没有** ——
`onShareAppMessage` 未定义，右上角菜单里连「转发」都不出现（这是官方判据：
不定义该函数则无入口）。

**决策一：两处都定义，且标题跟着页面状态走。**

| 状态 | 分享标题 |
|---|---|
| 有明确预告 | `Tibo 预告：周二可能重置额度` |
| 其余（含线索档） | `距上次重置 3 天，还在等` |
| 历史页 | `29 次重置 · 平均间隔 8.4 天` |

⚠ **线索（hint）档不得套用预告句式。** `view.js` 的 `signalView` 给线索**同样挂
`headline`**（线索也有窗口），所以「有没有 headline」不足以区分两者 —— 只看它就会
把旁证说成承诺。判据是 `level === 'explicit'`。

**决策二：不传 `imageUrl`，走微信默认截图。**

| 候选 | 否掉的理由 |
|---|---|
| 复用网页端 `dist/og-image.png` | 它是 1200×630（比例 1.905），小程序分享图是 **5:4（1.25）** —— 差得远，会被裁成中间一条 |
| 换成网络图片 | 要额外配 `downloadFile` 合法域名，等于再添一处「没配就静默失败」的地方（与 `request` 域名同类，不弹错、最难查） |
| 构建期单独产一张 5:4 图 | 值得做，但要动 `build.mjs` 与资源管线；而默认截图截到的正是品牌区 + 当前状态，对这一页反而最贴切。**留作后续增强，不是现在的缺口** |

**决策三：不调 `wx.showShareMenu`。** 官方把 `menus` 参数标注为 Beta 且**暂只 Android 支持**；
而「定义了 `onShareTimeline` 才有朋友圈入口」是跨平台判据 —— 靠定义函数，不靠调接口。

**决策四：「分享到朋友圈」必须配套单页模式适配，这不是可选优化。**

朋友圈点开的**不是小程序**，是「单页模式」（scene 1154）。官方禁用清单里正好有三处
落在本项目的页面上 —— 不区分的话，从朋友圈进来的用户会看到一个「点了弹一句
『请前往小程序使用完整服务』」的页面：

| 被禁能力 | 本项目落点 | 处理 |
|---|---|---|
| 设备 → 剪贴板 | 两页共 3 处「复制原推链接」 | 不渲染 |
| 组件 → `navigator` | 两页页脚的互相跳转 | 不渲染（官方运营须知也禁止在单页模式里诱导跳转） |
| 开放接口 → 登录 | F9 提醒（`subscribeOnce` 先走 `wx.login`） | 不显示入口 |

还有**一处不是「被禁能力」而是布局约束**：单页模式顶部固定一条导航栏、底部固定一条
「前往小程序」操作栏，**两条都不支持自定义样式**。官方原文承认这「很可能会影响小程序
页面的布局」，运营须知又要求「应在单页模式中尽可能呈现完整的内容」。顶部那侧有官方配置
`singlePage.navigationBarFit` 兜着（默认「页面被导航栏挤压、与页面不相交」，本项目两页
都用默认导航栏，即此值）；**底部那侧官方没给配置**，只能自己留 —— `.wrap` 原本只留
80rpx，单页模式下由 `.wrap.sp` 抬到 240rpx（操作栏约 100rpx + iPhone 底部安全区约
68rpx + 余量）。刻意不写 `env(safe-area-inset-bottom)`：它在不支持的渲染环境里会让
**整条声明失效**、静默退回 80rpx —— 正是本项目最忌讳的那种「坏了但不报错」。

判定用 **`getEnterOptionsSync`**（2.20.1+），不是 `getLaunchOptionsSync` —— 后者只反映
**冷启动那一次**。用户先自己打开小程序（scene 1001）、再点朋友圈链接进来时，它仍返回
1001，整套适配就静默失效了，而这条路径恰恰最常见。缺 `getEnterOptionsSync` 时才回退，
判断不出来一律按**普通模式**处理（宁可在单页模式里多显示两个按钮，也不要让正常用户以为功能被砍）。

**⚠ 一个代码侧管不了的前提，而且两位官方口径不一致**：官方**文档页**《分享到朋友圈》
给的判据只有两条 —— 页面定义 `onShareAppMessage`，再定义 `onShareTimeline`，两条都满足
即可被分享到朋友圈，**全程没提任何后台开关**；但官方**社区**的置顶排查答复
《为什么我的小程序无法分享?》另外列了四项：开发者工具「项目设置 → 启用分享到朋友圈」、
小程序后台「功能 → 推广 → 分享到朋友圈」是否开通、微信认证与备案是否完成、
有无分享类违规记录。谁对谁错在代码侧无法判定，也无法验证该账号的实际状态（登录不了后台）。
所以结论只能是：**两处都写上不亏** —— 能力不具备时按钮不出现而已、不报错，也不影响
「发送给朋友」这条已经确定能用的路径。

**验证**：`scripts/test-miniprogram.mjs` 第 13 节（32 项）。八条反例注入逐条验过 ——
第一轮：把判据退回 `headline`、把 enter/launch 调换、去掉一处模板守卫、删掉历史页的
`onShareTimeline`、页面不传 `signal`；第二轮（对应上面那条布局约束）：去掉单页模式的
底部让位类、把让位量缩到 40rpx、把 `.wrap.sp` 改成会输给 `.wrap` 的单类 `.sp`。
各自只让对应的断言变红，还原后 **163 项全绿**。

## D-030 「窗口是否失效」判据挂到**字段**上，不挂在档位上

**背景**：KI-004 加的过期判据是这样写的 ——

```js
if (a.level !== 'explicit' || !isExpiredForecast(a)) return a;
```

它的**前提**是「这条推文带着一个指向未来的窗口」，而 `hint` 档同样满足这个前提
（`intent >= 3 ? 'explicit' : 'hint'`：额度意图只有 2 分时，推文带着窗口落到线索档）。
渲染层两个端都用 `.find((s) => s.window)` 挑线索，于是窗口过了、里面早已重置过，
它照样占着页首 —— 用户看到的是「还在等」，事实是「早就到了」（KI-011）。

**决策**：把判据从**档位**移到**字段**上 —— `staleWindowReason(signal)` 只看
`signal.window` 在不在、过没过期，与档位无关；档位只决定**处置方式**：

| 档位 | 处置 | 理由 |
|---|---|---|
| `explicit` | 撤走，或（正文里另有「已发生」整句时）降级成 occurred | 它是**承诺**，过期即作废；但承诺里夹着的事实不能陪葬（KI-010） |
| `hint` | 只撤 `window`，推文留档进 `windowExpired` | 它从来不是承诺，过期只是「不再指向未来」；推文本身仍是「他说过这一天」的记录 |

**被否掉的选项**

| 选项 | 否掉的理由 |
|---|---|
| 继续按档位过滤，给 hint 再写一个 `isExpiredHint` | 两份判据必然漂移：下次新增档位（或某个字段开始在第三个档位出现）时又要记得改第三处。按字段判一次就够 |
| 撤窗口时改写成 `candidateWindow` | 那个字段的语义是「还没被采用的候选」，`buildHypothesis` 会把它当**可用证据**捞起来。装一个已失效的窗口进去，等于让聚合逻辑把过期时间当证据用 |
| 过期就直接整条丢掉那条推文 | 线索的原文有留档价值（事后要能复核「当时系统看到了哪个窗口、为什么撤」）。撤窗口、留推文，两头都不丢 |
| 在渲染层加一道兜底判断 | 逻辑会分叉到三个消费方（网页 / 小程序 / API）。数据层出结论是这个项目的既定架构（D-018），渲染层只画 |

## D-029 截断正文的补全走「推文详情页」，并按「全量 / 手工」两条通道分工

**背景**：X 在时间线只渲染长推文的前 ~280 字符，而额度语义经常落在最后一句
（KI-009）。KI-002 那次的修法是「用上游历史的正文回填」，但它有个前提 ——
**上游得先收录这条**。2026-09-29 丢数据的那次，本地截断、上游也还没收录，
两个条件叠加，正文永远停在半句。

**决定**：

1. **补全的来源是本机登录态打开推文详情页**，不是第三方接口。理由是那条链路
   （CDP + 已登录 Chrome）本来就在跑，详情页是 "Show more" 指向的目标，
   拿到的就是完整正文。引入一个只读第三方接口等于把「能不能补全」交给第二个
   不受控的外部依赖 —— 而我们已经有一个不受控的了（上游）。
2. **搭在采集的同一次 Chrome 会话里**，在时间线收完之后跑：既能省掉第二次冷启动，
   又天然做到「两条流重叠的推文只开一次详情页」（跨流去重后才判候选）。
3. **跑在自动链路上的是「本轮收下的推文」**，不是「库内全部」。后者必然对
   「本来就完整、只是恰好超过门槛」的长推文白开详情页 —— 而它取回来的正文并不更长，
   于是不该打 `text_full`，于是下一轮又会被选中：每轮固定的无效请求。
4. **库内历史遗留走手工通道** `scripts/backfill-fulltext.mjs`（幂等）。
   历史债只存在于「这个功能上线之前」，补一次就收敛；跑一次付一次的代价，
   不摊到每一轮。

**被否掉的选项**

| 选项 | 否掉的理由 |
|---|---|
| 从详情页 HTML 的 RSC payload 里按 id 抠 `full_text` | **实现过，实测证伪**：详情页是纯 CSR，`document.documentElement.outerHTML` 里 `client:` / `full_text` / base64 键**一个都不出现**（诊断三连 false）。留着一路恒为 0 的「备份」不是安全网而是虚假的信心 —— 真正会失效的是 DOM 选择器，它一样兜不住，还多一个永远为 0 的数字误导人。真需要结构化数据时正确的路是 CDP 的 `Network.getResponseBody` 去接 TweetDetail 的响应 |
| 复用同一个 tab 做导航（省一个 target） | 详情页是客户端路由，同一 tab 再 `Page.navigate` 常常只换 SPA 视图、不重新渲染，会**静默取到上一条的正文**（不报错、只看长度也看不出来）。单开的代价实测 1–2 秒/条 |
| 每个候选都开详情页，不设上限 | 全量回补一次可能翻出几十条长推文，会把一轮采集从 1 分钟拉到 10 分钟以上。上限（默认 12）写进报告，是可复核的取舍而不是静默截断 |
| 候选只认「展开」入口这一个判据 | 渲染时机不同，入口可能还没挂上 —— 那时正文确实被切在半句，却没进候选。长度判据（≥240，实测截断点 275–278）兜住这种情形。两个判据的假阳性代价都不对称地小（多一次请求 vs 语义永久丢失） |

**连带改动**：`mergeTweetBatch` 多一条出口规则 —— 库里标了 `text_full` 的条目，
**不被更短的采集覆盖**。全量回补每 72 小时把整条时间线重采一遍，而重采到的正文
又是页面上那半句；没有这条规则，等于每三天把补好的全文打回半句，且不报错。

## D-028 发券型（credit）算一次重置：统一两处「上一次重置」的口径

**背景**：同一条 2026-09-22 的记录（`type: "credit"`，发券型），两处给出不同的
「上一次重置」—— 页面锚到 09-22（显示 0.29 天），采集下界仍锚到 09-12。
这不是笔误：`resetFloorMs` 的 `r?.type === 'reset'` 过滤器被 `test-parse.mjs` 里一条
注释为「更晚，但不是重置」的断言钉住，所以当初只登记为 KI-003，并写明
「**需要产品口径确认**，不宜由实现侧单方面改」。

**这次先把「口径有没有定过」查了一遍 —— 答案是定过，而且和实现相反：**

| 载体 | 原文 | 时间 |
|---|---|---|
| `PRD.md` §6 数据口径 | 「`reset`（直接重置额度）/ `credit`（发额度券）——**两者都计入**，但在时间线上分别标注」 | 原型期 |
| `PRD.md` §11.1 M0 需求基线 #4 | 「`credit`（发券型）是否计入统计」→ **计入**，「与第六节口径一致：两类都计入」 | 2026-09-21 确认 |

所以这**不是**一个需要重新拍板的产品问题，而是**实现与已确认的 M0 基线不一致**：
页面按 §6 做了（含 credit），采集下界没跟上。当初登记成「待产品确认」低估了它 ——
M0 那一栏就是产品确认。结论：**发券型算一次重置。**

**理由**：判据是产品要表达的那一件事 —— 对用户而言普通重置与发券型都是
「**额度被补充了**」，页面标签（`render.mjs` 的「普通重置」/「发券型」）与
`buildStats` 也一直按同一件事处理。于是统一到「含 credit」，即与页面口径拉平。

**决定**：

| # | 决定 | 直接后果 |
|---|---|---|
| 1 | `resetFloorMs` 的过滤器改为 `RESET_LIKE_TYPES.has(r?.type)`（`new Set(['reset', 'credit'])`） | 采集下界 09-11T08:09Z → 09-21T18:23Z（09-22 那条发券 − 24h 缓冲），**少回扫约 10 天** —— 原条目里说的那笔代价消失 |
| 2 | **显式列出两种类型**，不写成「任何带 `announced_at` 的记录」 | 将来上游若新增别的类型（故障、维护声明…），它该不该推进下界是**另一个问题**，不该被那一行默默决定。`test-parse.mjs` 补一条 `type: 'maintenance'` 守卫用例钉住这点 |
| 3 | `resetFloorMs` 与 `signals.mjs` 的 `latestEventMs` **仍然分开** | 口径统一 ≠ 函数可合并。一个答「该从哪儿开始扫」（按类型过滤 + 往前减 24h 缓冲），一个答「额度有没有落到账」（不分类型、不减缓冲）。合并会让 KI-004 的 `lastResetAt` 莫名早 24 小时 |
| 4 | `test-parse.mjs` 里复用 `floor` 的那组 `normalizeTimelineItems` 用例改为自带写死的 `sinceMs` | 它测的是去重 / 排序 / 裁剪本身，不该被 floor 的口径牵着走 —— 这次改动把它弄红了 4 条，正是耦合的证据 |

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 维持两处不一致，只把页面改成不含 credit | 页面数字会从 0.29 天跳回 10 天以上，与用户刚收到发券的事实相反。要统一的话，错的是采集侧那个口径，不是页面 |
| 写成「任何带 `announced_at` 的记录都算」 | 省一行，但把「新类型怎么算」变成一个静默的默认值。本仓库对静默默认值一贯零容忍 |
| 顺带把 `latestEventMs` 合并进 `resetFloorMs` | 见决定 3。两者用途不同，合并属于「看起来简化、实际把两件事绑死」 |
| 让 `resetFloorMs` 也接受 `reset_type` 原文（`banked` / 其他） | 类型映射已经在 `fetchHistory` 收敛成两种（`banked → credit`，其余 `→ reset`）；在下界这层再判一次等于把映射规则抄成两份 |

**影响的量级（实测，不是推测）**：**信号窗口不变** —— 窗口下界取「now − 60 天」与
「下界」里更早的那个，60 天（07-25）远早于两者，下界动不了它。重建快照实测
`windowFrom` 只差构建时刻的 12 秒（`04:04:15` → `04:04:27`），与口径无关。
所以这次改动的全部后果都在**采集侧**（少扫 10 天），页面与信号均无变化。

**留下的坐标**：见 KI-003（已移到「已修复」区）。

## D-027 小程序首屏快照摘出构建产物：不入库，改独立生成 + 测试前置

**背景**：`miniprogram/data/snapshot.js` 是构建产物，却一直入库，于是**每次构建
`git status` 都多一行 modified**。旧规矩（`data-source.md` §5）靠 `data-changed.mjs`
的判据挡住「垃圾提交」—— 挡的是提交，挡不住工作区噪声。而「长期 modified」这件事
本身就是伤害：它训练人忽略 `git status`（`miniprogram/config.js` 至今如此，那是
脱敏设计使然，但代价是同一个）。

**先查清了一件事：它不可能稳定。** 两个原因各自独立，都得治才算根治：

| 来源 | 实测 |
|---|---|
| 内嵌构建时刻：`generatedAt` 与由 `now` 派生的预测值、信号时间窗 | 受控实验（同数据、两个 `BUILD_NOW` 相隔 7 天）差 **120 行**，覆盖整个预测模型（`baseRate` / `exposure` / `rate` / `p` / `expectedRemaining` / `median` / `q50`…）与 `windowFrom` / `windowTo` |
| 不确定性区间：`bootstrapCI` 1000 次重采样，默认 `Math.random`（`src/lib/predict.mjs:402`） | 同数据 + 同 `BUILD_NOW` 两次构建，`p.lo/mid/hi` 与 `medianDays.lo/mid/hi` 仍不同。全库**没有一处**给 `rng` 注入过实现 |

所以「把它改成数据时刻」只解决前者 —— 收益是少一半噪声，代价是动用户可见数字
（见下表）。**决策：不入库。**

**决定**：

| # | 决定 | 直接后果 |
|---|---|---|
| 1 | `.gitignore` 命中 + `git rm --cached`（**磁盘文件保留**） | 工作区不再有长期 modified 的产物。它与 `dist/` 同类：都是从入库数据生成的 |

## D-026 增量更新只换容器；OG 分享图的滞后继续接受；apt 源做成可切换

**背景**：一次采集漏检修复（见 KI-002）之后要判断线上要不要重新部署。逐文件比对
（服务器在跑的镜像 vs 工作区）的结论是：**运行时代码一个字节都没变** ——
`page.mjs` / `render.mjs` / `signals.mjs` / `svg.mjs` / `server/*` 全一致；
`collect.mjs` 虽然变了，但容器里 `COLLECT_INTERVAL_MIN=0`、调度器压根不 `start()`。

真正陈旧的只有一处：`dist/og-image.png` 是**构建期产物**（`scripts/og-image.mjs` 用
@resvg/resvg-js 渲染成图片，接口改不了它）。于是页面上的数字早就翻新了，而分享到
微信/群里时卡片上还是上一次构建时的数值 —— 实测：页面 0.29 天，卡片印着 10.1 天。

**决定**：

| # | 决定 | 直接后果 |
|---|---|---|
| 1 | 重建镜像，把 OG 图刷到当前（顺带兜底页与种子数据） | 卡片终于显示真实数字。这是「OG 图只能在构建期出」这个代价**第一次真的产出一个错数字** |
| 2 | 更新走 `update-image.sh`（只换容器），不重跑 `deploy-remote.sh` | 首次部署那套（装证书、往网关配置追加 server 块）都已就位，重跑会重复注入 |
| 3 | 换完容器**必须** `nginx -s reload` | 网关按**容器名**反代（`proxy_pass http://tibo-reset:8787`），nginx 在启动/reload 时解析一次并缓存；换容器后 IP 变了，不 reload 就 502 |
| 4 | 旧容器留在 `tibo-reset-prev` 作回滚点 | 任一步失败自动还原（含 reload）；确认稳定后手工清理 |
| 5 | Dockerfile 的 apt 源做成 `ARG APT_MIRROR`（默认空＝官方源） | 国内构建时 `deb.debian.org` 被 DNS 解析到坏地址（实测 8.134.121.112），apt 层 exit 100，而报错只说 "not signed / Bad Gateway"。由 `ship-image.sh` 探测到取不到索引后自动切国内源，默认行为不变 |

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 不重建，接受卡片数字滞后 | 卡片是**对外**可见的。错的数字比「没有」更糟，而重建的成本只是一次构建 |
| 把 OG 图改成请求时生成，或从数据卷读 | 根治方向，但要引 resvg（devDependency）进运行镜像，与 D-002「运行镜像零依赖」冲突 —— 属架构决策，需单独评估 |
| `docker cp` 把新图拷进运行中的容器 | 秒级、不重建，但非声明式：容器一重建就退回旧图，且不解决兜底页与种子数据 |
| 更新时顺手 `docker compose up -d` 重建网关 | 会中断主站和另外几个子域，而这里只需要一次 reload |

> ⚠ **2026-10-09 更正（原文不改，见 D-053）**：上表里「把 OG 图改成请求时生成，**或从数据卷读**」
> 这条把两件事混成了一件。「从数据卷读」**不需要** resvg —— 图由**别处**构建好送进来就行
> （resvg 只在**渲染**那一半需要）。真正撞 D-002 的只有「在容器里渲染」那一半。
> 现在采取的正是「从数据卷读」：本机 `build.mjs` 出图 → `push-ingest.mjs` 随数据 POST →
> 落 `data/og/`，服务端请求时读。所以这条被否的选项，**一半被否对了、一半被误否了**。

## D-025 网页改由后端请求时实时渲染；数据本机直推；后端同源提供网页与 API

**背景**：三条要求 —— 后端不用 `deploy/` 那套（不做 systemd/Caddy，把镜像放服务器上直接跑起来）、
后端域名用 `https://reset.example.com`、**网站与后端都通过接口拿动态数据、分析放在后端做，
因此不需要重复触发构建**。

**决定**（三条相互依赖，拆开任一条都不成立）：

| # | 决定 | 直接后果 |
|---|---|---|
| 1 | 网页在**请求时**由后端渲染（`GET /` 读模板 + 当前 `data/` → `src/lib/page.mjs`） | 数据一变、刷新即新，不必重建、也不必重启容器 |
| 2 | 后端**同源**提供网页与 API（一个域名、无跨域） | `dist/` 降级为渲染失败时的兜底；Pages 退为异地备份入口 |
| 3 | 数据由**本机采集后直接 POST `/api/ingest`** | 数据链不再经过 CI，`INGEST_URL` / `INGEST_TOKEN` 两个 Secret 作废 |

**必须先看清的一条因果链**（本次最容易做错的地方）：原先把 `data/**` 从 CI 触发里摘掉是
**不安全**的 —— 数据到后端的唯一路径当时是「CI 构建后转发」：

```
本机采集 → git push data/ → CI 触发 → build → POST /api/ingest → 后端
                                    ↑ 想摘掉的就是这一环
```

摘掉它，后端就再也收不到新数据（页面照样上线，只是数据静默停在旧值 —— 正是本项目
最想避免的那种「看起来一切正常」）。所以决定 1 与决定 3 必须**同时**做：先让本机能直推，
才能安全地把构建触发摘掉。

**为什么渲染逻辑没有变成第二套实现**：`render.mjs` 原本在 `scripts/` 下（构建脚本的位置），
但它只依赖 `src/lib/chart-data.js`、`src/lib/scene.js` 与 `svg.mjs` —— **三者全是零依赖纯 ESM**。
所以把它与 `svg.mjs` 一起挪到 `src/lib/`，后端就能原样调用，构建期与请求时共用**同一个
`renderPage()`**。少了这一步，「页面数字 = API 数字」（A3）会从架构保证退化成两份实现对表。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 页面出厂快照 + 前端 fetch 接口替换区块 | 首屏会闪一下；脚本被禁用时只能看到旧快照；还要给每个区块加容器、改模板 —— 而收益与服务端直接渲染完全相同 |
| 把渲染逻辑搬到浏览器重写一套 | 两套实现必然漂移。本项目已因「同一个判断两处实现」吃过两次亏（词表分裂、时间戳口径） |
| 后端定时 `git pull` 取数据 | 容器里要装 git，新鲜度还受拉取间隔限制，不如本机直推直接 |
| 保留 `data/**` 触发构建 | 数据变化后重建页面**没有任何产出**（页面本来就是新的），只剩 CI 分钟数 |

**已知且接受的代价**：OG 分享图（`dist/og-image.png`）**动态不了**。它是图片文件，只能构建期
生成，接口改不了它 —— 分享出去的卡片会停在最后一次构建的数值。这是本轮唯一没有更好解的一处。

> ⚠ **2026-10-09 更正（原文不改，见 D-053）**：这条**站不住**，而且原因是它默认了一个没人守的
> 前提。「停在最后一次构建」在纸面上成立，但线上真正走得通的部署路径是
> **diff + `docker commit`** —— 那条路**从不重新执行构建**，于是 `dist/` 被一路原样继承，
> 「最后一次构建」永久停在 `2026-10-02`。实测卡片滞后 **7 天**、三个数字全错。
> 现在这张卡由本机构建后**随数据经 `/api/ingest` 送达**（`data/og/`），页面请求时读它。
> 「只能在构建期出」仍然成立（resvg + 中文字体，运行镜像零依赖），但那份产物**是可以送的**。

**顺带修掉的三处**：

  Docker **不会**自动填充（那是 named volume 才有的行为），空目录会让首屏静默走兜底路径。
  于是新增 `server/entrypoint.sh`：数据卷为空时拷入 `/app/seed-data`，已有数据则一个字不碰。

  `miniprogram/utils/scene.js` 都是构建产物，本机每采集一次都会提交它们。不排除就等于
  每采一次触发一次重建 —— **这条是决定 1 的必要条件，漏了它整件事会被悄悄撤回**。

  > ⚠ **2026-09-23 更正（见 D-027）**：`miniprogram/data/snapshot.js` 已改为**不入库**，

## D-024 更正「采集必须在境外」：真约束是「必须从非机房出口发起」

**背景**：排查后端部署就绪度时发现，「`x.com` 境内不可达 → 采集必须在境外」这个结论
被写进了 9 个文件、20 多处 —— 而它从未被验证过适用范围。它的全部依据，
是一次「境内 `curl x.com` 超时」的观测。

**实测**（三条同时成立）：

| 观测对象 | 结果 |
|---|---|
| 本机（广州，住宅出口，走代理） | **HTTP 200**，213KB 完整页面，4 次重试全中 |
| GitHub Actions runner（AWS 机房 IP） | **HTTP 403**，5,749 字节 Cloudflare 挑战页 |
| 那次「3/3 超时」 | 是 **`curl` 没走代理**造成的，不是「境内不可达」 |

**结论**：Cloudflare 拦的是**机房 IP 段**，与境内 / 境外无关。采集的真实约束是

被多个文件互相引用，越引用越像既成事实。**「实测」不能替代「实测是否覆盖了结论的全部范围」。**

**本次修改的载体**：`Dockerfile`（顶部注释 + `COLLECT_INTERVAL_MIN` 默认值 `30`→`0`）、

`server/index.mjs`（注释 + 启动日志 + 默认值）、`server/ingest.mjs`、`server/wechat.mjs`。

**保持原样的**：D-002 / D-003 / D-009 的正文按「历史记录不改写」原则保留，各加一行更正标注；

## D-023 移除 CI 定时采集，改由页面自己发现「数据停止更新」

**背景**：老大问「现在都已经不在 github 采集了，为什么还要每 30 分钟执行一次？现在都是本地采集，
不应该本地采集后推送数据再更新吗」。**这个质疑是对的** —— 数据更新早就由 push 驱动了
（`collect.yml` 的 `on.push.paths: data/**`），那条 `*/30` 的定时器与数据更新无关。

**实测一轮定时运行的产出**（数据不变时）：

| step | 实际效果 |
|---|---|
| 采集 `--max-age=540` | 短路，一个请求都不发 |
| 构建页面 | 产物重建（内嵌构建时刻） |
| 提交采集数据 | `data-changed.mjs` 判据 → 跳过，零提交 |
| 部署 Pages | **真部署** |
| 推送到境内服务 | **真 POST** → 服务端按 stale 幂等忽略 |

净产出 = 1 次 Pages 重部署 + 1 次被忽略的 POST，数据与提交历史一个字都没动。
按 `gh run list` 统计：每天 48 轮、每轮 36–89 秒。

**它唯一不可替代的职责**是发现「本机没在跑」：本机停了 → 没有 push 事件 → push 链永不触发
→ 页面安静地停在旧数据上。定时器是那条链上唯一的心跳。

**决策**：删掉定时器与 CI 采集链，把那份职责交给**页面自己**（`render.mjs` 的 `renderFreshness`）：

- 判据 = 「当前时间 − `tweets.json` 的 `updated_at`」超过阈值
- 阈值由 `LOCAL_COLLECT_INTERVAL_MINUTES` **推导**（`× 2`），不是第二个手写数字
- 两道提示互斥：`errors` 非空说「数据采集异常」，超期未更新说「数据未更新」

**为什么这样反而更及时**：定时器只能在「它自己跑的那一刻」发现陈旧，粒度是它的间隔；
页面判据在**页面被打开的那一刻**就在算，且不依赖任何进程在跑。

**同时删掉的**：`collect.yml` 的「采集」与「采集失败时显式告警」两个 step、顶层
`env.LOCAL_COLLECT_INTERVAL_MINUTES`（阈值推导的单一真值来源，随机制一起退役）、以及
`test-collect-warning.mjs` 第 5/6 节那 10 条断言（重写为「CI 不再采集」+「阈值由周期推导」）。

**顺带修掉的三处**：

1. `src/index.html` 页脚写着「每 **30 分钟**自动采集」—— 实测本机是每 2 小时，**这句本身就是错的**。
   改为不写频率：读者要知道的是「数据多新」（由后面的时刻回答），频率是内部信息
   （老大此前说过同类的话：「这种系统内部信息不应该在网站显示」）。
2. 提交 step 的 git 身份从 `git config` 改为 `GIT_AUTHOR_*` / `GIT_COMMITTER_*` 环境变量。
   那段 shell 曾被人在本机原样执行（排查用），后果是本仓库 local 身份被改成
   `github-actions[bot]`、提交作者写错 —— 2026-09-22 真实发生过一次。环境变量只作用于该
   step 的 git 进程，这个坑于是物理消失。
3. `docs/tech-selection.md` 的架构图还写着「x.com ──► GitHub Actions（每 30 分钟）」，
   而主链路早已改成本机 —— 一并更正。

**被否掉的选项**：

| 选项 | 否掉的理由 |
|---|---|
| 保留定时器但降频（如每 4 小时） | 降的是噪音，不是根因。它的产出仍是「重部署 + 被忽略的 POST」；发现职责挪到页面后，连这一次都不需要 |
| 删定时器但不补页面判据 | 本机静默时**没有任何发现路径**，页面会一直安静地展示旧数据 —— PRD 要求「停更必须一眼可见」 |

**代价（如实记）**：

- 页面判据只能报警、不能补数据。本机真停了，页面会提示「数据未更新」，但仍需人工把机器唤醒 ——
  这与定时器时代没有区别（那时 CI 也采不到，只能报警）。
- **阈值依赖「本机周期」这个数字**，而它在 WorkBuddy 自动化配置里，仓库只能记实测值：
  实测六组 `lastRunAt → nextRunAt` 间隔全部精确等于 **2.00 小时**，而配置声明的 rrule 是
  8 小时 —— **两者不一致，原因未确证**（没有去读 App 的内部调度存储）。仓库按**实测值**
  120 分钟记录。⚠ 若哪天自动化真按 8 小时跑，页面会常态化显示「数据未更新」，那时改这一处即可
  （`src/lib/render.mjs` 的 `LOCAL_COLLECT_INTERVAL_MINUTES`）。

> ⚠ **2026-10-02 更正（原文不改，见 D-035）**：上面这条「实测 2.00 小时」是 **09-22 当天的
> 取样快照**，不是稳态值 —— 09-22 20:05 之后的 17 组间隔**全部精确等于 8.00 小时**，与声明的
> rrule **一致**，「两者不一致、原因未确证」不成立。而常量停在 120、阈值 240 对上 480 分钟的
> 周期期间，**页面有一半时间挂着「数据未更新」**。教训：记「实测值」必须连**取样区间**一起记，
> 否则它会在配置改动后静默过期，且过期时没有任何测试会红。

## D-022 兜底阈值 120 必须由本机周期 480 推导，而不是「记得改两处」

> ⚠ **本决策的机制已于 2026-09-22 整体退役**（CI 不再采集，`--max-age` 与那条定时器一起
> 移除）—— 见 D-023。仍然保留它，是因为其中的**推导式修法**（把阈值从周期算出来，而不是
> 写两个需要同步的数字）与「两个各自合理的数字合起来矛盾」这个错法，都还值得记住。
>
> 2026-10-02 补：**D-035 是同一类错的又一次发生**（常量与周期脱钩），只是方向相反 ——
> 那次是「阈值小于周期」（横幅常亮），D-035 是「周期变大而阈值没跟」（横幅一半时间常亮）。
> ⚠ 本文的「120 分钟」指当年的 **CI 短路阈值**，与当前的**页面陈旧阈值 120 分钟**数值相同
> 但**毫无对应关系**（当前 = 周期 60 × 2），别把两者读成一件事。

**背景**：老大问「为什么数据采集失败了」。查下去，**采集本身没坏** —— 是 CI 有 **75% 的运行在
必然失败**，成因是两个各自看着都合理的配置数字合起来矛盾：

| 量 | 值 | 出处 |
|---|---|---|
| 本机采集周期 | **480 分钟** | WorkBuddy 自动化，每 8 小时一次 |
| CI 短路阈值 | **120 分钟** | `collect.yml` 的 `--max-age=120` |

`--max-age` 的判据是「数据年龄 < 阈值」，而数据年龄从本机刚采完的 **0** 涨到下一轮本机采集前的
**满 480 分钟**。120 < 480，于是每个周期里有 360 分钟都超阈值：

| 阈值 | 一个 480 分钟周期内（CI 跑 15 轮） | 折算每天 |
|---|---|---|
| **120** | **12 轮真采 → 必然 403**（占 80%） | 36 次白撞 = CI 运行的 **75%** |
| **540** | **0 轮** | 0 次 |

**实测证据（不是推理）**：

1. **时间线对得上**：本机 12:59 采完 → 13:11 / 13:38 / 14:19 / 14:51 四轮 CI **都没提交**
   （短路生效，当时年龄 12 / 39 / 80 / 112 分钟）→ **15:14 那轮年龄 134 分钟刚过阈值** →
   真采 → 403 → 提交 `b1dea67`。
2. **代码侧印证**：`freshEnough` 分支**不写任何文件**，所以「中间四轮没提交」只可能来自短路。
3. **规模**：`stats.json` 的提交历史里，**20 次有 12 次**的 `errors` 是同一句
   `实时采集失败：HTTP 403`。读起来像采集一直在坏，其实只是每轮都白试一次。

**更值得记的是「为什么三天没发现」**：`采集` step 有 `continue-on-error: true`，GitHub 会把
`conclusion` 改写成 `success`，只有 `outcome` 保留 `failure` —— 于是

```
gh run list                                    → 每一轮都是绿点 ✅
gh run view <id> --json jobs --jq '.jobs[].steps[] | "\(.outcome)\t\(.conclusion)"'
                                               → 采集 = failure / success ← 真相只在这儿
```

**采集连续失败三天，状态灯一路绿灯。** 这比 403 本身更值得担心。

**决策**：

1. **阈值改为由周期推导**，不是硬编码：

   ```yaml
   env:
     LOCAL_COLLECT_INTERVAL_MINUTES: '480'   # 单一真值来源
   ...
   run: node scripts/collect.mjs --max-age=$(( LOCAL_COLLECT_INTERVAL_MINUTES + 60 ))
   ```

   取 `+ 60`（一轮余量）= 540。**改本机周期只改那一处**，阈值自动跟着变。
   `test-collect-warning.mjs` 新增 4 条断言守这条推导关系，含「`--max-age` 在整个 workflow 里
   只许出现一次、且必须是推导式」—— 防止有人以后在别处又加一个硬编码的。

2. **CI 的提交判据从字节级换成 `scripts/data-changed.mjs`**。`git diff --staged --quiet` 会把
   `stats.json.generated_at`、`stats.days_since_last`、`signal.json.generatedAt` 这些**每轮必变、
   却与数据无关**的字段当成变化 —— 那正是同一个「垃圾提交」问题的另一半。

   ⚠ 但 `errors` 要按「**首次**失败必须落档、重复的失败不重复落档」理解：否则「线上挂着横幅」
   在仓库里没有痕迹，下一轮从仓库检出就成了「数据陈旧但页面一切正常」—— 页面会说谎。

**实测**：

| 验证 | 手段 | 结果 |
|---|---|---|
| 540 在「数据 200 分钟前」时短路 | 沙箱 dataDir 里把 `updated_at` 推到 200 分钟前，跑 `runCollection` | `skippedFresh: true` · `errors: []` · **文件 mtime 未变** |
| 提交判据四个场景 | 把 workflow 那个 step 的 shell **原样提取**出来（commit/push 换替身）实跑 | 干净→跳过 · 只改时刻→跳过 · 新推文→提交 · 错误内容变了→提交 |
| 判据用真实失败数据 | 拿 `b1dea67` 的 `stats.json` 当基线，只推时刻字段 | 跳过（正是那 12 轮的形态） |

**被否掉的选项**：

- **「在注释里写清楚『改一处要改两处』」**：靠人记。这类矛盾恰恰是「两处各自看着都对」才发生，
  注释拦不住。改成推导之后，漏改在物理上不可能。
- **B：CI 彻底不采，只用仓库数据构建发布**：本轮 `push` 触发的 CI 已经把它实证了一遍
  （`采集` step **skipped**、`refresh`/`ingest`/`deploy` 三个 job 全绿、零噪音）—— 可行。
  否掉它只因为会失去「本机忘了跑」时的唯一兜底，而那时正是最需要有人拉一把的时候。
- **C：把本机周期压到 2 小时以内**：方向反了。8 小时是**刻意选的**（要调起 Chrome 登录态），
  降周期只是让阈值更容易满足，代价是采集侧频繁拉起浏览器。修的是阈值，不是周期。

**代价（如实记）**：本机若真停摆超过 9 小时，CI 兜底会晚一轮才触发（540 而非 120）。
这是刻意的取舍 —— 那次触发失败才是**真该告警**的，而「本机停了 9 小时」比「本机停了 2 小时」
更值得一跳。

## D-021 留档上限 60 → 200，触顶提示改成「保留 X / 共 Y」

> **更正（2026-10-07，见 D-039）**：本条**决策 2 与 3 里关于「页面提示」的部分已撤销** ——
> 页面上不再显示留档触顶提示（它报的 `rejected` 两端都不渲染，见 D-039），
> 「不静默」改由采集日志承担。`MAX_LISTED = 200`、以及「按倒序截取、丢最旧留最新」
> 这条方向判据**仍然有效**。
> 另：本条此前**没有标题**（正文在，「`## D-021 …`」那行丢了），2026-10-07 一并补上 ——
> 顺序是按编号倒序排的，缺标题会让它在 D-022 与 D-020 之间变成引不到的隐形条目。

**背景**：老大看到页面上这行字 ——

> 「线索/排除项超出留档上限，signal.json 中只保留了前 9 / 60 条
> 这又是什么东西，60条也太少了，200吧，每次有新的进入就删除最旧的」

**先纠三条**（这三条都是那行文案与旧注释造成的误读，不是老大看错）：

| 读到的是 | 实际是 |
|---|---|
| 「60 条里只保留了 9 条」 | **两个不同列表**的长度被并排了：`9` 是 `hints`（那一轮**没**触顶，9 条全在），`60` 是 `rejected`（触顶）。`前 X / Y 条` 这个形如「X of Y」的句式把读者带偏了 |
| 「现在保留最旧的，得改成删最旧的」 | 本来就是**留最新、丢最旧**：`list` 按 `created_at` **倒序**，`slice(0, N)` 取的是头部。实测 `rejected` 首条 09-22 07:02（最新）、末条 09-12 01:50（最旧），被丢的正是 09-12 那几条 |
| 「每条新进来的会挤掉一条旧的」 | 这**不是累积日志**。每轮 `detectSignals` 都在时间窗内**全量重算**，推文离开列表的原因是**滑出 60 天窗**，不是被淘汰。所以上限的真实约束是「窗内条数的峰值」，与历史总量无关 —— 提高它不会让文件随时间无限涨 |

**另查实一件事**：`MAX_LISTED = 60` 的原始动机**已经消失**。它引入于 `7586fc3`（09-22 12:03），
保护的对象是「rejected 随小程序快照下发」；而 `3b5f1f0`（09-22 **12:44**，晚 41 分钟）把 rejected
从快照里整个摘掉了 —— 那个提交的注释还写着「实测这一项就占快照的一半（47KB / 92KB）」。
所以这个数字现在只保护 `data/signal.json` 一个仓库文件，页面与小程序都不受它影响。

**决策**：

1. `MAX_LISTED` **60 → 200**。窗内被拒条数（实测 62 条 / 60 天）要涨到 3.2 倍才再触顶，按当前
   节奏约 194 天。代价为零：rejected 不进页面、不进小程序快照、不进首屏。
2. **重写那句提示**：只列**真触顶**的列表，写成「保留 X / 共 Y 条」，并点明保留的是**最近**的。
3. ⚠ **提示必须两条渲染路径都带上**。`renderSignal` 里 `if (!blocks.length) return` 是早退，而提示
   原先排在它**后面** —— 于是「本轮一个信号都没有 + 留档触顶」直接吞掉提示，成了静默截断，
   正是 AGENTS.md 那条红线的反面。现提取为 `truncationNote()`，早退路径也拼上。
4. **`counts` 补 `rejected` 真实条数**。要写「共 Y 条」就得有 Y，而 `rejected.length` 是**保留数**。
   不复用 `counts.none`：那是减法结果，语义是「none 级的条数」；当前二者相等只因每条 none 都被
   排除，不是定义上的等价。
5. **小程序快照的 `truncated` 改为重算**（只按 hints）。快照里 `rejected` 被清成 `[]`，沿用原值会
   自相矛盾 —— 保留 0 条却标着触顶，渲染出来就是「排除项保留了最近的 0 / 共 62 条」。
6. **修正一处被记错的归因**（代码注释与 AGENTS.md 都复述过）：旧注释举 2026-09-12 03:20
   「A reset and a quick update…」为例，说它被 `.slice(0, 5)` 丢掉、据此把「rejected 丢最早」当成
   危险源。实测那条推文是 **`occurred` 档**（声明的是「已经重置了」），从不进 `rejected` —— 真正的
   重置信号走 `explicit` / `occurred`，而两类不设上限。所以「留最新、丢最旧」对 rejected 是安全的。

**实测**（构造数据跑 `renderSignal`，不靠推断）：

| 场景 | 输出 |
|---|---|
| 有预告 + 排除项触顶（201 条） | `留档超出上限 · 排除项保留了最近的 200 / 共 201 条` |
| **无信号 + 触顶**（早退路径） | 同上 —— 修复前这一格是**空**的 |
| 线索与排除项同时触顶 | `留档超出上限 · 线索保留了最近的 201 / 共 260 条 · 排除项保留了最近的 200 / 共 201 条` |

`bulk-200`），以及真实数据上「排除项按时间倒序」。脚本共 109 项。

## D-020 右上角「观测中」后面是当前北京时间，不是数据采集时刻

**背景**：老大截了右上角的图 ——

> 「这右上角应该是当前北京时间才对」
> 「应该与时钟一致，时间变了他也应该变」

当时的输出是 `● 观测中 · 12:59`，而真实时间是 15:02。

**先纠一条**：这个 `12:59` 没算错，它是**数据采集时刻**（`dataUpdatedAt`）。
错的是**它被放在了哪里**：

| | 显示 | 读者会怎么读 |
|---|---|---|
| 旧 · 右上角 | `观测中 · 12:59` | 「观测中」是**现在进行时**，后面却跟一个两小时前的数字 —— 只能读成「现在 12:59」，第一反应是页面停更了 |
| 页脚 | `最近一次采集 2026.09.22 12:59 北京` | 同一份数据时刻，但写清了它是什么 |

**决策**：右上角改成**当前北京时间**，由页首脚本每秒推进（`HH:MM:SS`）。

1. **静态兜底值取构建时刻**（`m.now`），不取数据采集时刻 —— 页面刚构建/部署时两者几乎一致；
   而数据时刻会引发上表那种误读。`builtAt` 是「渲染时刻」、`generatedAt` 是「采集时刻」，
   **两者都不是当前时间**，这一点以前没区分开。
2. ⚠ **必须显式写 `timeZone: 'Asia/Shanghai'`**，不能读本机时钟 —— 浏览器可能在任意时区。
   小程序侧不用 `Intl`（部分安卓机型不可用或不完整），由 `beijingParts` 手算 `+08:00`，
   两端都是 `HH:MM:SS`。
3. **数据新鲜度仍由页脚的「最近一次采集 ⋯」承担**，一处只讲一件事。
   这不是把信息删掉，是把它放回该在的地方。
4. 降级态反过来：那时要传达的正是「这是什么时候的快照」，所以仍给数据时刻，
   文案两端统一为 `快照 · HH:MM`（此前小程序历史页只有一个光秃秃的「快照」）。
5. `.pulse #upd` 加 `font-variant-numeric: tabular-nums` —— 秒位每秒一变，
   不用等宽数字整块胶囊会左右晃。

**取舍**：右上角从此不再承担「数据多新」。这是有意的 ——「观测中」本身就是现在进行时，
让它说现在，比让它说过去更省读者的力气。

**实测**（不是只看渲染结果）：

| 检查 | 手段 | 结果 |
|---|---|---|
| 秒位真的在跳 | headless 同一页读两次读数（间隔 2.5s） | `15:12:43 → 15:12:45` ✅ |
| 走的是北京时间，不是本机时钟 | 把浏览器强制到 `America/New_York`（偏移 −4）再跑一遍 | 本机 `03:11:37` / 页面 `15:11:37` ✅ |
| 页脚不受影响 | 同上 | 仍为 `2026.09.22 12:59` ✅ |

⚠ 探针第一版把判据写成「页面值 === 独立算的值」，实测会误报 —— 页面每秒才写一次字，
读的瞬间可能刚跨过下一秒。**判据必须容 1 秒**，否则测的是「采样时刻对不对齐」，
不是「显示的时间对不对」。

## D-019 窗口时间：具体时刻优先，区间只留给本来就含糊的粒度

**背景**：老大的三句原话 ——

> 「距离窗口开启时间倒数应该也动起来，另外你这时间也不对啊，应该是距离北京时间的倒数，
> tibo 当地时间为什么还不是具体的时间，北京时间也只需填具体时间，
> 只有时间不明确的时候才是时间段。」

拆开是两件事：

**① 网页端根本没有「距窗口开启」这条倒数。** 页首那个跳动的数字是「距上一次重置」——
**往回看**的；往前看的那条只在小程序里有。而且它只给数字、不写数到哪一刻，
读的人没法核对。**先纠一条**：这个倒数本来就数到北京时间 09-22 15:00，换算没错；
错的不是换算，是页面上没有可核对的锚点。

**② 窗口块在凭空长精度。** 实测的旧输出：

| 行 | 旧值 | 问题 |
|---|---|---|
| Tibo 当地时间 | `2026.09.22（周二）00:00 – 23:59` | 「周二」是**天**粒度，硬展开成钟点区间，读起来像他定在当地午夜重置 |
| 北京时间 | `2026.09.22（周二）15:00 → 2026.09.23（周三）14:59` | 页面上唯一的「具体时刻」被夹在跨日箭头里，看不出哪一刻是**窗口开启** |

**决策**：

1. `describeWindow()` 按**粒度**定形 —— 具体时刻优先，区间只在时间本来就含糊时出现：
   - `instant`（真说了钟点）→ 两边各给**一个时刻**；
   - 当地一整天（`day`）→ 当地「`2026.09.22（周二） 全天`」，北京只给**开启那一刻**
     「`2026.09.22（周二）15:00 起`」，跨日的事实退到 `rangeNote` 一句话里；
   - 整周 / 一周内的某几天 → **时间本来就含糊**，区间才是诚实的表达，照给区间。
     一刀切成单点，页面就会报出一个他不认得的时刻。
2. 「距窗口开启」的倒数补齐到网页端（放在窗口块上方，每秒跳动），
   **锚点写在标签里**（`北京时间 2026.09.22（周二）15:00`）——数字和时刻同一行，
   对不上就是我对不上。窗口开了换成「窗口已开启 · 随时可能重置」。
   两端文案对齐，小程序端不再各写一套。

**被否掉的选项：把「3am」当成窗口时刻。** 老大选的是这条（「采纳 3am 当具体时刻」），
查证后**没有照做** —— 那条回复的上下文是这样的：

| | 内容 |
|---|---|
| 被回复（@My_Ai_Bi） | `the GPT-6 Community Night was 🔥` |
| Tibo 回 | `3am on a tuesday` |

他在跟人聊**社区活动办到几点**，不是回答重置时间。全仓 69 条推文（含 52 条回复的
被回复原文）里只有 **2 处钟点**：这一处，与 `11pm on a Tuesday, big startup energy`
（原创，同样在说自己的作息）。**没有一处与额度同段。**

想另找一个「他历史上的典型重置钟点」也不成立：53 次历史重置铺在 **19 个不同小时**上
（峰值洛杉矶 17:00 也只占 13.2%），没有任何钟点可以当默认值。

照做的话，页面上会写「重置在 09-22 18:00（北京）」——而依据是一句聊聚会的话。
这与本项目的底线冲突：**漏检伤覆盖，假信号伤可信度，而可信度是这个产品唯一的资产。**
3am / 11pm 照旧作为**未采纳的钟点线索**列在依据区（可见、可复核），只是不参与定窗口。

**首屏预算**：多出来的倒数条 43px（桌面）没白拿 —— 卡片内距同步收了一轮
（`.sig` padding 18→14、`margin-top` 18→12、`.sig-head` 12→8、`.sig-win` 12→9）。
实测（判据是倒计时**底部** ≤ 视口高）：

|---|---|---|---|
| 1440×900 / 1440×760 | ✅ | ✅ | ✅ 底部 695 |
| 1280×720 | ✅ 底部 693 | ⚠️ 底部 712（余量只剩 8px） | ✅ 底部 695 |
| 390×844 | ✅ 底部 709 | ✅ 底部 801 | ✅ 底部 784 |
| 375×667 | ❌ 底部 741 | ❌ 底部 834 | ❌ 底部 817 —— **接受**（同 D-018） |

**测试**：signals 96 → **102 项**（新增 6 项：三种粒度的窗口表述 + `rangeNote`）；
一致性 24 → **27 项**（新增【⑤ 倒计时锚点自洽】—— 把 `data-from` 按北京时间格式化，
必须与标签逐字相同。这条判据不依赖外部数据，校验的是「页面自己说的话前后一致」，
也就是用户真会做的那次核对）；小程序 115 项、布局 7 档全过。
两端倒数用 headless 实测「同一页读两次读数」确认**确实在跳**，不是只看渲染结果。

## D-018 预告与证据合并：一条预告 = 一个时间窗口，里面挂 N 条推文

**背景**：老大的原话 —— 「这些信息应该合并成一条预告，然后是一条预告里面 4 条推文」。

此前同一件事被拆成了**三处**呈现，读的人得自己拼：

| # | 位置 | 内容 | 问题 |
|---|---|---|---|
| ① | 预告横幅 | 只挂**最新那条**推文的原文 | 另外 3 条在别处 |
| ② | 一行状态条 | 「另有 1 条指向同一时间窗口的预告（先铺垫、后宣布），不重复列出」 | **在陈述「我做了去重」这个实现细节**，不是用户能拿走的信息 |
| ③ | 折叠块 | 「综合 4 条推文指向 2026.09.22」 | 又一个独立单元，与 ① 的关系要自己推 |

②尤其糟：它把内部取舍当成内容往外发。用户看到「另有 N 条不重复列出」，既不知道是哪几条，
也不知道它们说了什么，只知道系统藏了东西。

**决策**：合并的逻辑**下沉到数据层**（`signals.mjs` 的 `buildForecasts()`），
产出 `forecasts: [{ window, evidence[], counts, ... }]`；渲染层（网页 / 小程序 / 采集日志）
只认这个字段，不再各自拼装。

```
forecasts = [
  { window, precision, evidence: [4 条推文], counts: {hard: 2, soft: 2}, clockHints, ... }
]
```

**合并的边界是「时间窗口」，不是「推文条数」** —— 按 `dayNum` 分组：

| 情况 | 结果 |
|---|---|
| 多条 explicit 指向同一天 | **一条**预告，证据 N 条 |
| explicit 指向不同的天 | **两条**预告，各挂各的证据 |

后者是刻意的：他先说周四、后改口周二时，把两个互斥的窗口拍成一条，
会给出一个**谁也不认的时间** —— 那比不合并更危险。

**假设只锚定一个日子**（D-017），所以当第二个窗口存在时它自己做证据链，退化为单条。
结构保持一致，渲染层不必写两套。

**呈现：网页端默认展开，窄屏默认收起。**

| 端 | 默认 | 理由 |
|---|---|---|
| 网页（≥760px） | **展开** | 证据是这条预告的**可追溯性**，不是可选的复核材料。藏着等于要求用户先信结论、再决定要不要验 —— 顺序反了 |
| 网页（<760px） | 收起 | 实测 390×844 下预告卡 1152px，「窗口 + 4 条推文 + 倒计时」一屏放不下。收起后 726px，倒计时回到第一屏 |
| 小程序 | 收起 | 同上，且手机上更紧 |
| 脚本被禁用 | 展开 | HTML 里本来就带 `open`，脚本只负责**窄屏收起**，退化成「内容一条不少」 |

**证据条目**只占两行（元信息一行、原文一行 clamp 两行），宽屏两列。这是 D-014 的延续：
页首堆砌会把倒计时挤出去，而倒计时才是这一页的主角。

**顺带修掉的三处既有缺陷**

| 缺陷 | 后果 |
|---|---|
| 证据条目里的时间贴的是 **UTC**（`createdAt.slice(0,16)`） | 同一条推文在页面上有两个相差 8 小时的时间戳（页面其它地方全部北京），与 `render.mjs` 顶部「一律按 Asia/Shanghai 渲染」的约定自相矛盾 |
| 来源写「回复 @udiWertheimer」（九个字） | 把元信息行顶断，「原推 ↗」被甩到下一行，看起来像另一个条目的东西 |
| 「承诺 / 提及」的标签在旧折叠块里才有 | 合并后不能丢 —— 前者决定窗口，后者只是旁证，混起来会让人以为 4 条推文分量相等 |

**首屏口径与实测**（判据：倒计时**底部** ≤ 视口高度，不是「顶部在视口内」）

| 视口 | 改前 | 改后 |
|---|---|---|
| 1440×900 | ✅ | ✅ |
| 1440×760 | ❌ 底部 768 | ✅ |
| 1280×720 | ❌ 底部 768 | ✅ 底部 693 |
| 390×844 | ❌ 底部 850 | ✅ 底部 709 |
| 375×667 | ❌ | ❌ 底部 741 —— **接受**：再压要动窗口块的文案本身，收益不抵复杂度 |

为拿到这几档，页首的尺寸整体收了一轮（顶栏 padding 26/22→20/16、`.sig` margin 26→18、
窗口行 padding 12→10、hero padding 46→30、counter margin 20→15 等，合计约 70px）。
**这不是审美调整，是首屏预算。**

**否决的选项**

| 选项 | 理由 |
|---|---|
| 保持三处，只把「另有 N 条」那行改写得好看点 | 治的是措辞，不是结构 —— 用户仍要自己拼归属关系 |
| 把所有 explicit 拍成一条（不按窗口分组） | 改口场景下会把两个互斥窗口混成一条，给出谁也不认的时间 |
| 证据默认收起（两端一致） | 把可追溯性变成「需要主动索取」的东西，与「网页端已成熟」的定位不符 |
| 窄屏也展开 | 实测把倒计时顶出第一屏，直接违反 D-014 |
| 把证据做成 `<details>` 但**不写脚本**、全靠 CSS | 纯 CSS 做不到「宽展开 / 窄收起」；用 checkbox hack 会把 HTML 弄得更脏 |

## D-017 时间证据跨推文聚合：同一天的多条线索收成一条假设

**背景**：老大连着两问 —— 「他不是都有 3am on a tuesday 这样的回复了吗？为什么没有明确时间」
以及「你需要做综合分析，而不是抓取到了一条 reset 信号就结束了」。

查下来是三件事同时成立：① 那些钟点**确实都被解析出来了**，只是单条看没有额度语境，
`window` 被置空、线索随之消失；② 解析器此前**没有钟点维度**，即使有额度语境也只到「全天」；
③ 系统**从不看推文之间**的关系 —— 逐条判完就结束。

**决策**：`detectSignals` 除逐条判定外，产出 `hypothesis`（`buildHypothesis()`）——
把指向**同一当地日历日**（`dayNum`）的推文收成一条证据链，并分明强度：

| 强度 | 来源 | 作用 |
|---|---|---|
| `hard` | `level === 'explicit'` | **决定窗口** |
| `soft` | 只有时间、没有额度语境 | 仅作旁证，**不改窗口** |

**为什么 soft 不能参与定窗口**：那等于「他随口提到某个周二 → 页面报一个重置时间」。
这个产品最不能出的错就是假信号 —— 漏检伤的是覆盖，假信号伤的是可信度，
而可信度是这个观测台唯一的资产。所以 `hypothesis.precision` 永远是硬证据的产物。

**聚合真正提升精度的地方**：同日的多条硬证据中，一条说到「天」、一条说到「钟点」时，
按 `PRECISION_RANK` 收敛到更精确的那条。只取「最近一条」会丢掉这个精度。

**钟点线索要显式列出「未采用」及原因**（`clockHints`）。「系统没看见」是缺陷，
「看见了但判它语境无关」是判断 —— 两者可信度完全不同，页面上必须区分得开。
老大问的正是前者，而真实情况是后者。

**时间线索一律不许丢**：`intent < 2` 的分支保留 `candidateWindow`
（词、精度、`dayNum`、歧义 note），不再直接 `window: null` 就结束。

**呈现**：网页端是 `<details>` 折叠块（默认收起），小程序端只下发摘要。
选择折叠而不是铺开，理由是 D-014 那次教训 —— 把复核材料放在页首会把倒计时挤出第一屏。

**被否的方案**：
- 把 soft 钟点也算进窗口（哪怕标注「可能」）→ 会造出「09-22 03:00 重置」这种没有依据的精确时间
- 给软证据单独做一块视觉 → 与 D-014 同类问题，喧宾夺主
- 在小程序端下发完整证据链 → 快照跟着小程序包走，且手机上没有折叠交互，铺开会把正文推走

## D-016 时间解析补上钟点维度，并给「A reset」加时态闸门

**背景**：同一次追问。他反复用「星期 + 钟点」埋时间（实测语料：
`11pm on a Tuesday, big startup energy`、`3am on a tuesday`），
而 `parseTimes` 此前最深只走到「星期 → 全天」，钟点被整段忽略。

**决策**：
1. 新增第 7 类时间表达：`3am` / `11pm` / `3:30pm` / `midnight` / `noon` → `precision: 'instant'`。
2. **钟点与同句的日期是一个整体**，合并且以钟点为准（`SPEC.clockInDay` = 96）。
   否则会同时产出「周二全天」和「某一个 3am」两个窗口，而排序会让那个**没有日期约束**的
   3am 抢先 —— 那是错的。
3. 句中**没有**日期时，钟点才自行取「最近的未来那一刻」。
4. 给名词化陈述加时态闸门：`occurredShape && !future.some(w => w.spec > VAGUE_SPEC)`。
   `"I promised a reset for Tuesday"` 形态上完全符合「A reset」名词化陈述，但它是**承诺**。
   此前之所以没暴露，是因为真实那句话里恰好有 "See you soon" 命中了 `RE_FUTURE`
   才侥幸走了预告分支 —— **靠巧合成立，不是判据成立**。

**顺带修掉两个既有缺陷**：星期分支与「月+日」分支漏传 `SPEC`（落到默认值 28，
即「最含糊的表达」）。后果不只是排序错 —— `future` 过滤对 `spec ≤ VAGUE_SPEC`
的表达要求「窗口过半还没过」，于是**当天下午说「reset on Tuesday」会因为当天窗口
已过半而被整条丢掉**。

**被否的方案**：
- 把「有没有时间词」（`RE_FUTURE`）当作判断未来的依据 → 太宽，
  一句 `See you soon` 就能把「刚重置过」翻成「将要重置」
- 钟点独立成窗口、不与被修饰的日期合并 → 会产生「今天 3am」这种错日期

## D-015 回复是一等来源：直接收 `/with_replies`，回复雷达退为兜底

**背景**：老大指出「他在别人帖子下的回复你也需要获取，很多消息是在回复中拿出来的」。

**先审计，再动手。** 现场是：回复只靠一条叫「回复雷达」的旁路 —— 盯住一批
「他可能会去回复的人」，抓他们推文的详情页，在回复列表里找他的回复。实测它的
对象池里只有一个账号（`udiWertheimer`），一轮扫 6 条详情页、命中 0。它为什么长成这样，
注释里写着前提：**「回复不进 profile 流；`/with_replies` 与 `/search` 在未登录态
都只返回『JavaScript is not available』空壳页」**。

**那条前提只对未登录态成立。** 实测登录态（CDP 驱动已登录 Chrome）访问
`x.com/thsottiaux/with_replies`：标题正常、`loggedIn: true`，一路能滚到 09-12
（上一次重置那天）。一轮全量收下 **52 条回复**，覆盖 30+ 个被回复者。

**决策**：

1. **主路径改为直接收 `/with_replies`**。`collectTimeline` 加 `path` 参数，新增
   `collectStreams` 在**一个浏览器会话**里跑完多条流。
2. **上下文必须在收割当时配对**（`pairReplyContext`）。`with_replies` 流把
   [原推文, 回复] 成对渲染，而虚拟列表滚过去就卸载 —— DOM 顺序是配对关系的唯一载体，
   事后再看只剩一堆散条目。配对结果存进 `inReplyTo`，识别侧早就写好的 `viaContext`
   规则（`ownIntent < 2 && ctxIntent >= 2`）这才第一次有了大批量输入。
3. **回复雷达默认关闭**（`--radar` 才开）。

**为什么雷达不能只是「再扩一扩池子」**：池子要人工维护，而回复流自己就带着
「他回复了谁」这个信息 —— 绕开现成的答案去猜，是用更高的成本换更低的覆盖率。

**被否掉的选项**：

| 选项 | 否掉的原因 |
|---|---|
| 只扩雷达对象池 | 人工维护 + 天生抽样（详情页只渲染部分回复），且实测命中 0 |
| 每条流各起一次 Chrome | 第二条流会复用到正在退出的实例，实测撞出 `CDP 超时：Target.createTarget` |
| 把回复塞进免登录 HTML 路径 | `/with_replies` 未登录就是空壳页，这条路是死的（与 D-009 同理） |

**实测收益**（2026-09-22 一轮全量）：

| 项 | 之前 | 之后 |
|---|---|---|
| 库内推文 | 16 条 | 69 条（17 原创 + **52 回复**） |
| 明确预告 | 0 条 | **2 条**，其中一条全靠上下文才读得出来 |
| 旧方案（雷达） | 扫 6 条详情页、命中 0 | 默认关，保留作兜底 |

最硬的一条证据是「OK fine. But it's also still coming in Tuesday」—— **原创流里
一个字都没有**，且它本身不含任何额度词。判定依据栏写的是：「上下文：回复
@udiWertheimer「ok tibo you guys didn't ship anythin…」· 本条不含额度词，
额度语境借自上下文 + 延续语气 → 判为预告」。

**连带处理**：

- `renderSignal` 按**时间窗口去重**预告。他习惯先铺垫后宣布，两条指向同一个窗口
  （09-19 的回复、09-22 的原创），并列会把倒计时挤出首屏 —— 与 D-014 是同一类问题。
- 小程序快照**不再下发 `rejected`**。它是排查材料，小程序一处都不读；而并上回复流后
  被排除的推文从个位数涨到 50+ 条，实测占快照体积的一半（47KB / 92KB）。

**代价（已知，接受）**：回复流的滚动深度比原创流大（条目多、密度低），全量一轮从
约 45 秒涨到约 90 秒；增量一轮约 41 秒。回复流失败**不判整轮失败**（记 `replyError`）。

## D-014 已发生的重置只做判定，不在页首列举

**背景**：D-013 把「已发生」补成第四档之后，页面的信号区变成**页首两块原文卡片**
（09-12 那两条各占一块），把真正的主角 ——「还要等多久」的倒计时 —— 挤到了首屏之外。
老大一句话否掉：「已经发生的不需要列举了啊」。

**他指的是对的，而且这是个产品判断不是审美问题。** 信号区回答的问题是
**「下一次什么时候」**，它天然是往前看的；而「已经发生」是往回看的事实。同一段事实
同时挂在三处载体上（顶部倒计时、下方「最近记录」、每轮采集日志），再在页首铺卡片
只是复述，代价是把可行动的信息挤走。

**决策**：**「判定」与「呈现」分开。**

| 层 | `occurred` 的地位 |
|---|---|
| 识别（`src/lib/signals.mjs`） | **保留全部能力** —— 分档、计数、`occurredAt`、置信度 |
| 呈现（网页 `/ 小程序横幅） | **不展示**。信号区优先级链回到 `explicit → hint` |
| 空闲态措辞 | 「没有检测到重置**预告**」—— 不能写成「没有检测到重置信号」，那是假话 |

**为什么不能顺手把判定也删掉**：D-013 补这一档的最初动机是**不许漏检** ——
早先的实现把 `Reset all propagated` 判成「已完成的过去事件」丢掉，**数据里就看不见
09-12 那次重置**，老大提的第一个问题正是这个。去掉呈现不等于去掉识别；
把两者混为一谈会把 D-013 修好的洞重新打开。

**代价（已知，接受）**：`signals.occurred` 目前没有消费方（既不呈现，也还没回写
`resets.json`）。它的价值落在「数据可查」与「后续自动收口」上，见 `data-source.md` §7。

**回归**：`scripts/test-miniprogram.mjs` 在【5】与【8b】两处**同时**断言
「已发生被识别出来（数据层）」与「已发生不进横幅（呈现层）」——
一边成立一边不成立就是这次改动被改坏了。

## D-013 已发生的重置必须有自己的一档，且识别与分类共用一份词表

**背景**：老大实测反馈「很明显的重置信号你都没检测到」。核实后确认属实：
2026-09-12 那天两条重置推文（`Reset all propagated`、`Hi Astra users. A reset and a quick update`）
**一条被判为噪音丢弃、一条被静默截断**。

**两层原因，都是设计缺陷，不是手滑**：

| 层 | 缺陷 | 实测证据 |
|---|---|---|
| 识别 | 只有三档，没有「已发生」。带过去时的重置被归入「已完成的过去事件，不是预告」直接丢 | 09-12 两条都进 `rejected` |
| 截断 | `signals` / `hints` / `rejected` 各 `.slice(0, 5)`，列表按时间倒序 | `checkedTweets: 16` 但三类合计只有 10 —— **吞掉 6 条**，被吞的恰是最早、最靠近上一次重置的那几条 |

**决策**：

- 新增 `occurred` 档，位置在 `explicit` 之后。它给的是**发生时刻**而不是倒计时窗口 ——
  「已经发生」和「将要发生」是两件事，不该共用一种呈现。
  ⚠ **呈现部分已被 D-014 取代**：识别与计数保留，但不在页首列举。
- 判定用**名词化陈述**：`RE_ANNOUNCE`（`A reset` / `the reset` / `another reset`…）
  表达的是「存在一次重置」这个事实。配三道反例闸门：`RE_HYPOTHETICAL`（if / unless / would /
  could / might）、`RE_FUTURE_PERFECT`（will have reset）、`RE_FUTURE`（有未来语气时名词化不作数）。
- **不静默截断**：`signals` / `occurred` 全量保留；`hints` / `rejected` 仍有上限，但触顶置
  `truncated: true`，让「看到的是全部」这件事可被验证。
- **采集侧的 `classify` 改为转发识别侧的 `classifyEvent`**。它们曾经各持一份词表、结论互相打架：
  识别侧把 `Reset all propagated` 丢掉，采集侧靠词表里的 `all` 把它蒙成 `reset` ——
  那个 all 是「全部传播完毕」，与额度无关，纯属巧合；同一天写着 `A reset` 的那条没有 all，
  就被判成 `other`。**同一份数据两套结论，是这类 bug 的共同形状。**

**回归**：`scripts/test-signals.mjs` 锁住「09-12 那两条必须都被认出（=2）」、
四类计数之和等于扫描条数、触顶状态显式，以及三条反例。改词表或改判定顺序必须跑它。

## D-012 出口代理必须实测探测，不读 `HTTPS_PROXY`

**背景**：排查「采集跑得通、却一条推文都没入库」时发现的隐蔽 bug。本机
`HTTPS_PROXY` 被沙箱设成 `http://127.0.0.1:57119` —— 那是**沙箱自己的出口端口**，
`curl -x` 它拿 x.com 实测 **HTTP 000 / 0 字节**。真实代理在 **7890**（实测 200 / 215,228 字节）。

**为什么之前的几轮没暴露**：采集复用了老大手动以 7890 起的登录窗口，连接根本不经过
我们传的代理参数，于是「看起来一直是对的」。一旦脚本自己起 Chrome（定时任务的常态），
代理参数才真正生效，结果就是静默拿到 0 条 —— 不报错、不崩溃，只是空。

**决策**：新增 `src/lib/proxy.mjs`，候选端口逐个 `curl` 实测探测（`7890 / 7891 / 1087 /
10809 / socks5h://1080 / 8888 / 6152 / 8118`），环境变量**排在最后**作兜底。
`X_PROXY` 显式设置即权威（`off` / `none` 表示直连）；显式设了就不再探测。
探测判据是「位置码不是 000」而非「200」—— 403 也证明代理通。

**为什么不能用「哪个端口开着」来判断**：端口开着只说明有进程在听，不代表它连得通 x.com
（57119 就是反例）。只有真的发一次请求才算数。

**顺带实测掉的两个假设**：`--remote-allow-origins='*'` 在当前 Chrome 153 上**不必要**；
而 `--user-agent` 是**必需**的 —— 少了它 headless 的 `HeadlessChrome` 会被 Cloudflare
稳定判成 403，容易被误归因为「代理出口 IP 不行」。

## D-011 增量采集是默认，读取按时间窗，且必须周期性全量回补

**背景**：老大提出两点 —— 已采到的内容要保存下来，后续只更新未读时间段；以及推文本身
带时间标记，不该废弃，分析时应当**按时间节点**读取再判断。

**决策**：三件事一起做。

| 变更 | 实现 |
|---|---|
| 增量优先 | `collectTimeline` 接受 `knownIds`，翻到**连续两整屏都已知**即停（`isKnownScreen`） |
| 时间窗读取 | `detectSignals` 只吃 `[windowFrom, windowTo]` 内的推文，窗口写进结果可复核 |
| 全量回补 | 距上次全量超过 `DEFAULT_FULL_SCAN_HOURS`（72h）或库为空时，自动退化成全量 |

**为什么增量不能取代全量**：X 没有「给我某段时间」的查询入口，增量只能靠「翻到已知就停」
来模拟。这假设时间线连续且单调 —— 而虚拟列表抖动会丢整屏、他也会删推。这些洞**增量
永远补不回来**（看到已知的就停了，不会往回想）。所以 72 小时一次的全量回补不是可选的
优化项，是正确性的一部分。

**为什么窗口下界取 `min(now - lookbackDays, sinceMs)`**：`lookbackDays` 保证不漏近期发言，
`sinceMs`（上次重置 − 24h 缓冲）保证「上一次重置以来」整段在窗内。两者取小，才不会因为
「重置太久没发生」而把窗口收窄到看不见重置那天。

**数据不废弃**：超窗的推文只是**不参与本轮判断**，一条都不删。口径按时间轴切，不按条数切。

**顺带修掉的一个既有 bug**：降级轮（免登录兜底）重建 `tweets.json` 时会丢掉
`coverage_since`。改成展开旧对象而非重建。

## D-010 本阶段不建外部告警通道

**背景**：M2 技术选型时讨论「采集失败怎么让你知道」。已查明一个技术事实：
**WorkBuddy 的飞书连接器是本机能力，GitHub Actions 跑在境外 runner 上，够不着它。**
所以「Actions 失败 → 调连接器发飞书」这条最直觉的路径不成立。

**决策**：**本次不配置任何外部告警通道**（飞书 / 企业微信 / 邮件服务 / 短信），
不新增 webhook、不新增 Secret、不新增接收端。老大拍板。

**为什么这个决定是安全的** —— 采集链路本身已经「失败可见」，不依赖推送：

| 机制 | 谁提供 | 额外配置 |
|---|---|---|
| workflow 失败邮件 | Actions 内置，自动通知仓库关注者 | 无需 |
| `/api/health` 端点 | 本项目后端，含数据新鲜度 | 无需 |
| 页面上的数据更新时间 | 产物本身，陈旧一眼可见 | 无需 |

再叠一层推送的边际收益只是「知道得早一点」，代价是长期维护一个凭证与接收端。
本阶段不付这个代价。

**对设计的一处反向要求**：既然没有外部告警，「数据停更」的发现责任全落在页面上 ——
所以**数据更新时间必须显著展示**，不能藏在角落。这条落到 M3 的 UI 上。

**否决的选项**

| 选项 | 理由 |
|---|---|
| 只有自己一人的飞书群 + 自定义机器人 webhook | 技术上最优（零权限门槛、不依赖本机开机），但本阶段不做；后续要接走这条 |
| 飞书自建应用 → 私聊 | 需开放平台建应用权限，还要处理 `tenant_access_token` 缓存，复杂度更高 |
| 本地 WorkBuddy 定时任务调连接器 | **把线上服务的告警挂在「本机是否开机」上等于没挂**，不能作主通道 |
| 引入第三方告警服务（如 Healthchecks） | 为单点需求引入一个外部平台与账号，不划算 |

## D-009 境内外分离：采集只在境外发生一次，产物双通道分发

> ⚠ **2026-09-22 更正（见 D-024）**：标题与「要解的矛盾」里的前提「`x.com` 境内不可达（采集必须在境外）」
> 已被证伪 —— Cloudflare 拦的是**机房 IP 段**，采集现由本机（住宅出口）承担，CI 不采集。
> 但本条的**结论不受影响**：单次采集、双通道分发、境内服务器不主动访问境外，全都仍然成立；
> 只是「境内外分离」这个命名应读作「**采集出口与服务入口分离**」。
> 另：正文里「git commit data/ + dist/」中的 `dist/` 已不进版本管理。

**背景**：M2 技术选型。已确认的资源前提是境内服务器（已有）+ 已备案域名 + 网页主站放 GitHub Pages。

**要解的矛盾**：两个硬约束把「采集」和「服务」分到了两个网络域 ——
`x.com` 境内不可达（采集必须在境外），而小程序要求后端域名已备案（服务必须在境内）。

**决策**：数据**只在境外采集一次**，然后朝两个方向分发，**境内服务器不主动访问境外**。

```
Actions 采集完成
   ├─ 通道 1：git commit data/ + dist/  →  GitHub Pages
   └─ 通道 2：POST https://<备案域名>/api/ingest  →  境内服务器落盘
```

**为什么不让境内服务器定时 `git pull`**：境内访问 `github.com` 虽然可达，但长期 HTTPS 链路一旦抖动，
就会出现「页面是新的、API 是旧的」这种最难排查的静默不一致。
而反方向 —— GitHub runner 访问境内服务器的公网入口 —— 没有任何网络障碍。
**把不可靠的方向换成可靠的方向，比加重试更有效。**

**幂等**：载荷带 `generatedAt`，服务端只接受更新的，旧数据回 `stale` 丢弃。全量覆盖而非增量追加。

**代价**：Actions 侧多一个 Secret（`INGEST_URL` / `INGEST_TOKEN`），服务器多一个 POST 端点。

**否决的选项**

| 选项 | 理由 |
|---|---|
| 后端也放境外 | 小程序域名必须已备案，境外域名备不了案（微信硬要求） |
| 境内服务器 pull GitHub | 见上，方向错 |
| 用云函数做中转 | 为一次 POST 引入一个额外平台与计费面，不划算 |

## D-008 用分段风险模型做时间预测，并把失败项一起公开

**背景**：老大要求「做出 reset 预测」。

**决策**：分段常数风险模型（按已等待天数分桶，桶内风险率恒定）+ 样本外平移校准。
**并且必须在页面上公开校准成绩，包括失败的那一项。**

**为什么不用 Brier 分数选参数**：7 天窗口的基准发生率就有 80.8%，闭眼猜「会」也不难看。
实测不同配置的 skill 长期在 ±10% 内正负翻转（全量等权 +7.22%，生产配置 −2.31%）。
**用 Brier 选型等于拟合噪声**，改用分位数覆盖率检验 —— 说「中位数 X 天」时历史是否真有一半落在 X 内，
这个指标糊弄不了。

**为什么必须公开失败项**：产品的可信度来自「可验证」，不是「准确」。
实测「7 天内是否发生」的 Brier skill ≈ −2.3%（不如直接按基准率猜），这一条也上页面。
只报好看的数字，等于把产品唯一的差异化赔掉。

**实证效果**：校准层把 `cov50` 从 70.0% 拉到 **50.0%**，近期中位偏差从 −2.65 天压到 −0.60 天。

方法论与全部回测数字见 `docs/model.md`。

## D-007 网页与小程序双端，共享同一套几何与信号

**背景**：老大已有一个备案通过的小程序，要求同时产出小程序版本。

**决策**：把图形几何抽成与渲染目标无关的「图元」描述（`src/lib/scene.js`），
网页端用 `src/lib/svg.mjs` 序列化成 SVG，小程序端用 `miniprogram/utils/draw.js` 画到 canvas 2d。

**为什么不做双实现**：两张图的坐标计算有几十个刻度、标签、异常值处理，
双实现一定会漂移，且漂移是静默的（两边都能画出图，只是数不一样）。

**为什么不做「服务端出图给小程序」**：小程序 `<image>` 不认 SVG；
要出 PNG 就得引入 resvg/sharp，破坏「零运行时依赖」这条底线（见 D-002）。

**注意**：几何必须**按目标尺寸重新布局**，不能把 900px 宽的桌面图等比缩到 345px ——
那样 11px 的图内文字会缩成 4px，等于没有。所以 `scene.js` 的所有函数都接受
`{ width, height, fontScale }`，小程序按自己的设备宽调用。

## D-006 信号识别必须区分「未来预告」与「已发生」

**背景**：老大要求「如果有明显的重置信号，要有明确提示，给北京时间和 Tibo 那边的时间」。

**决策**：`src/lib/signals.mjs` 分四级：`explicit`（预告，给时间窗口）>
`occurred`（**已发生**）> `hint`（线索）> `none`。

**`occurred` 这一档是补上来的，不是后来加的装饰。** 最初的实现只找预告，
把「已发生」判成「已完成的过去事件，不是预告」直接丢掉 —— 于是页面自相矛盾：
下方历史里那条显眼地标着「普通重置」，上方信号区却说「没有检测到重置预告」。
同一个事实两套结论。观测台的主问题本来就是「上次重置是什么时候」，
把已发生的事实丢掉等于不回答自己的主问题。详见 D-013。

**为什么必须有负向规则**：现有真实数据里有一条
「the main thing i was excited about launching this week will be next week instead」——
它含 "next week"，但讲的是**发布延期**，不是重置。如果不加语境判断就报「重置信号」，
这个功能的可信度当场归零。所以 `hint` 级别**不当作重置信号展示**。
`occurred` 放宽了识别面，因此配了三道反例闸门（假设语境 / 将来完成时 / 未来语气），
见 D-013。

**时区**：推文原文用的是发推者所在地的时间语境。因此一律同时给出
**北京时间**与 **Tibo 所在时区（默认 America/Los_Angeles）**，并算出两者时差，
不做「翻译成北京时间就完事」这种丢信息的处理。

**歧义**：英文相对时间词（"next Tuesday"、"next week"）本身有歧义。
不掩盖——主解读给出确定的日期窗口，若存在第二种合理解读则一并标注。

## D-004 倒计时改为逐位滚动，并显示到秒

**背景**：老大要求「距上一次额度重置希望是动态的，能有数字滚动效果」。

**决策**：把每一数字位做成一个 0–9 的竖向条（reel），用 `transform: translateY(-N em)`
配合 CSS transition 滚动。网页端在 JS 里渐进增强（脚本被禁用时回落到静态数字）；
小程序端在 WXSS 里做同样的事。

**为什么加秒**：只显示「天/时/分」时，数字最快要 60 秒才动一次，滚动效果基本看不见。
显示到秒后每秒都有一位在滚，才真正做到「动态」。

## D-003 采集放境外，服务本体可以放境内

> ⚠ **2026-09-22 更正（见 D-024）**：标题与正文的前提「`x.com` 境内不可达 → 采集必须由境外执行」
> 已被证伪 —— Cloudflare 拦的是**机房 IP 段**，与境内/境外无关。采集现由**本机（住宅出口）**承担，

**背景**：需求方希望有后端定时抓推文。

**决策**：内置调度器（`server/scheduler.mjs`）默认 30 分钟一轮；

## D-000 内核不是「预测」而是「描述分布」

**背景**：市面上 7~8 个站都在给「下次重置概率」。

**决策**：主视图是**等待生存曲线** —— 不预测未来，只描述过去，并把用户标在曲线的位置上。

**依据**：53 条记录里平均间隔 6.93 天，**中位只有 3.22 天**，标准差 11.40 天，最长 67.7 天。
均值被两次极端等待（49.7 / 67.7 天）硬拉高。所以「平均 7 天」倒计时是错的，
而「62% 概率」这种数字无法被用户验证。生存曲线可验证。

**后续修订**：老大后来要求加时间预测，于是补了 D-008 的分段风险模型 +
样本外校准，并且**必须在页面上公开校准成绩**。曲线与预测并存，不是替代关系。
